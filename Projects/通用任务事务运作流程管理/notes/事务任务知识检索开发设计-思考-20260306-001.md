# 事务任务知识检索开发设计-思考-20260306-001

## 1. 需求分析和目标分析

### 1.1 需求分析
基于 `think-学术事务运作流库与多层调度设计-20260305-002.md`，本轮需要把“设计理念”转为“可开发方案”，重点是三组能力：

1. 事务/任务管理表格与数据库系统。
2. 事务/任务管理 Agents/Skills。
3. 文献管理数据库与文献管理 Agents/Skills。
4. 知识数据库与知识管理 Agents/Skills。
5. 文献/数据检索流程与 Agents/Skills 改造。

你提出的核心判断是：

1. 路由决策在 CC，总经理 agent 做一步一决策。
2. AOK/AOF 更适合承载可复用事务、流程模板、表驱动状态与执行留痕。
3. 所有 agents 的每一步都需要可追溯、可记录、可管理。

该判断与当前架构一致，可作为开发总原则。

### 1.2 现有能力盘点（可复用资产）

#### A. ARW 现有 agents 可复用性

1. `项目经理 agent`：可直接作为总管理调度雏形，用于任务拆解、分派、回传格式约束。
2. `cn-literature-retriever`、`cn-data-retriever`：可直接承接一级事务中的文献/数据检索执行。
3. `data-engineer`、`rag-literature-econometrics-expert`：可承接数据管理、证据抽取与知识结构化。
4. `whitelist-auditor`、`reproducibility-auditor`：可直接承接双审计闭环。

结论：ARW 已有“事务执行层”与“审计层”主干能力，但缺少专门的“任务/事务表管理 agent”。

#### B. ARW 现有 skills 可复用性

1. 可直接复用：`cn-local-library-manager`、`api-data-fetch`、`rag-evidence-synthesis`、`variable-operationalization`。
2. 可间接复用：`model-routing-dispatch`（用于模型选择，不是事务表管理）。
3. 需补齐能力：任务状态机写表、事务边权更新、知识库存储治理。

结论：检索和证据综合技能已有，管理类技能不足。

#### C. AOK / AOL 可借鉴性

1. AOK `管理文档单元数据库`（`autodo-kit/src/affairs/管理文档单元数据库/affair.py`）
- 优点：增量更新、变更检测、索引重写、落盘一致性机制成熟。
- 适配建议：复用其“增量维护 + 清单/索引重建”思想，用于知识库和事务日志库维护。

2. AOL `library.py`（`autodo-lib/scripts/library.py`）
- 优点：`items/tags` 生命周期管理、关系表维护、manifest 同步、CLI 化操作成熟。
- 适配建议：复用其“条目表 + 关系表 + manifest + 命令入口”模式，用于事务/任务管理表。

结论：

1. 事务/任务管理表更像 AOL `items` 系统，应优先借鉴 `library.py`。
2. 文献管理中的原文单元化与索引维护更像 AOK `Unit DB`，应优先复用 `管理文档单元数据库`。
3. 两者组合最优，而不是二选一。

### 1.3 可行性与主要挑战

可行性：高。

挑战：

1. 若直接上全量表模型，开发初期复杂度高。
2. 现有 agents 侧重业务执行，缺少“写表一致性约束”。
3. 检索事务改造需兼容闭源授权闸门与审计约束。
4. 边权/概率路由需持续校准，否则会出现策略漂移。

## 2. 决策和计划

### 2.1 总体技术决策

1. 采用“CC 决策主控 + AOK/AOF 执行承载”的双层模型。
2. 决策权归 CC：下一跳事务选择、优先级、回退裁决、人工闸门。
3. 执行与存储归 AOK/AOF：事务执行、表更新、索引维护、日志落盘。
4. 所有 agent 动作必须结构化写入运行日志与状态表。

### 2.2 开发对象一：事务/任务管理表格与管理 Agents/Skills

#### 2.2.1 数据库系统设计（借鉴 AOL `library.py`）

建议先做 MVP 6 表：

1. `tasks`
- 任务主表，记录任务状态、优先级、负责人、当前一级事务。

2. `transactions`
- 事务主表，记录一级/二级事务定义、输入输出契约、版本。

3. `task_transaction_map`
- 任务与事务执行映射，记录 step_order、结果码、执行人。

4. `task_edges`
- 事务关系边，含 `base_tendency_score`、`dynamic_delta`、`transition_prob`。

5. `execution_runs`
- 每一步执行日志，记录 selected_edge、edge_score、edge_prob、审计结果。

6. `manifests`
- 表版本与快照元数据，支持回滚与审计。

实现策略：

1. 先用 CSV/JSONL + CLI（参考 `library.py`）快速落地。
2. 再平滑升级到 SQLite（保留相同 schema）。

#### 2.2.2 管理 Agents/Skills 设计

新建建议：

1. `task-state-manager`（agent）
- 职责：任务状态迁移、任务图维护、父子任务编排。

2. `transaction-state-manager`（agent）
- 职责：事务定义维护、边权维护、路由候选生成。

3. `table-maintenance`（skill）
- 职责：统一执行表增删改查、完整性校验、快照输出。

可复用：

1. `项目经理 agent` 作为上层 PM（总经理）调度。
2. `whitelist-auditor`、`reproducibility-auditor` 作为状态迁移闸门。

### 2.3 开发对象二：文献管理与知识管理（明确分层）

#### 2.3.1 文献管理层（极简 Zotero 无界面版）

文献管理不是知识提炼，而是“文献对象资产管理”，核心是条目和原文可追溯。

文献管理对象：

1. 文献元数据条目（题录、作者、期刊、年份、DOI、引用键）。
2. 文献原文文件与附件（PDF/CAJ/补充材料）。
3. 文献单元化切分结果（段落/标题/表格/公式）。
4. 文献向量化索引（用于检索召回，不代表知识结论）。

文献管理数据库建议：

1. `literature_items`：文献条目主表（增删查改）。
2. `literature_files`：原文与附件映射表。
3. `literature_units`：单元切分索引表。
4. `literature_vectors`：向量索引映射表。
5. `literature_manifest`：文献库快照与版本表。

实现建议：

1. 元数据管理借鉴 AOL `library.py` 的 items/tags/manifest 模式。
2. 原文切分与增量索引借鉴 AOK `管理文档单元数据库`。
3. 文献管理输出是“可检索文献资产”，不直接输出研究知识结论。

#### 2.3.2 文献管理 Agents/Skills 设计

新建建议：

1. `literature-library-manager`（agent）
- 职责：文献条目增删查改、引用键映射、重复条目治理。

2. `literature-index-maintenance`（skill）
- 职责：原文切分、向量索引维护、增量重建。

可复用：

1. `cn-local-library-manager`（本地文献盘点）。
2. `cn-literature-retriever`（检索与补全）。
3. `cn-web-acquisition`、`cn-subscribed-literature-access`（来源接入）。

#### 2.3.3 知识管理层（极简 Obsidian 无界面版）

知识管理是对文献和数据的深加工，核心是任务驱动的知识提炼与笔记网络。

知识管理对象：

1. 任务驱动知识笔记（结论、假设、方法适用前提、反例）。
2. 概念卡片与术语卡片（可引用、可回链）。
3. 证据链节点（结论 -> 证据片段 -> 文献条目/数据来源）。
4. 笔记向量映射与语义关联边。

知识数据库建议：

1. `knowledge_notes`：知识笔记主表（类似无界面 Obsidian note）。
2. `knowledge_links`：笔记双向关联表（note-to-note / note-to-literature）。
3. `knowledge_evidence_map`：知识与证据映射表。
4. `knowledge_vectors`：知识笔记向量索引表。
5. `knowledge_manifest`：知识库版本与快照表。

边界规则：

1. 文献管理回答“有什么文献与原文”。
2. 知识管理回答“从文献中提炼出什么可执行知识”。
3. 文献向量库用于召回原文片段，知识向量库用于召回加工后的观点和证据链。

#### 2.3.4 知识管理 Agents/Skills 设计

新建建议：

1. `knowledge-base-manager`（agent）
- 职责：知识笔记入库、版本治理、冲突合并、证据绑定。

2. `knowledge-index-maintenance`（skill）
- 职责：知识笔记向量化、链接校验、增量索引更新。

可复用：

1. `rag-literature-econometrics-expert`（证据抽取与方法知识化）。
2. `rag-evidence-synthesis`（证据矩阵）。
3. `variable-operationalization`（概念到变量知识映射）。

### 2.4 开发对象三：文献/数据检索改造

#### 2.4.1 是否可在 AOK 现有事务基础上改进

可以，建议“复用并分层增强”：

1. 复用现有事务目录中的文献处理链路：`导入和预处理文献元数据`、`合并去重文献元数据`、`解析与分块`、`语义预筛选`、`文献矩阵`。
2. 复用文档入库链路：`管理文档单元数据库`、`向量化与索引构建`。
3. 在其上增加“检索治理层”：权限闸门、来源可信度、失败回退与审计写表。

#### 2.4.2 检索 Agents/Skills 复用与新增

可直接复用：

1. agents：`cn-literature-retriever`、`cn-data-retriever`、`data-engineer`。
2. skills：`cn-local-library-manager`、`cn-web-acquisition`、`cn-subscribed-literature-access`、`api-data-fetch`。

建议新增：

1. `retrieval-governance`（skill）
- 职责：统一输出检索结果码、权限状态、来源级别和证据链。

2. `retrieval-router`（agent）
- 职责：按一级事务和边权倾向分值选择“文献检索/数据检索”下一跳子流程。

### 2.5 分阶段开发计划（MVP -> 扩展）

第 1 阶段（MVP，1-2 周）

1. 建立 MVP 6 表与 CLI。
2. 新建 `task-state-manager`、`table-maintenance`。
3. 把 `项目经理 agent` 接到写表链路，实现“每步有记录”。

第 2 阶段（扩展，2-3 周）

1. 接入文献管理库（条目 CRUD + 原文单元化 + 文献向量索引）。
2. 新建 `literature-library-manager`、`literature-index-maintenance`。
3. 打通任务-事务-文献三向关联键。

第 3 阶段（知识管理扩展，2 周）

1. 接入知识管理库（任务驱动提炼 + 笔记化 + 知识向量映射）。
2. 新建 `knowledge-base-manager`、`knowledge-index-maintenance`。
3. 打通任务-事务-知识三向关联键与证据映射。

第 4 阶段（检索治理，2 周）

1. 改造文献/数据检索为“可审计事务化流水”。
2. 新建 `retrieval-governance`、`retrieval-router`。
3. 接入倾向分值与概率路由校准日志。

### 2.6 开发落位确认（执行方式与目录规范）

#### 2.6.1 是否使用 AOK 事务进行开发

结论：是，采用“CC 决策 + skill 调用 + AOK 事务执行”的主路径。

推荐调用链：

1. CC（总经理/调度 agent）做任务级决策与下一跳选择。
2. CC 调用对应 skill（文献管理、知识管理、任务表维护等）。
3. skill 在 `scripts/` 中调用 AOK 事务/流程图执行器。
4. AOK 事务完成实际 CRUD、索引更新、日志落盘。
5. 结果码回传 CC，触发下一步调度。

#### 2.6.2 是否每个动作都在 agent 中硬编码

结论：不建议“每个动作都硬编码在 agent 中”。

边界建议：

1. agent 只硬编码：路由策略、输入输出契约、异常处理策略。
2. 具体 CRUD 与流程细节下沉到 skill 脚本与 AOK 事务。
3. 文献条目增删查改等高频动作必须沉淀为可复用事务，不应散落在 prompt 中。

#### 2.6.3 目录落位建议（本项目）

1. 事务/任务数据库目录。
- `database/tasks/`
- MVP 文件建议：`tasks.csv`、`transactions.csv`、`task_transaction_map.csv`、`task_edges.csv`、`execution_runs.jsonl`、`manifests.json`
- 升级后：`database/tasks/tasking.db`（SQLite）

2. 文献条目数据库目录。
- `database/references/`
- 建议文件：`literature_items.csv|db`、`literature_files.csv|db`、`literature_manifest.json`
- 原文文件仍放 `references/normal/fulltext/`，数据库只保存映射与索引。

3. 文献单元化与向量索引目录。
- `database/references/unit_db/`（单元索引与 data/*.txt）
- `database/references/vector_index/`（向量索引文件）

4. 知识管理数据库目录。
- `database/knowledge/`
- 建议文件：`knowledge_notes.csv|db`、`knowledge_links.csv|db`、`knowledge_evidence_map.csv|db`、`knowledge_manifest.json`

5. 知识笔记与向量索引目录。
- `database/knowledge/notes/`（结构化笔记文件）
- `database/knowledge/vector_index/`（知识向量索引）

6. 事务/任务 AOK 流程图程序放置目录。
- 优先放在 skill 对应目录的脚本路径：`.opencode/skills/<skill-name>/scripts/`
- 工作流定义目录建议新增：`.opencode/workflows/`
- 如需复用 AOK 现有事务源码：以 `autodo-kit/src/affairs/<事务名>/` 为上游，当前仓库 skill 脚本负责调用与适配。

7. 调度与审计日志目录（保持现有约定）。
- 运行日志：`logs/run/`
- 审计日志：`logs/audit/`

## 3. 任务分配

### 3.1 分配给任务运作智能体

任务 A：事务/任务管理表 MVP
1. 内容：实现 6 表 schema、CLI、快照与回滚。
2. 预期结果：可查询、可更新、可回放的任务/事务状态面板。

任务 B：管理类 agent/skill 首批上线
1. 内容：实现 `task-state-manager`、`transaction-state-manager`、`table-maintenance`。
2. 预期结果：CC 调度动作全部结构化落表。

任务 C：文献管理库主干接入
1. 内容：实现文献条目 CRUD、原文单元化切分、文献向量索引。
2. 预期结果：文献资产可管理、可检索、可追溯。

任务 D：知识管理库主干接入
1. 内容：实现任务驱动知识提炼、笔记化存储、证据链绑定、知识向量映射。
2. 预期结果：知识笔记可检索、可回链、可验证。

任务 E：检索流水事务化改造
1. 内容：复用 AOK 文献/数据相关事务并加治理层。
2. 预期结果：检索链路具备权限闸门、结果码、审计日志。

任务 F：复用资产对接与缺口补齐
1. 内容：建立“可复用/需改造/需新建”资产清单并执行。
2. 预期结果：减少重复开发，保证迭代节奏。

任务 G：目录与持久化落位初始化
1. 内容：初始化 `database/tasks`、`database/references`、`database/knowledge`、`.opencode/workflows`。
2. 预期结果：数据库、流程程序、日志路径统一可发现。

### 3.2 复用资产清单（实施起点）

1. 直接复用：`项目经理 agent`、`cn-literature-retriever`、`cn-data-retriever`、`data-engineer`、`rag-literature-econometrics-expert`。
2. 直接复用：`cn-local-library-manager`、`api-data-fetch`、`rag-evidence-synthesis`、`variable-operationalization`。

## 4. 监控和调整

### 4.1 监控指标

1. 表更新完整率：agent 执行步骤写表成功率。
2. 状态一致性：任务状态与事务状态冲突率。
3. 文献入库稳定性：文献条目与原文单元索引一致性。
4. 知识提炼有效性：知识笔记与证据链绑定完整率。
5. 检索可追溯率：来源、权限、证据链完整率。
6. 边权路由有效性：高 `transition_prob` 边的成功收敛率。
7. 复用率：已有 agents/skills/affairs 被复用比例。

### 4.2 调整机制

1. 若写表失败率高：优先收敛 schema，减少一次性字段扩张。
2. 若状态冲突高：加强 `task-state-manager` 与 `transaction-state-manager` 的写入事务边界。
3. 若文献索引不稳定：先收敛文献条目 schema，再调整单元切分策略。
4. 若知识质量波动大：强化任务驱动提炼模板与证据绑定校验。
5. 若检索链路回退过多：提高授权闸门前置率与来源预筛选阈值。
6. 若新建组件过多：优先复用现有 agent/skill，延后非关键新建。
7. 若目录分散或重复：以 `database/` 为唯一数据库根目录收敛。

### 4.3 本轮结论

1. 事务/任务管理表应优先借鉴 AOL `library.py` 的 items/tags/manifest 机制。
2. 文献管理应定位为“极简 Zotero 无界面版”：条目 CRUD + 原文单元化 + 文献向量索引。
3. 知识管理应定位为“极简 Obsidian 无界面版”：任务驱动提炼 + 笔记网络 + 知识向量映射。
4. 文献/数据检索应在 AOK 现有事务基础上改造，而非重写。
5. ARW 现有执行类 agents/skills 可大量复用，但文献/知识管理类 agents/skills 需要新增。
6. 以 CC 做决策主控、AOK/AOF 做执行承载的路线可落地且与当前设计一致。
