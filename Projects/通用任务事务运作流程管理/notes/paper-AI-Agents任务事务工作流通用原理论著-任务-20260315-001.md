# paper-AI-Agents任务事务工作流通用原理论著-任务-20260315-001

## 摘要

在 v3 版本中，任务事务工作流已经完成了主协议冻结：任务状态机、结果码协议、候选动作包、结构化决策记录和四类核心数据库均已具备工程基础。然而，v3 的控制面仍主要以“单 PA 强裁决 + 规则门控 + 程序控制器执行”为核心，这一结构足以支撑最小治理闭环，却尚不足以为后续多智能体强化学习提供统一的概念接口。若未来版本希望逐步走向多智能体强化学习，则系统需要尽早把状态、观测、动作、转移、决策者边界、证据记录与治理主体切换到 MDP 术语体系下。

本文提出 v4 版本的通用任务事务工作流原理模型。v4 的关键任务不是引入强化学习，也不是重写 v3 执行主干，而是把整个控制面从“规则裁决语言”升级为“MDP 术语语言”。在这一版本中，PA、TA、NA、AA 被统一定义为 Agent 角色，它们都具有状态集、观测集、动作集与决策集的形式化接口；但在当前阶段，真正承担最终裁决职责的仍然是决策部门，而决策部门的成员默认由 PA 与人类专家构成。也就是说，v4 的目标不是立即让所有 Agent 自治，而是先让未来所有 Agent 可以被置于同一类决策框架中表达、记录与比较。

围绕这一转变，本文把 v4 定义为从 v3 走向 v5 的中间态。v3 的核心价值在于冻结协议，v5 的核心方向是走向多智能体强化学习，而 v4 的职责则是完成术语、接口与记录口径的统一。为此，本文提出三项核心原则：第一，保留 v3 的状态机、结果码协议、四类数据库和执行主干；第二，把状态、观测、动作、转移、决策部门和 Agent 角色全部切换到 MDP 口径；第三，所有最终决策仍由决策部门给出，而不由强化学习模型直接决定。这样，系统一方面可以继续保持可解释、可审计和可运行，另一方面也能为后续策略学习保留清晰、稳定的数据接口。

本文进一步论证，v4 的意义不在于“比 v3 更智能”，而在于“比 v3 更可迁移”。只要状态、观测、动作和决策记录已经统一，未来无论加入 TA、NA、AA 的局部自治，还是引入多智能体强化学习，系统都不必再重写协议语言本身。相反，如果没有 v4 这一层中间态，团队将不得不在 v3 的规则语言与 v5 的学习语言之间做一次高风险跳跃，导致工程语义、历史记录与未来策略接口出现断层。

**关键词**：AI Agents；任务事务工作流；MDP 术语体系；决策部门；结果码协议；任务状态机；多智能体强化学习前置框架；结构化决策

## 1. 引言

### 1.1 问题背景

通用任务事务工作流若要承接开放任务，必须同时解决三个层面的问题。第一，任务推进本身并非固定顺序执行，而是在环境变化、权限波动、目标修正与外部介入中不断重组。第二，控制系统必须在可解释和可扩展之间保持平衡，既不能退回图外脚本式拼接，也不能直接跳入黑箱化智能。第三，系统若希望进一步演化到多智能体强化学习，就必须在此之前先把状态、动作、观测和决策接口统一起来。

v3 已经较好地解决了前两个问题中的一部分。它把工作流重新定义为任务驱动的连续控制闭环，并通过结果码协议与任务状态机把许多过去散落在图外的治理逻辑收口到统一结构中。但 v3 的问题在于：其概念语言仍主要围绕“规则”“候选动作”“PA 裁决”“程序控制器”展开，而不是围绕“状态”“观测”“动作”“转移”“策略主体”展开。对于当前工程运作，这并非致命问题；但对未来多智能体强化学习而言，这一差异会逐渐变成接口层面的阻碍。

### 1.2 v4 的理论定位

本文将 v4 定位为一个明确的中间态版本。它不是 v3 的简单增量，也不是 v5 的学习型原型，而是一次语言层和接口层的重构。v4 的目标可以概括为：

1. 在不破坏 v3 主干协议与主干执行器的前提下，引入完整的 MDP 术语体系。
2. 把 PA、TA、NA、AA 统一建模为 Agent 角色，即使它们当前不全部承担最终裁决。
3. 保留“决策部门”作为最终决策收口点，使现实运行仍依赖 PA 与人类专家，而不是依赖强化学习。
4. 为 v5 之后的多智能体强化学习准备统一的数据语言、行为语言与角色语言。

### 1.3 核心立场

本文的核心立场是：

1. v4 不追求立即自治，而追求接口先统一。
2. v4 不追求立即学习，而追求决策记录先标准化。
3. v4 不取消人类与 PA 的决策地位，而是让未来 TA、NA、AA 的自治能够在同一框架下被定义。
4. v4 仍以可解释、可留痕、可审计为第一原则。

2. 任务状态机沿用 v3。
3. 结果码协议沿用 v3。
4. 决策角色全面改用 Agent 术语表达。

6. 决策部门成为最终裁决主体。

8. 所有决策记录按 MDP 术语写入结构化数据库。

### 2.3 设计原则

1. 先统一术语，再升级策略。
2. 先统一接口，再升级自治。

4. 先把训练数据口径做好，再考虑训练算法。
5. 先保证与 v3 可兼容，再推进 v5 学习系统。

## 3. v4 总体框架

### 3.1 从控制器体系到 Agent 术语体系

v3 中的 TM、NM、AM 主要以程序控制器形式出现，PA 是唯一真 Agent。v4 并不立即改变执行现实，而是先改变表达结构。在 v4 中：

1. PA 被定义为项目级 Agent。
2. TA 被定义为任务级 Agent。
3. NA 被定义为节点级 Agent。
4. AA 被定义为事务级 Agent。
5. 人类专家被定义为外部高权限治理主体。

但这种定义并不意味着 v4 立即让 TA、NA、AA 直接自治。相反，v4 允许它们首先以“可表达、可记录、可扩展”的 Agent 接口存在，而把当前最终裁决仍保留在决策部门。

### 3.2 决策部门的理论地位

v4 中最重要的新对象不是单个 Agent，而是“决策部门”。决策部门是任务步决策的最终裁决主体，它接收来自各类 Agent 或控制层整理后的观测包，并返回最终动作。其默认成员为：

1. PA
2. 人类专家

后续版本可根据策略逐步加入 TA、NA、AA 的建议通道，甚至在更后续阶段让某些 Agent 成为正式成员。但在 v4 中，决策部门的存在保证了系统仍然拥有明确的责任收口点和现实治理边界。

### 3.3 v4 的中间态意义

如果说 v3 解决的是“如何把控制协议收口到统一结构”，那么 v4 解决的就是“如何把未来学习系统所需的术语和接口提前冻结”。因此，v4 的价值不是即时性能提升，而是长期迁移成本下降。

## 4. MDP 术语体系下的对象重述

### 4.1 状态

在 v4 中，状态不再只被理解为数据库里的一组字段，而被统一理解为工作流在某一任务步上的结构化世界快照。对单个 Agent 而言，状态可以是该 Agent 所管理对象的局部状态；对主闭环而言，状态则是任务、节点、事务、父子关系、阻断信息与策略元数据的综合表示。

### 4.2 观测

观测是某个 Agent 或决策部门在当前时刻能够看到的信息摘要。v4 特别强调：并不是所有主体都直接读取世界全量状态，而是通过 TM、NM、AA 等整理后的观测包进行工作。这样做既保留了现实运行的效率，也与未来部分可观测学习框架保持兼容。

### 4.3 动作

动作沿用 v3 已经冻结的任务动作集合，即 `continue/retry/backtrack/suspend/split/human_gate/complete/fail/cancel`。v4 的改动不在于发明新动作，而在于把动作提升为统一 Agent 术语中的“动作空间”。

### 4.4 转移

转移仍由 v3 状态机和执行主干定义。也就是说，v4 不改变动作执行后的状态迁移规则，而是仅把这些迁移规则重新解释为 MDP 语义下的转移约束。

### 4.5 决策

v4 最关键的变化在于：决策不再默认等价于某个固定控制器的规则判断，而是被统一理解为“决策部门基于当前观测，对候选动作空间做出选择”。这一选择可以来自 PA，也可以来自人类专家，也可以在后续版本中逐步接纳 TA、NA、AA 的自治或学习型策略。

## 5. Agent 角色体系

### 5.1 PA

PA 是项目级 Agent。它的职责仍然最接近 v3 中的唯一真 Agent，但在 v4 里，它被明确放入更大的 Agent 角色体系中。PA 关心的是全局目标推进、跨任务治理、一致性判断和高层风险边界。

### 5.2 TA

TA 是任务级 Agent。它对应原先任务管理层的职责语义，但在 v4 中不再只被理解为程序控制器，而被定义为未来可能具备自治能力的任务级 Agent。当前版本中，TA 可以更多承担状态组织、观测整理、任务摘要与候选动作空间准备的职责。

### 5.3 NA

NA 是节点级 Agent。它对应节点语义、节点级风险、路径约束和局部候选解释。v4 中 NA 的意义主要在于给未来节点级自治保留明确接口，而不是立即让其成为默认裁决主体。

### 5.4 AA

AA 是事务级 Agent。它承接事务执行、回执标准化、失败解释与输出契约整理。AA 并不直接等于执行器本身，而是执行层和控制层之间的 Agent 化接口对象。

### 5.5 人类专家

人类专家不是工作流内部的普通 Agent，而是高权限外部治理主体。v4 中，人类专家与 PA 一起构成决策部门的默认成员，从而保证复杂、高风险、需要责任承担的动作仍能被现实世界接受。

## 6. 决策部门原理

### 6.1 为什么需要决策部门

如果 v4 直接让所有 Agent 各自裁决，系统会立即引入与 v5 类似的多智能体协调复杂度；但如果 v4 仍完全停留在单一 PA 模式，又无法真正完成术语和角色框架的升级。因此，决策部门是一个必要的中间机制。它允许系统在保留最终裁决收口的同时，提前把多角色 Agent 框架搭起来。

### 6.2 决策部门的输入

决策部门在 v4 中接收以下输入：

1. 当前任务状态摘要。
2. 当前节点状态摘要。
3. 当前事务回执。
4. 候选动作空间。
5. 历史摘要与证据集合。
6. 父子任务关系摘要。
7. 必要时来自 TA、NA、AA 的局部建议。

### 6.3 决策部门的输出

决策部门输出的是结构化决策结果，而不是自然语言结论。其核心字段包括：

1. `selected_action`
2. `reason_code`
3. `reason_text`
4. `next_node_uid`（如需要）
5. `split_children`（如需要）
6. `human_gate_request`（如需要）

### 6.4 与 v3 的连续性

v4 的决策部门并不否认 v3 的候选动作包和结构化决策记录，恰恰相反，它是对这套机制的重新命名和重新定位。v3 的 `DecisionPacket` 和 `DecisionResult` 在 v4 中可以继续存在，只是其语义要改写为“决策部门输入包”和“决策部门输出结果”。

## 7. 结果码协议与任务状态机的延续地位

### 7.1 为什么结果码协议必须保留

结果码协议是 v3 留下来的最重要结构资产之一。所谓结果码协议，指的就是执行层向控制层输出的统一信号语言，包括 `PASS/RETRY/BACKTRACK/BLOCKED` 以及阻断原因码、阻断范围、重试许可、人工需求和证据字段。没有这套协议，Agent 体系再完整，也只能重新退回字符串日志式的脆弱模式。

### 7.2 为什么任务状态机必须保留

任务状态机规定的是任务从一种状态跳到另一种状态的硬边界。它相当于整个工作流系统的制度约束。v4 即使引入了更多 Agent 术语和决策部门，也不能允许系统绕过状态机去自由跳转，否则结构化治理就会失效。

### 7.3 v4 的真正变化在哪里

v4 不改变结果码协议，也不改变任务状态机；v4 改变的是对它们的解释方式。它们不再只是控制器内部的工程结构，而是被正式纳入 MDP 术语体系中的环境信号与状态转移约束。

## 8. v4 与 v5 的关系

### 8.1 v4 为什么不是终点

v4 的任务不是完成学习系统，而是为学习系统提供可稳定承接的接口语义。如果未来 v5 要走向多智能体强化学习，那么它最需要的不是更多新的动作，而是已经统一好的状态、观测、动作、角色、证据和决策记录口径。

### 8.2 v5 为什么可以建立在 v4 之上

只要 v4 已经把 PA、TA、NA、AA 都放入同一个 Agent 术语框架里，那么 v5 无论是选择逐层自治、分层学习，还是多智能体联合学习，都不必再重新定义系统语言。训练阶段要做的只是替换决策者，而不是重写整个记录系统。

### 8.3 v4 的长期价值

v4 的真正价值不在于让当前版本立即更聪明，而在于避免未来版本因术语切换而产生架构断层。它是一次面向未来的接口冻结，而不是一次面向当下的激进自治升级。

## 9. 结论

本文提出了 v4 版本的任务事务工作流原理模型。与 v3 相比，v4 的关键并不是新增复杂能力，而是把整个控制面切换到 MDP 术语体系，并正式引入 PA、TA、NA、AA 与决策部门的角色框架。v4 仍保留 v3 的结果码协议、任务状态机、四类数据库和执行主干，也仍由 PA 与人类专家构成默认决策部门；但与此同时，v4 已经为未来多智能体强化学习铺设了统一的概念语言、角色语言和数据语言。

从这个意义上说，v4 是一个非常关键的中间态。它让系统既不必在当前阶段承担学习型策略的不稳定性，也不必在未来版本到来时再经历一次高风险的术语与接口重构。只要这一版的状态、观测、动作、决策记录和角色边界被稳定下来，v5 之后的多智能体强化学习就有了真正可以承接的工程支点。

## 10. 开放任务环境中的控制难题

### 10.1 开放任务不是封闭脚本

开放任务环境与传统脚本流水线之间的根本差异，在于前者面对的对象不是预先完全枚举的输入集合，而是持续变化的现实情境。一个真实任务在推进过程中，常常会遇到目标表述变化、资源不可用、依赖对象延迟响应、权限状态变动、上游需求重写、下游验证口径变化等问题。若系统只按静态步骤表执行，那么这些扰动就会把整个流程撕裂成无数图外修补动作，最终导致系统名义上有流程，实际上仍靠人工兜底维持。

任务事务工作流的提出，本质上就是为了从这种“脚本假稳定”中走出来。系统不再假设每一步都会成功，也不再假设所有失败都能被本地重试解决。它承认任务推进本身是一种连续控制过程，承认失败、阻断、回溯、拆分、人工介入与目标修正都是主流程的一部分，而不是异常噪声。正因为如此，v3 才会引入结果码协议和任务状态机；而正因为开放任务仍将持续变复杂，v4 才必须进一步引入 MDP 术语体系，对这种连续控制进行更稳定、更统一的描述。

### 10.2 规则系统为何会逐渐逼近表达边界

单纯的规则系统在任务数量较少、场景较单纯时往往是有效的。开发者可以用若干条件判断和优先级列表把动作选择组织起来，系统也能跑通最基本的闭环。但当任务逐渐进入复杂开放环境时，规则数量会出现三个问题。第一，规则越来越多，解释成本越来越高。第二，规则之间的交互越来越密，局部改动可能触发全局副作用。第三，规则语言天生不善于表达“谁在依据什么观测对什么动作空间做选择”这一类未来学习系统特别关心的问题。

换言之，规则系统的问题并不总是立即表现为“不能运行”，而更常表现为“可以运行，但越来越难以迁移、比较、学习和治理”。v4 的提出，就是为了在规则系统尚未完全失效之前，提前完成概念升级。它不是否认规则的价值，而是把规则降格为观测整理、候选动作生成和治理约束的一部分，而把更上层的语言切换为状态、观测、动作、转移、决策者与证据记录。

### 10.3 为什么不能直接跳到强化学习

从表面看，既然未来要走向多智能体强化学习，那么似乎最直接的做法就是立刻构建学习型策略，让系统在真实数据中不断训练。但这种跳跃在工程上风险极高。原因至少有四点。

第一，当前系统的历史记录口径并非天然为训练准备。很多字段是工程调试字段，而不是策略学习字段。第二，当前角色体系尚未完成统一。PA、TA、NA、AA 在现实执行中承担的边界不同，但若没有统一术语，就无法构造清晰的训练样本。第三，当前系统的责任治理仍要求高解释性和高可审计性，直接引入学习型策略会导致责任边界模糊。第四，强化学习真正有效的前提之一是状态、动作和回报语义足够稳定，而这恰恰是 v4 想先完成的工作。

因此，v4 的中间态意义并非保守，而是务实。它先把语言统一、接口统一、记录统一、角色统一，再把学习问题留给后续版本。这种顺序能显著降低系统演化中的制度断层和数据断层。

## 11. 状态、观测与世界模型的工程化表达

### 11.1 世界状态不是一张表，而是一组相互制约的结构

在任务事务工作流中，所谓世界状态，并不是某个单独对象的一行记录，而是一组相互制约的结构。至少包括以下几个方面：任务对象自身的状态、节点位置与路径信息、事务执行结果与回执、父子任务依赖、资源与权限状态、环境约束、人工介入记录、历史决策证据、策略元数据等。任何一个任务步上的决策，实际上都不是在孤立字段上完成的，而是在这一整组结构关系上完成的。

v4 要求系统在理论上承认这种复合状态，而不是把决策简单理解为“某个 if 条件满足则触发某动作”。这样一来，即使当前实现仍然通过数据库、缓存对象和结构化摘要来承载状态，系统在概念上也已经转入了更高分辨率的表达层次。未来无论是规则治理、统计分析还是策略学习，都将以这一复合状态视角为前提。

### 11.2 局部状态与全局状态的分层

在多角色 Agent 框架下，全局状态和局部状态必须被区分。PA 关注全局项目推进，因此它更接近全局状态；TA 关注单个任务及其上下文，因此它面对的是任务级局部状态；NA 关注节点条件与路径语义，因此它最关心节点级局部状态；AA 则更接近事务级执行状态和回执结构。不同角色所见并不相同，但这些局部状态都必须能映射回同一个可组合的世界状态描述框架。

这种分层非常重要。因为没有分层，系统就只能在“所有主体都看全量状态”和“每个主体都只看碎片信息”之间摇摆。前者在工程上过重，后者在理论上失去统一。v4 的做法是：允许不同角色拥有不同的局部状态表示，但要求这些表示都能够被放回一个共同的状态语义框架内，从而保证跨角色分析和后续学习成为可能。

### 11.3 观测包的必要性

在开放环境中，决策者通常不直接面对未经整理的全量事实，而是面对一个经过压缩、聚焦和结构化的观测包。v3 中已经存在类似做法，例如候选动作包、事务回执、节点上下文等。v4 做的，是把这些对象正式提升为观测语义的一部分。也就是说，系统不再把它们仅仅视为工程传参对象，而是把它们理解为 Agent 或决策部门在某个时刻可以获得的信息界面。

观测包有三个作用。第一，控制复杂度。决策部门不必每次都重新理解所有底层结构。第二，控制责任边界。哪个角色能看到什么、基于什么做决定，可以被明确记录。第三，控制历史可追溯性。未来回放某次决策时，我们不仅能看到结果，还能看到当时究竟看到了什么。

### 11.4 部分可观测性与现实一致

任务环境天然具有部分可观测特征。并不是所有外部约束都能被系统立刻感知，也不是所有任务状态都能被完全结构化描述。某些信息只能在事务执行后才显现，某些信息只能通过人工反馈确认，某些信息甚至只在更高层治理主体那里才存在。这意味着，把工作流直接想象成一个完全可观测的简单系统，反而会遮蔽真实问题。

v4 选择正视这种现实。它不要求所有角色都拥有全知状态，也不假装当前记录已经足够完整。它只是要求：无论信息是否完整，系统都要用统一的观测语言来记录“已知什么、未知什么、缺失什么、谁知道什么、谁需要补充什么”。这一点对未来学习尤其重要，因为只有承认部分可观测性，后续策略模型才不会建立在虚假的全知假设上。

## 12. 动作空间、候选动作与动作约束

### 12.1 为什么 v4 不扩动作集

很多系统在版本升级时喜欢新增动作，以显示能力扩张。但对任务事务工作流而言，动作空间过快膨胀反而会损害稳定性。v3 已经冻结了一组具有良好治理意义的任务级动作：继续、重试、回溯、挂起、拆分、人工门控、完成、失败、取消。这组动作并不奢华，却已经覆盖了开放任务推进中的大多数关键操作类型。

v4 选择保留这一动作集合，原因有三。第一，这组动作已经与状态机形成稳定配对。第二，这组动作已经与结果码协议形成稳定映射。第三，未来学习型策略最需要的是稳定动作语义，而不是频繁改写动作词典。换句话说，v4 要升级的是对动作的理解层次，而不是动作集合本身。

### 12.2 候选动作不是最终动作

v3 中候选动作构建机制已经存在，但在很多直觉里，人们容易把候选动作列表误解为接近最终决策本身。v4 要特别强调，候选动作空间只是“可被选择的动作集合”，而不是“已经被选择的动作”。这一区分看似简单，却极其关键。因为只有把候选动作空间和最终决策区分开来，决策部门、角色建议、历史比较和后续学习才有清晰对象。

在 v4 中，候选动作更像是系统在当前约束下整理出的合法动作边界。它既受规则约束，也受状态机约束，还受当前观测质量约束。例如，当依赖未就绪时，继续动作可能被降权甚至从候选集中剔除；当风险过高时，人工门控可能被提升；当父任务已失败时，某些局部动作可能不再具有实际意义。也就是说，候选动作空间本身就是治理的结果，但它仍然不是最终裁决。

### 12.3 动作约束的三重来源

v4 可以把动作约束概括为三重来源。第一类是制度约束，即任务状态机和结果码协议所定义的硬边界。第二类是场景约束，即当前资源、依赖、权限、目标与证据条件带来的现实限制。第三类是治理约束，即组织上不允许某些角色在某些条件下直接执行某些动作，例如高风险完成、跨范围取消、带破坏性回溯等。

这三类约束的存在，使得动作空间从来不是抽象自由空间，而是受规范塑形的工程动作空间。v4 的价值在于把这种塑形过程记录清楚，而不是把它埋进分散的条件判断里。只有这样，未来我们才能区分“某动作没有被选中”与“某动作根本不合法”之间的差异。

### 12.4 动作空间稳定对未来版本的重要性

对 v5 及以后版本而言，稳定动作空间是极其宝贵的资产。无论未来采用何种多智能体策略，只要动作语义长期稳定，历史记录就具备持续可训练性与可比较性。相反，如果动作词典每个版本都改，历史数据就会迅速贬值，策略迁移成本会急剧上升。

因此，v4 的保守恰恰是一种前瞻性设计。它把系统升级的重点从“新增动作能力”转移到“提升动作解释层级”，使得动作空间能成为跨版本的稳定基础设施。

## 13. 决策部门的治理结构与责任闭环

### 13.1 决策部门不是装饰性概念

在很多系统设计中，“部门”“委员会”“审议层”之类的说法容易沦为抽象隐喻，最后并未真正进入工程对象。v4 不能接受这种空泛表达。决策部门必须是一个真实存在的治理对象，具有明确输入、明确输出、明确责任边界、明确成员资格和明确升级路径。否则，它就会退化成“仍然由某个 Agent 决定，只是换了个名字”。

因此，v4 对决策部门的要求是：它必须成为所有高价值任务步决策的正式收口点。系统要能记录一次决策属于哪个部门实例、由哪些成员参与、使用了什么观测包、选择了什么动作、给出了什么理由、是否触发人工确认、是否留下补充意见。这种记录不是为了官样文章，而是为了让“最终谁负责”成为可审计事实。

### 13.2 成员结构为什么默认是 PA 与人类专家

v4 之所以将默认成员限定为 PA 与人类专家，并不是因为 TA、NA、AA 不重要，而是因为默认成员必须兼顾两个维度：一是足够理解系统整体目标，二是能够承担现实责任。PA 作为项目级 Agent，天然更接近全局目标和跨任务协调；人类专家作为高权限治理主体，则能在复杂不确定场景下进行价值判断、风险承担和组织协调。

相比之下，TA、NA、AA 虽然在未来可以逐步承担更多自治职责，但在 v4 当前阶段，它们更适合作为建议源和观测整理者，而不是默认最终裁决者。这种安排既避免了过早放权，也为后续逐步升级留下清晰路径。

### 13.3 决策部门内部不是黑箱投票

决策部门的存在不意味着内部过程必须复杂化，更不意味着要引入形式主义的多轮表决。v4 更强调结构化裁决而非程序化拖延。也就是说，部门内部可以非常简洁，但必须留下明确记录：谁提出了什么意见、最终谁确认、为什么如此决策、是否与默认推荐动作一致、若不一致则差异在哪一层。

这种记录方式有两个好处。第一，它能帮助团队积累“规则推荐与最终裁决之间的偏差样本”，这对未来优化非常重要。第二，它能帮助人类理解系统究竟在什么地方需要人工治理，什么地方已经足够稳定，可以逐步放权给更低层角色或学习系统。

### 13.4 责任闭环与现实组织的兼容性

任何工作流系统若要进入真实组织，就必须面对一个问题：谁对系统行为负责。仅靠技术上“能跑通”远远不够。v4 引入决策部门，就是为了让任务事务工作流能与现实组织责任结构对接。某些动作可以由默认自动路径直接执行，某些动作必须进入部门确认，某些动作则必须人工签收。这样，系统才不会在关键场景下变成无人负责的自动化黑箱。

从长远看，这种兼容性也是未来多智能体系统走向真实应用的前提。学习型策略可以提供建议、排序、局部自治，甚至逐步成为正式成员，但责任治理的语言必须先被建立起来。v4 做的正是这一层基础建设。

## 14. PA、TA、NA、AA 的角色重构

### 14.1 角色重构的必要性

如果继续沿用 v3 的习惯，把 PA 看成唯一真 Agent，而把 TM、NM、AM 都视为程序控制器，那么未来一旦要讨论多智能体协作，语言会立刻失真。因为在那样的语言下，某些角色天生就没有状态、观测和动作空间，后续只能通过一次突兀的概念跳跃，把原先的“控制器”硬改成“智能体”。v4 试图避免这种断裂。

它采用更稳健的办法：先在术语层承认 PA、TA、NA、AA 都是 Agent 角色，再根据当前版本的治理能力，决定它们在现实运行中拥有多大的决策权。这意味着“是不是 Agent”与“当前有没有最终裁决权”被区分开来。前者用于建立统一语言，后者用于控制现实风险。

### 14.2 PA 作为全局协调 Agent

PA 之所以在 v4 仍然居于核心位置，不是因为系统要永远停留在单 Agent 结构，而是因为在当前阶段，全局协调能力仍主要集中在 PA 这里。PA 能够理解目标优先级、跨任务依赖、组织边界和长期推进路径，因此它适合继续担任决策部门的关键成员。

但与 v3 不同的是，v4 不再把 PA 的重要性建立在“其他角色都不是 Agent”之上，而是建立在“PA 当前拥有更高层次的全局治理权限”之上。这种表述更清晰，也更适合后续权力迁移。

### 14.3 TA 作为任务级组织 Agent

TA 的价值不只是“管理任务”，更在于把任务推进所需的局部世界整理成可决策对象。它能够聚合任务级上下文、生成阶段性摘要、识别需要拆分或挂起的局部信号，并把这些信息组织成对决策部门有意义的观测包。未来如果某些任务类型高度稳定，TA 也可以逐步承担更多局部裁决权。

因此，在 v4 中，TA 既是当前的组织者，也是未来的自治候选者。把它纳入 Agent 体系，正是为了使这种演化在概念上连续。

### 14.4 NA 作为路径与语义守卫 Agent

节点级语义往往决定了一个任务步的局部目标、进入条件、退出条件和证据口径。NA 的意义就在于，它不是单纯保存节点配置，而是承担路径语义解释、节点风险识别和局部动作合理性判断的职责。许多过去分散在图配置和条件判断中的东西，在 v4 中都可以被视为 NA 的知识边界。

这一定义的重要性在于，未来若要对节点级行为进行优化，系统已经有了自然承载对象，而不必重新寻找“到底谁对节点负责”的概念位置。

### 14.5 AA 作为执行回执桥接 Agent

AA 是最容易被误解的角色。很多人会把事务执行器本身当作 AA，但这并不准确。AA 更像是执行层与控制层之间的 Agent 化桥梁。它不仅关心事务是否执行成功，还关心执行结果如何被翻译为结构化回执，如何附带证据，如何表达失败原因，如何决定某次执行结果是否足以支持上层决策。

因此，AA 的存在把“执行动作”与“解释执行结果”区分开来。这种区分非常关键。因为未来无论是规则系统还是学习系统，都必须依赖可比较、可积累、可追溯的执行回执，而不是依赖零散日志。

## 15. 结构化记录、证据沉淀与历史回放

### 15.1 为什么历史记录不是附属物

在很多自动化系统中，历史记录只被当作运维辅助材料，用来在出错时排查日志。但对任务事务工作流而言，历史记录本身就是系统能力的一部分。因为任务推进不是瞬时行为，而是需要连续判断、连续解释和连续治理的过程。若没有高质量的历史记录，就无法复盘一次任务为什么这样走、某个动作为什么被选中、某次人工介入到底改变了什么。

v4 把历史记录提升到更重要的位置。它要求结构化记录不仅包含“做了什么”，还包含“当时看到了什么、有哪些候选、谁参与了决策、理由是什么、是否与默认推荐不同、差异证据是什么”。这类记录的价值，在当前版本中用于审计和优化，在后续版本中则可以直接转化为学习样本和比较样本。

### 15.2 证据链的最小闭环

一条有价值的证据链，至少应包含以下内容：当前状态摘要、观测包、候选动作空间、最终动作、结果码、执行回执、后继状态变化、人工补充意见。如果缺少其中关键部分，系统就很难在事后回答一个简单问题：这次决策究竟是合理但失败，还是信息不足导致的错误判断。

v4 的贡献在于把这些对象从“可能存在的调试字段”提升为“默认应当沉淀的制度化记录”。只有这样，历史数据才会在时间上越积越有价值，而不是越积越混乱。

### 15.3 回放能力为何是未来学习的前提

未来若要引入学习型策略，仅仅有最终动作和任务是否成功的结果是不够的。系统需要能够回放当时的观测条件、动作候选、局部约束和人工意见，才能理解某次决策为何被作出、某种策略为何优于另一种策略。也就是说，回放不是锦上添花，而是训练前提。

v4 虽然不做强化学习，但它从一开始就用适合回放的方式去组织记录。这使得系统在未来进行离线评估、行为克隆、策略比较或风险审计时，不需要再回头补建整套日志制度。

### 15.4 从复盘文档到结构化数据库

组织内部常常会写复盘文档，但文档形式的复盘有一个局限：它更适合表达结论，不适合表达大规模可计算样本。v4 的目标不是取消文档复盘，而是让文档复盘建立在结构化数据库之上。这样，复盘就不再只是少数案例叙述，而可以逐步转化为跨任务、跨场景、跨版本的系统级比较材料。

## 16. 典型场景分析

### 16.1 场景一：事务成功但目标尚未满足

很多工程系统会把“事务执行成功”误当成“任务已经推进成功”。但在任务事务工作流中，这两者并不等价。某个事务可能按照输入契约成功返回，然而返回的结果并不足以支撑任务进入下一阶段。例如资料抓取成功了，但内容质量不足；文本生成成功了，但不满足结构要求；外部查询成功了，但关键信息缺失。在这种情况下，AA 可以给出结构化回执，TA 可以指出任务目标尚未满足，NA 可以补充当前节点的退出条件尚未达到，而最终是否重试、回溯、拆分或人工门控，应由决策部门裁决。

这一场景说明，v4 的角色分工不是为了制造复杂性，而是为了把不同层次的“成功”区别开来。执行层成功、节点条件满足、任务目标推进、全局项目方向正确，分别是不同层次的判断。只有把它们分开记录，系统才能真正理解任务为何停滞或偏航。

### 16.2 场景二：依赖未就绪导致阻断

开放任务中最常见的问题之一是依赖未就绪。某项任务本身并没有错误，但它所需的前置资源、外部答复或父任务结果尚未到位。若系统仍然盲目继续，只会制造重复失败和资源浪费。v3 已经可以通过阻断码和挂起机制表达这种情况；v4 则进一步把它置于观测与决策框架中：谁识别出了阻断，谁确认了阻断范围，当前候选动作有哪些，是否需要拆分出等待子任务，是否需要通知上层，是否需要人工介入。

这样，阻断不再只是一个错误状态，而是一次完整的治理事件。它既能被当前系统正确处理，也能成为未来优化等待策略和依赖管理策略的重要样本。

### 16.3 场景三：候选动作存在冲突

在复杂场景下，规则系统可能同时给出多个看似合理的候选动作。例如，某任务既可以继续尝试，也可以因风险升高而转人工门控；既可以就地重试，也可以回溯到上一个节点重新收集材料。此时最危险的做法，是让系统仅凭固定优先级表机械选一个动作，而不记录冲突来源。v4 的做法是把这种冲突显式保留下来，并交由决策部门结合证据做出最终裁决。

这类场景对未来学习尤其重要，因为策略学习往往真正需要的不是那些毫无争议的样本，而恰恰是这些“多个动作都似乎合理，但最后为什么选了其中一个”的高信息密度样本。

### 16.4 场景四：高风险动作需要人工签收

某些动作在技术上可以自动执行，但在组织上不应自动执行。例如取消一个仍可能恢复的重要任务、回溯并覆盖已有成果、对外发布高影响内容、改变某个正式流程的目标定义等。v4 通过决策部门和人工门控机制，使系统能够在技术可执行与组织可接受之间建立明确桥梁。这意味着系统不会因为“能自动”就默认“该自动”。

这正是 v4 相比纯自动化流水线的重要制度优势。它把高风险动作放入责任治理框架中，从而让自动化真正具备进入现实工作的条件。

## 17. 从 v3 到 v4 的迁移原则

### 17.1 迁移不是推倒重来

v4 并不要求把 v3 所有工程实现全部改写。相反，v4 的成功标准之一，就是尽可能在保留 v3 主干协议与执行路径的基础上完成概念升级。也就是说，迁移首先是命名体系、接口语义和记录口径的迁移，而不是运行时核心逻辑的全面推翻。

这种迁移方式有很强的现实意义。它允许团队边运行边升级，允许旧数据继续可用，允许现有测试与状态机继续发挥价值，也允许文档体系逐步同步。对一个已经具备一定基础的系统来说，这比全面重构更稳健。

### 17.2 先文档冻结，再接口落地

任何跨版本框架升级，最怕的是代码先行而语言未定。代码可以暂时工作，但一旦概念语言不稳定，后续所有实现都会因为理解偏差而分裂。v4 因此必须先完成原理文档、设计文档和附录文档的冻结，再逐步落地代码接口。这样做不是形式主义，而是为了确保团队在同一术语空间内讨论问题。

换言之，v4 的文档不是附属产物，而是框架升级本身的一部分。没有这一步，代码层面的“升级”很容易只是局部重命名，无法形成真正一致的控制面。

### 17.3 先补记录字段，再谈行为自治

若系统未来要走向更高自治，那么首先要补的往往不是策略本身，而是记录字段。没有稳定的状态摘要、观测包、候选动作记录、最终裁决记录、证据记录和人工意见记录，任何自治都无法被可靠评估。v4 的优先级因此非常明确：先保证系统知道自己做了什么、为什么这样做，再考虑让系统做得更多。

### 17.4 迁移中的兼容性原则

v4 应当坚持“新增语义优先包裹旧对象，而不是立即废弃旧对象”的原则。例如 v3 的 `DecisionPacket` 与 `DecisionResult` 可以继续保留，但文档和接口说明要将其重新解释为决策部门输入包和输出结果。这样，既减少破坏性改动，又逐步完成语义切换。

## 18. 从 v4 到 v5 的演化通道

### 18.1 为什么 v5 需要 v4 打底

v5 若要走向多智能体强化学习，需要一套长期稳定的训练与评估对象。最理想的情况不是“重新设计一个学习专用系统”，而是在已有工作流系统上自然长出学习层。要做到这一点，v4 必须先把状态、观测、动作、角色、部门、证据和责任口径都统一下来。只有这样，学习层才能插在清晰的位置上，而不是悬浮在系统之外。

### 18.2 哪些对象会在 v5 中被替换

v5 真正可能变化的，并不是全部基础设施，而主要是决策者本身。今天由决策部门主导的部分动作选择，未来可能逐步交由某些 Agent 的策略模型承担；今天由规则系统生成的部分候选排序，未来可能被统计模型或学习模型增强；今天由人工判断的某些低风险场景，未来可能被委托给经过验证的自治策略。但这些变化都建立在 v4 已经把对象边界说明清楚的前提上。

### 18.3 哪些对象应当尽量保持稳定

即便到了 v5，也有一些对象应尽量保持稳定，包括任务状态机、基础动作语义、结果码协议核心形态、结构化回执制度、历史回放能力和高风险动作的责任治理边界。这些对象越稳定，系统越容易在升级中保留组织可接受性与数据可持续性。

### 18.4 v4 的成功标准不是像 v5，而是支撑 v5

判断 v4 成败的标准，不应是它看起来多像一个学习系统，而应是它是否真正为学习系统铺好了路。若 v4 只是堆砌了一些 MDP 术语，却没有落实到记录结构、角色边界和治理闭环，那么它就只是表面升级。反之，如果 v4 让系统在不引入学习的情况下就已经具备统一语言和统一证据，那么它就成功完成了自己的历史任务。

## 19. 方法论意义：从流程自动化到任务治理操作系统

### 19.1 为什么本文讨论的不是普通工作流

普通工作流强调的是步骤串接，默认对象往往是可重复、可预判、边界清晰的流程。任务事务工作流面对的则是开放任务，是会发生阻断、回溯、拆分、等待、人工确认和目标修正的任务世界。因此，它更接近一种任务治理操作系统，而不是传统意义上的流程图工具。

当我们用这种视角看待系统时，就会明白 v4 的升级也不是简单的“规则更多一点”或“智能更强一点”，而是操作系统层面的语言升级。它重新规定了系统如何理解世界、如何表达角色、如何组织证据、如何定义决策、如何承接未来学习。

### 19.2 从功能堆叠到原理统一

一个系统如果只按需求堆功能，很容易形成看似丰富、实则松散的结构。每个模块都能工作，但彼此之间没有统一的原理约束。v3 已经在协议层迈出关键一步；v4 进一步把这种统一推进到控制面语言层。它让不同模块不再只是“能调用”，而是“能在同一个任务控制原理下被理解”。

这正是原理论著存在的意义。它不是把已有功能再描述一遍，而是说明这些功能为何可以被组织成一套有内在一致性的体系。

### 19.3 任务治理操作系统的核心特征

如果把任务事务工作流看作任务治理操作系统，那么它至少具有以下特征：有稳定的状态制度，有统一的结果信号，有标准化的决策输入输出，有可回放的历史证据，有可扩展的角色分工，有可嵌入现实组织的责任治理，有逐步走向学习型策略的演化能力。v4 的工作，正是把这些特征从工程习惯提升为明示制度。

## 20. 工程实施建议

### 20.1 先做术语对齐清单

在具体实施层面，团队应首先完成一份术语对齐清单。将现有代码与文档中的控制器、规则、推荐动作、回执、人工介入、节点控制、事务执行等概念，逐一映射到 v4 的状态、观测、动作、决策、角色、部门与证据术语上。这样可以快速识别哪些对象已经具备 v4 语义，哪些对象仍停留在 v3 表达。

### 20.2 再做记录字段补齐

完成术语对齐后，应优先补齐结构化记录字段。尤其是观测摘要、候选动作集合、最终决策成员信息、理由文本、差异说明、人工补充意见等字段。这些工作看似不如“新增智能”显眼，却决定了后续一切升级是否有数据基础。

### 20.3 最后再做角色边界调整

只有在语言和记录都相对稳定后，才适合进一步推进角色边界调整，例如让 TA 在低风险场景下拥有更强局部裁决权，让 NA 提供更丰富的节点级建议，让 AA 的回执结构更接近可比较样本。这个顺序不能颠倒，否则系统会先扩权、后补账，最终很难解释历史行为。

## 21. 风险与限制

### 21.1 术语升级可能被误解为能力升级

v4 的一个现实风险是，团队可能把术语升级误解为已经具备学习型或多智能体能力。实际上，v4 的核心是框架预备而不是能力兑现。如果没有清晰的沟通，组织可能会对系统能力产生过高预期。因此，在推进 v4 时，必须始终强调：这是控制面与记录面的升级，不是立即放弃决策部门、进入全面自治。

### 21.2 结构化记录会增加短期工程成本

补齐观测、证据和决策记录，必然会带来短期工程成本上升。字段更多、接口更长、测试更细、文档更重。这种成本在短期内看似增加负担，但如果省略这一步，未来版本会以更高代价偿还。v4 的方法论，就是用当前较低成本的制度建设，换取未来更低成本的系统跃迁。

### 21.3 决策部门若设计不当会造成流程拖滞

若把所有决策都无差别推入部门确认，系统就会失去自动化效率。v4 因此并不主张凡事上会，而是主张建立清晰的进入条件：哪些场景可直接按默认路径执行，哪些场景需部门裁决，哪些场景需人工签收。只有边界清楚，决策部门才会成为治理增益，而不是瓶颈。

### 21.4 历史数据质量决定后续上限

v4 虽然为未来学习铺路，但是否真的能承接到 v5，很大程度上取决于 v4 期间沉淀的数据质量。如果记录字段存在缺失、理由文本敷衍、证据链断裂、人工意见不可回放，那么未来即使引入学习，也只能建立在脆弱样本上。因此，v4 的纪律性与记录质量，本身就是长期竞争力的一部分。

## 22. 总结性讨论

v4 的价值，归根到底，在于它完成了一次“先把语言建对”的工作。过去系统已经拥有相当多可运行的工程对象，但这些对象尚未被放进统一的 MDP 术语与多角色 Agent 术语框架中。没有这一层统一，系统很难稳健地跨向未来版本。v4 通过决策部门这一中间制度，把当前现实治理和未来多智能体演化连接起来：一方面继续保留 PA 与人类专家作为最终裁决主体，确保当下系统可解释、可审计、可承担责任；另一方面又把 PA、TA、NA、AA 全部纳入 Agent 角色框架，保证未来自治升级不需要再做一次痛苦的概念断裂。

从工程史角度看，很多系统并不是败在“没有更高级的算法”，而是败在版本演化中缺乏中间态设计。它们要么永远停留在脚本式规则堆叠，无法形成可持续治理；要么过早引入复杂智能机制，结果在记录、责任和制度上全面失稳。v4 所代表的，正是一种更克制也更成熟的系统演化观：先把协议冻结，后把术语统一，再把角色建模，继而沉淀证据，最后才进入学习。

因此，v4 并不是一个“过渡版所以不重要”的版本，恰恰相反，它是整个任务事务工作流体系中最关键的桥梁版本之一。它决定了系统能否从 v3 的规则治理平稳走向 v5 及以后版本的多智能体学习治理。只要这一桥梁搭得稳，后续版本就可以在不牺牲解释性和治理性的前提下逐步增强自治能力；若这一桥梁缺失，任何更高级的智能尝试都可能沦为高风险实验。基于这一判断，本文主张将 v4 视为通用任务事务工作流迈向长期演化能力的正式奠基版本。

## 23. 决策语言统一对系统演化的基础价值

### 23.1 语言不统一时，系统会出现什么问题

一个系统的演化往往不是先败在功能，而是先败在语言。若不同模块用不同术语描述同一件事，那么局部都可能正确，整体却会逐渐失真。有人把某次判断叫作规则命中，有人把它叫作动作推荐，有人把它叫作策略输出，有人把它叫作人工审批前置；在文档、代码、日志和复盘里，这些说法可能都能成立，但一旦版本演化需要跨模块协作，语言差异就会变成真实成本。

在 v3 阶段，这种成本尚可接受，因为系统的核心目标是把最基本的控制闭环搭起来。只要结果码协议与状态机是稳定的，很多术语上的局部差异不会立即阻断系统运行。然而，当系统进入 v4 阶段，目标已经从“能跑”转向“可持续演化”，语言不统一的问题就不能再被容忍。因为未来无论是引入更多 Agent，还是引入策略学习，甚至只是让更多团队成员参与维护，统一的决策语言都会成为最底层的协作前提。

### 23.2 统一语言不是抽象美学，而是工程资产

很多团队低估统一语言的价值，认为这只是文档修辞或命名风格问题。实际上，统一语言直接决定了代码接口能否稳定、日志能否复用、历史记录能否比较、人员协作能否高效、版本迁移能否低风险。若系统今天用“推荐动作”，明天用“候选决策”，后天又改成“策略输出项”，那么即使字段结构没变，认知摩擦也会不断累积。

v4 对这一问题的处理方式很明确：把状态、观测、动作、转移、角色、决策部门、证据、责任、历史回放全部拉入同一套语言体系中。这种统一本身就是一种长期资产。它不直接提升某次任务成功率，却显著提升系统在未来数个版本中的可维护性和可迁移性。

### 23.3 决策语言统一如何反哺实现层

语言统一并不是停留在论文层面。它会反过来影响实现层的对象划分与接口选择。当团队开始真正按状态、观测、动作去思考系统时，原先混杂在一起的逻辑会被重新拆开：哪些是状态组织，哪些是观测整理，哪些是候选动作生成，哪些是最终裁决，哪些是执行回执解释，哪些是责任门控。对象边界一旦变清楚，代码层的改造就更容易以最小风险推进。

从这个角度看，v4 所做的不是给现有系统套上一层理论外壳，而是在为未来实现层清理地基。正因为如此，本文才强调 v4 首先是语言层升级，而不是算法层升级。

## 24. 双图结构与任务连续性的再解释

### 24.1 为什么图仍然重要

任务事务工作流并不是反图设计。相反，图结构仍然承担着表达路径、节点语义、局部约束和阶段关系的重要职责。问题从来不在于有没有图，而在于是否把图误当成了全部控制逻辑。v3 已经完成一个关键转向：图不再独占控制权，真正的推进单位变成任务步与结构化决策。v4 延续这一点，但进一步用 MDP 术语重新解释图与任务之间的关系。

在 v4 中，图是世界结构的一部分，是状态与观测的重要来源，却不是唯一的决策引擎。节点位置、边关系、节点配置、节点证据口径仍然重要，但它们要被纳入状态与观测体系，而不是凌驾于任务治理主闭环之上。这样，系统才能既保留图带来的表达力，又避免被图的静态结构绑死。

### 24.2 主图、节点与任务步的关系

一个常见误区是把节点执行等价于任务推进。实际上，任务推进是更高层对象。节点只是任务在某一阶段所处的位置，以及该位置上的局部约束集合。任务步才是主闭环中的真实推进单元，因为它包含了当前状态、观测、候选动作、决策结果、执行回执和后继状态变化。

v4 通过这一视角，把主图的作用重新安放到合适位置：图定义可供任务步参考的结构边界，而任务步负责将这些结构边界与现实事件、执行回执和治理规则整合起来。这样，图不再承担超出其能力范围的职责，任务也不再失去结构支撑。

### 24.3 双图思想与 MDP 术语的兼容

如果未来系统继续发展出更多图层，例如项目图、任务图、节点图、事务图甚至关系图，那么 v4 的 MDP 术语也不会失效。因为这些图层都可以被视为世界状态的结构部分，或观测生成过程的结构来源。换句话说，MDP 术语不是要取代图，而是要给图找到统一的上位语言。

这也是 v4 相比传统图工作流设计的一个优势。传统图工作流一旦面对多层图结构，往往只能不断叠加新的图语义，最终让系统概念空间愈发凌乱。v4 则允许所有图结构被纳入状态与观测框架中，从而把复杂性约束在统一原理之下。

## 25. 人机协同的制度化重述

### 25.1 人机协同不是临时补丁

在很多自动化体系中，人工介入常常以“异常兜底”的形式存在。系统设计者默认机器应自动运行，只有在失败时才叫人接手。这种设计在封闭流程中或许可行，但在开放任务世界中并不充分。因为人类并不只是为失败收尾，更承担目标澄清、价值判断、责任确认、风险承担和跨组织协调等职责。这些职责不是噪声，而是系统的一部分。

v4 因此不把人类专家视为系统外的临时插件，而把其正式纳入决策部门，作为高权限治理主体。这样，人机协同就从“运行后修补”上升为“制度化协同”。系统从一开始就知道，在某些类型的任务步上，人类不是例外，而是标准参与者。

### 25.2 PA 与人类专家的协作边界

PA 与人类专家同处决策部门，但两者并不相同。PA 更擅长快速处理结构化观测、维持全局一致性、提供连续性建议；人类专家则更擅长处理价值冲突、模糊边界、责任判断和跨情境迁移。v4 的关键不是让二者彼此替代，而是让二者以结构化形式协同：PA 可以先给出建议，人类可以确认、修正或拒绝，最终结果都被明确记录下来。

这种协同关系对未来也有重要意义。随着系统能力增强，PA 可能承担越来越多低风险场景的默认裁决，但只要高风险场景仍保留人类专家入口，系统就不会因为能力增强而失去治理边界。

### 25.3 人类反馈的结构化表达

人类参与决策时，最大的浪费往往不是时间，而是信息没有被结构化保存。若人工只在聊天窗口、口头沟通或零散备注中表达意见，那么这些高价值判断就无法进入系统演化回路。v4 强调，人类反馈必须尽可能被结构化表达：为什么不同意默认动作、是否需要补充前置条件、哪些风险被认为不可接受、什么证据才能改变当前判断、是否允许系统在类似场景下自动处理等。

一旦这些信息被稳定记录，人类协同就不再只是成本，也会成为系统未来优化的核心知识来源。对 v5 来说，这些结构化人工反馈甚至可能比大规模低质量日志更有价值。

## 26. 评估框架：v4 应该如何被判断

### 26.1 不能只看任务成功率

如果用单一任务成功率来评价 v4，结论往往会失真。因为 v4 的核心工作不是提高短期自动化成功率，而是提高系统的结构稳定性、治理清晰度和演化准备度。某些情况下，v4 甚至可能因为引入更严格的记录和门控，使得短期吞吐量下降。但这并不意味着框架失败，反而可能说明系统更诚实地面对复杂现实。

因此，评价 v4 至少要看以下几个维度：状态与观测记录是否更完整，决策成员与理由是否更清楚，候选动作与最终动作是否被清晰区分，人工介入是否更可回放，高风险动作是否更受控，跨版本术语是否更稳定，后续学习接口是否更明确。只有把这些维度放进来，才能真正判断 v4 是否完成了自己的历史任务。

### 26.2 结构质量比局部性能更重要

v4 阶段最重要的，不是某个单模块性能指标，而是整套结构是否更坚实。结构质量高，意味着系统在复杂任务中即使失败，也能清楚知道失败在哪、由谁判断、有什么证据、是否该人工介入、下次如何改进。结构质量低，则意味着系统即便暂时成功，也只是碰巧成功，无法形成可积累能力。

换句话说，v4 更重视“失败是否可解释”而不只是“成功是否发生”。因为对长期演化系统来说，可解释失败比不可解释成功更有价值。

### 26.3 为未来版本提供可比较基线

v4 还承担一个经常被忽略的任务：为 v5 及以后版本提供基线。未来若引入学习型策略，我们需要回答一个问题：它到底比 v4 的决策部门机制好在哪里，坏在哪里，在哪些场景下值得放权，在哪些场景下不值得。若 v4 没有留下清晰基线，未来版本就没有比较对象，所有“提升”都只能停留在印象层面。

因此，v4 的评估框架本身也会成为未来版本评估的起点。它不是终局标准，却是后续所有比较的基线标准。

## 27. 数据制度与样本积累逻辑

### 27.1 样本不是天然存在的

很多团队在谈未来学习时，会自然地说“先跑起来，以后就有数据了”。这句话只对了一半。系统确实会产生数据，但不意味着会自然产生可用样本。若没有制度化的字段设计、稳定的角色边界和统一的术语语义，大量运行日志最终只会变成难以使用的历史堆积，而不是可比较、可训练、可评估的样本集合。

v4 的重要贡献，就是把“样本是被制度设计出来的”这件事前置。通过统一状态、观测、动作、决策、证据和责任记录口径，系统开始有能力主动生产高质量历史样本，而不是被动积累噪声。

### 27.2 高价值样本往往来自分歧场景

并不是所有任务日志都具有同等价值。那些一路顺滑、毫无争议的案例当然有参考意义，但真正高价值的样本往往来自分歧场景：规则推荐与人工意见不一致、PA 与人类专家看法不同、候选动作之间存在强冲突、任务表面成功但实际目标未满足、依赖未就绪却存在绕行诱惑、高风险动作技术可做但组织上不可做。这些场景的信息密度极高，对未来策略边界和责任治理都极其重要。

v4 通过决策部门记录、候选动作空间保留和人工反馈结构化，使这些高价值分歧场景不再散落在聊天记录和临时备注里，而能被系统性沉淀下来。

### 27.3 负样本、边界样本与异常样本

未来版本若要真正理解任务世界，就不能只收集成功样本。负样本、边界样本和异常样本同样重要。所谓负样本，不只是最终失败，而是那些“不该这样做”的行为记录；所谓边界样本，是指多个动作都看似合理、但只有在特定治理前提下才允许其中一个的案例；所谓异常样本，则是系统观测严重缺失、信息模糊或组织规则冲突的情况。v4 要求这些样本都能以可区分、可检索、可解释的方式保存下来。

一旦这类样本积累起来，后续系统不仅能学会“如何成功”，还能学会“何时不该自动、何时必须求助、何时应该暂停”。这比单纯追求自动成功率要成熟得多。

## 28. 组织治理视角下的系统边界

### 28.1 技术系统必须尊重组织边界

任务事务工作流并不是在真空中运行。它总要嵌入某个组织、某种协作关系、某种责任制度中。若系统只从技术角度追求高自动化，而忽视组织边界，就会在关键处失去可落地性。比如某些任务虽然技术上可以自动完成，但在组织制度上必须经过审批；某些目标虽然逻辑上可优化，但在业务现实中不可擅自改变。

v4 通过决策部门和人工门控机制，把组织边界正式写入系统。这样，系统就不会在面对现实约束时表现得像“技术上已经成功，组织上却无法接受”的不成熟自动化工具。

### 28.2 系统边界决定了什么能自动、什么必须治理

任何成熟系统都应承认自身边界。并不是所有可表达的问题都应自动求解。某些动作天然需要治理确认，某些结论天然需要责任主体背书，某些资源调用天然受制于外部制度。v4 相比更激进的智能路线，最大的优势之一，就是不把“系统能力边界”视为缺陷，而把其视为应被明确设计的制度事实。

这使得系统在现实落地中更可信。因为组织真正需要的，不是一个总声称自己能处理一切的黑箱，而是一个知道自己何时该停、何时该问、何时该升级、何时该交还给人类的治理系统。

## 29. 实施路线图建议

### 29.1 第一阶段：完成文档与术语冻结

第一阶段的核心任务是统一语言，包括原理论著、设计文档、附录、开发者指南以及关键对象说明。目标不是让所有实现立刻变化，而是让团队先以同一套术语看待系统。若这一步没有完成，后续接口落地很容易出现各自理解、各自命名、各自扩展的情况。

### 29.2 第二阶段：完成核心记录补齐

第二阶段聚焦数据制度建设。要补齐的不是炫目的新功能，而是观测摘要、候选动作、最终裁决、参与成员、理由说明、差异标记、人工意见、证据引用、后继状态等关键字段。这一步完成后，系统才算真正具备 v4 的最小闭环。

### 29.3 第三阶段：完成角色接口显化

第三阶段才轮到角色接口显化。PA、TA、NA、AA 各自的状态接口、观测接口、建议接口、回执接口和可升级空间，需要通过代码对象与文档约定被进一步明确。这里的重点不是马上分权，而是把未来可能分权的位置标出来。

### 29.4 第四阶段：完成部门化裁决落地

第四阶段将决策部门从理论对象落到实际流程，包括默认进入条件、人工签收条件、结构化意见记录、差异处理策略、升级路径和审计方式。做到这一步，v4 才真正从文档设计转入制度运行。

### 29.5 第五阶段：围绕数据开展离线分析

当系统稳定沉淀一段时间后，就可以围绕 v4 数据开展离线分析，例如高频阻断原因统计、规则推荐与最终裁决偏差分析、人工介入场景聚类、节点级高风险动作分布、观测缺失模式识别等。这些分析本身并不是 v5，但会直接为 v5 提供策略先验与放权依据。

## 30. 学术讨论：v4 的桥梁定位与版本间可迁移性

站在长期演化视角下看，v4 最容易被误读的地方，是它既没有停留在 v3 的纯规则叙事上，也没有直接冲向 v5 的学习叙事。有人会因此把它误解为折中版本、保守版本或过渡版本。但真正的系统工程经验恰恰说明，最关键的版本往往正是这种桥梁版本。因为系统能否跨越代际，不取决于愿景是否足够激进，而取决于是否有能力在现实治理与未来演化之间搭出一条不断裂的通道。

v4 的全部意义，就在于搭这条通道。它保留 v3 已经验证过的结构资产：结果码协议、任务状态机、候选动作机制、结构化回执、执行主干和数据库基础；同时又把这些资产重新组织进 MDP 术语和多角色 Agent 术语中，使它们不再只是当前可运行的工程构件，而成为未来版本可继承、可比较、可学习的制度基础。它引入决策部门，不是为了减缓系统，而是为了明确最终裁决的责任收口；它保留人类专家，不是因为系统无能，而是因为系统正在成熟地承认现实治理；它不立即引入强化学习，不是因为缺乏雄心，而是因为真正有雄心的系统知道何时应先把语言、边界和证据做好。

因此，v4 不是妥协，而是奠基。它不试图用一个版本解决所有问题，而是把最不该拖延的问题先解决：统一概念语言，统一角色表达，统一决策记录，统一证据制度，统一治理收口。只要这些基础被稳固下来，后续无论是更强的局部自治、更多 Agent 参与、离线策略分析，还是最终走向多智能体强化学习，都会拥有可承接的工程落点和组织落点。这正是本文对 v4 的最终判断：它不是终点版本，却是决定整个任务事务工作流能否走得更远的关键版本。

## 31. 反例讨论：没有 v4 会发生什么

### 31.1 路径一：继续停留在 v3 规则语言

若系统在 v3 之后继续停留在原有规则语言中，不做任何术语升级，那么短期内看似最省事。团队仍然可以不断往候选动作逻辑里添加条件，不断优化 PA 的推荐行为，不断修补某些边缘场景的门控规则。系统也许仍能继续跑、继续扩功能、继续处理更多任务类型。然而，这一路径的隐性代价会越来越高。

首先，系统历史记录会越来越难以作为未来策略接口使用。因为记录对象的命名、边界和语义并没有按状态、观测、动作、角色来冻结。其次，角色体系会长期停留在“一个真 Agent 加若干程序控制器”的不平衡结构中。一旦未来想讨论多角色自治，只能进行一场突兀的术语翻案。再次，组织治理层也会因为缺少明确的决策部门概念，而继续在“系统自动做了”与“到底谁批准了”之间反复摇摆。

换言之，继续停留在 v3 语言，虽然不是立即崩溃，但会让系统把版本债务不断积压到未来。等到真正需要跨代升级时，这些债务会集中爆发。

### 31.2 路径二：绕过 v4 直接追求 v5 学习化

另一条看似更先进的路径，是直接跳过 v4，开始构建多智能体学习系统。表面看，这条路似乎更符合长期愿景，因为它直接面向最终目标。然而，这种跳跃的风险更大。没有 v4，系统就没有稳定的状态语义、观测口径、候选动作记录、角色统一表达和责任收口结构。此时引入学习，只会把原本分散的问题隐藏进新的模型接口中，而不会真正消除问题。

更严重的是，直接学习化往往会带来双重不透明：一重来自原有工程语言不统一，另一重来自新增策略模型的黑箱性。到那时，团队既难以解释历史数据如何形成，也难以解释模型为什么这样决策，组织治理将变得更加困难。

因此，v4 的存在，本质上是为了避免系统陷入“两头不到岸”的状态：既不能长期停留在纯规则叙事中，又不能无准备地跃入学习叙事中。它提供的是一条真正可走的中间道路。

### 31.3 路径三：只改名，不改记录制度

还有一种更隐蔽的失败路径，即团队口头上接受 v4，文档里也开始使用状态、观测、动作等词汇，但系统记录制度并没有随之改变。结果就是：名词升级了，历史数据没升级；概念看起来统一了，证据链仍然断裂；角色说成 Agent 了，但实际没有清晰接口。这样的 v4 只是表面迁移，而不是实质迁移。

本文特别强调这一点，是因为很多框架升级都会停留在术语包装层。真正的 v4 必须让语言变化落实到记录字段、裁决结构、成员边界和回放能力上。否则，未来版本仍然无法继承到足够稳定的基础。

## 32. 长期研究议题与理论外延

### 32.1 从单任务控制到多任务耦合治理

本文主要讨论的是单任务主闭环如何在开放环境中被重新表达，但从长期看，任务事务工作流的真正复杂性往往来自多任务耦合。任务之间可能存在资源竞争、前后依赖、目标冲突、共享证据、重复执行风险以及优先级重新分配问题。v4 虽然还不直接解决这些全部问题，但它通过统一角色与决策语言，为多任务耦合治理预留了更坚实的基础。

未来研究可以在 v4 的语言框架上进一步讨论：多个 TA 如何在共享资源下被协调，多个任务的局部观测如何形成上层决策部门可理解的全局观测，不同任务间的阻断是否构成新的治理事件，项目级 PA 如何在多任务之间进行动态优先级裁决。这些研究都需要统一语言打底，而 v4 正是这一前提。

### 32.2 从任务治理到知识治理

任务推进并不只是动作序列，它同时也是知识不断更新的过程。某次事务回执可能改变对环境的理解，某次人工意见可能修正任务目标边界，某次失败案例可能重塑风险判断。换句话说，系统在治理任务时，也在治理知识。v4 目前主要从控制角度重述这件事，但它已经为后续知识治理奠定了形式条件，因为状态、观测和证据本身就是知识对象的结构化入口。

未来若要发展更强的知识图谱、经验库或策略记忆体系，v4 的决策记录和证据链将直接成为高价值原料。没有这一步，知识治理只能依赖事后人工整理，难以形成规模化积累。

### 32.3 从部门治理到策略宪章

决策部门在 v4 中主要作为现实治理收口机制存在，但从更长期视角看，它还可能演化为更稳定的策略宪章载体。所谓策略宪章，是指一组不轻易被局部优化覆盖的高层原则，例如哪些风险绝不自动承担，哪些任务类型必须人工签收，哪些证据缺失情况下系统必须暂停，哪些场景允许低层 Agent 局部自治等。今天这些原则主要通过制度与文档表达，未来则可能成为系统评估与放权的正式约束。

v4 通过部门化裁决，让这些高层原则首次拥有了清晰的承载位置。后续版本完全可以在此基础上继续发展，而无需重新寻找治理锚点。

### 32.4 从结构化记录到可验证学习

多智能体学习若要真正进入任务治理场景，单有训练能力还不够，还需要可验证性。也就是说，系统不能只说“模型学会了”，而必须说明在什么样的状态、观测和动作条件下，它的行为被认为是可接受的，何时需要回退到决策部门，何时必须恢复人工审查。v4 的结构化记录之所以重要，正是因为它能为这种可验证学习提供样本基础和制度接口。

因此，本文虽然不展开 v5 具体算法，但已经给出一个清晰判断：未来学习系统若不能继承 v4 的记录制度与责任制度，即使算法再先进，也难以被视为成熟的任务治理能力。

## 33. 最终结论

综合全文可以看到，v4 的提出并不是为了在概念上追赶某种流行术语，也不是为了给现有系统加上一层理论包装。它回应的是一个真正的系统工程问题：当一个已经拥有稳定协议与初步治理能力的任务事务工作流，准备走向更复杂的多角色协同乃至未来学习化时，究竟应当先做什么。本文给出的答案是，不应先追求更激进的自治，不应先迷恋更复杂的算法，而应先完成控制面语言、角色表达、决策制度与证据制度的统一。

正因为有了这一判断，v4 才被定位为桥梁版本。它既忠实继承 v3 的结构资产，又清晰指向 v5 的长期方向；既不回避开放任务环境中的不确定性，也不以此为理由放弃治理；既承认 PA、TA、NA、AA 都应进入 Agent 角色框架，又不急于让所有角色立即夺取最终裁决权；既把人类专家保留在正式决策结构中，又通过结构化记录让人工判断转化为系统长期资产。这样的 v4，不是停留在中间，而是在为后续所有升级铺设可走的道路。

因此，本文最终主张：应当把 v4 视为通用任务事务工作流从“规则可运行”走向“治理可持续、演化可承接”的正式起点。只有在这一层完成后，后续版本的多角色自治、离线策略分析、放权评估乃至多智能体强化学习，才不会成为脱离治理现实的空中楼阁。对一个面向长期演化的任务治理系统而言，先把这座桥建稳，远比急于冲向桥的另一端更重要。

## 34. 实践收口：如何判断 v4 已经真正成立

### 34.1 不是看名词是否写进文档，而是看系统是否按新语言运行

一个版本是否真正成立，最终不能只靠文档标题判断。v4 是否成立，取决于系统是否已经开始按新的语言组织自身。也就是说，当团队讨论一次任务步决策时，是否自然会区分状态、观测、候选动作、最终动作、执行回执与责任成员；当团队回放一次任务历史时，是否能够明确指出当时谁看到了什么、基于什么做了什么判断；当团队计划未来升级时，是否已经可以围绕 PA、TA、NA、AA 的角色边界展开，而不必重新发明一套解释语言。若这些问题的答案仍然是否定的，那么即使文档已经写成 v4，系统也仍未真正进入 v4。

因此，v4 的成立应被理解为一种运行方式的变化，而不只是文件命名的变化。只有当代码对象、记录字段、决策流程和团队讨论方式都开始服从同一套框架时，v4 才算真正落地。

### 34.2 最小成立条件

从务实角度看，v4 至少应满足以下最小成立条件。第一，任务状态机与结果码协议继续作为系统硬边界存在，并在所有相关文档中被明确保留。第二，PA、TA、NA、AA 已在文档与接口层被正式定义为 Agent 角色，而不是继续混杂在控制器与执行器叙事中。第三，关键任务步的决策能够通过决策部门进行正式收口，并能结构化记录参与成员与理由。第四，系统历史记录已能稳定保存观测摘要、候选动作和最终动作之间的关系。第五，团队已经能够用这些结构化记录对典型任务进行复盘，而不是依赖零散日志和口头记忆。

这五点看似朴素，但正好构成一个桥梁版本应有的骨架。只要骨架稳住，后续细节就可以逐步丰富；若骨架不存在，再多局部改进也难以承接长期演化。

### 34.3 进一步成熟的标志

在最小成立条件之外，v4 的进一步成熟还可以通过一些更高阶的标志来观察。例如，系统是否已经能识别哪些场景可直接走默认路径、哪些场景必须进入决策部门；是否已经开始积累规则推荐与最终裁决之间的偏差样本；是否能够围绕人类意见形成结构化经验库；是否已经可以从历史记录中抽取出高频阻断模式、高风险动作模式和观测缺失模式；是否已经初步具备把某些低风险场景逐步委托给 TA、NA 或更低层自治逻辑的判断依据。

这些标志说明，v4 不只是把语言建起来，而且开始把语言转化为治理能力。到这一步，v4 才真正体现出桥梁版本的厚度：它不仅为未来版本留接口，也开始反过来改造当前版本的日常运作质量。

### 34.4 何时可以向 v5 迈进

本文虽然不展开 v5 的具体实现，但从 v4 的完成度看，只有在以下问题获得较稳定回答后，系统才适合向更高程度的学习化演化迈进。第一，状态、观测和动作语义是否已经足够稳定，跨团队理解差异是否已经显著下降。第二，决策部门的裁决记录是否足够完整，足以作为后续离线分析与策略比较的可靠样本。第三，人工介入是否已经被结构化沉淀，而不是仍然主要存在于文本对话和个人经验中。第四，高风险动作的责任收口是否已经形成稳定制度，不会因引入更高自治而失守。第五，系统是否已经能够区分哪些任务类型适合继续保守治理，哪些任务类型具备放权试验价值。

如果这些问题尚未被回答，那么贸然进入 v5，极可能只是把不成熟的问题交给更复杂的机制处理。相反，若这些问题已有较稳定答案，那么 v5 的推进就不再是一次冒险，而是一次建立在稳固基础上的自然延伸。

### 34.5 对本体系的最终判断

基于全文分析，可以给出一个收口判断：v4 的真正贡献，不在于它让系统立刻显得更“智能”，而在于它让系统第一次具备了成为长期演化体系的资格。此前的系统更像一个已经很好用、但语言仍偏工程局部化的治理原型；而经过 v4 的统一之后，它才开始拥有足够清晰的状态语言、角色语言、决策语言和责任语言，能够承载更大规模的协作、更长周期的积累和更高层次的升级。

从这个意义上说，v4 不是简单的版本号前进，而是系统身份的变化。它标志着任务事务工作流从“一个能工作的框架”进一步变成“一个知道自己如何演化、为何演化、由谁决策、如何记账、怎样承接未来”的框架。这样的变化虽然不像新增功能那样直观，却决定了整个体系最终能走多远。正因为如此，v4 在本体系中的位置，应被视为战略级的结构转折点，而不是普通的中间版本。

## 35. 方法论附注：论证体量与概念完备性

本文之所以保留较长篇幅，并非单纯为了追求形式上的“长文”，而是因为 v4 所承担的并不是一个局部功能说明任务，而是一场跨版本的原理重述任务。若篇幅过短，很多关键区分就会被压扁，例如规则语言与 MDP 语言的差异、角色是 Agent 与角色拥有最终裁决权之间的差异、决策部门与单一 Agent 裁决之间的差异、结构化记录与普通日志之间的差异、桥梁版本与终局版本之间的差异。这些差异如果不被充分展开，后续实现时极易被重新混淆。

因此，较长的论述在这里具有方法论价值。它不是为了制造复杂感，而是为了给团队留下足够厚的公共语义背景，使不同成员在未来数个阶段内仍然能够回到同一份原理文本上对齐理解。对一个准备长期演化的系统来说，这种充分展开的共同文本，本身就是基础设施的一部分。

进一步说，v4 文本的完整性还承担了一个现实作用：它为后续设计文档、实现接口、评审标准、测试口径和复盘方法提供共同源头。只要这一共同源头足够清晰，后续各层实现即使分阶段推进，也不至于在原则上再次分叉。这也是本文坚持以较完整体量展开论证的最后理由。

若把整个体系放在更长的时间尺度上看，v4 的文字厚度本身也构成了一种版本护栏：它迫使后续任何新增能力都必须回应这套原理边界，而不能随意越过已经明确的治理约束与责任结构。

这正是 v4 作为桥梁版本的最终制度意义。

亦是其长期价值所在。

## 37. 形式化重述与命题

### 37.1 基本对象定义

记任务控制系统为五元组：

$$
\mathcal{M}_{v4}=\langle \mathcal{S},\mathcal{O},\mathcal{A},\mathcal{T},\mathcal{D}\rangle
$$

其中：

1. $\mathcal{S}$ 为状态空间（任务、节点、事务、关系、阻断、证据等联合状态）。
2. $\mathcal{O}$ 为观测空间（由 TA/NA/AA 组织后的观测包）。
3. $\mathcal{A}$ 为动作空间（`continue/retry/backtrack/suspend/split/human_gate/complete/fail/cancel`）。
4. $\mathcal{T}$ 为受状态机约束的转移关系。
5. $\mathcal{D}$ 为决策部门映射，负责从候选动作集中输出最终动作。

### 37.2 约束命题

**命题 1（裁决唯一性）**：在 v4 中，任一任务步至多存在一个最终动作写回记录。

**命题 2（动作合法性）**：最终动作必须属于当前候选动作集合，且满足状态机可达约束。

**命题 3（可追溯性）**：任一状态变化均可追溯至对应 `decision_uid` 与证据引用集合。

**命题 4（角色分权约束）**：TA/NA/AA 在 v4 只输出建议与执行信息，不输出最终裁决。

上述命题共同给出 v4 的最小可验证框架：它不依赖学习策略，但具备制度可验证性。

## 40. A/M 双轨角色体系

### 40.1 为什么 v4 需要同时引入 A 与 M

前文把 PA、TA、NA、AA 统一纳入 Agent 术语体系，解决的是“谁以智能体身份理解状态、观测与动作空间”的问题。但在真实运行中，仅有 Agent 还不够。原因很直接：开放任务中的语义判断、候选裁决和审计解释确实适合由 LLM 驱动的 Agent 参与，但任务账本、请求租约、状态推进、重复执行抑制、结构化落库这些能力，更适合由专用程序化管理器承担。若没有这条第二轨，系统就会在“语义上更聪明”和“记账上更稳健”之间来回摇摆。

因此，v4 需要在 Agent 角色之外，再显式引入 Manager 角色。A 表示由 LLM AI 驱动的语义角色，M 表示由专用程序实现的管理器角色。A 负责解释、建议、排序、审计与裁决倾向；M 负责幂等、状态机、租约、回执标准化、日志落库与任务记账。二者不是互斥关系，而是协同关系。默认情况下，AOE 应理解为“A 开启，M 常驻”：允许 Agent 参与控制循环，但不允许去掉 Manager 的制度性底座。

但这里还需要补一条层级边界：PA、PM 属于项目层外部角色，通常由人类通过 AI Agent 对话框或项目级入口显式发起；EA、EM、AA、AM、TA、TM 才属于嵌入 AOE 工作流系统内部、会随着控制循环时间步被程序性唤起的系统内角色。也就是说，A/M 双轨不是全部内嵌在 AOE 中，而是“项目层外部双轨 + AOE 内嵌双轨”并存。

### 40.2 角色对照表

| 角色对 | A 侧职责 | M 侧职责 |
| --- | --- | --- |
| PA / PM | PA 负责由人类在对话框中发起的项目级目标理解、跨任务建议、升级说明与高层语义裁决。 | PM 负责由人类触发的项目级程序化编排、配置生成、阶段推进、人工闸门与项目级状态约束。 |
| EA / EM | EA 负责引擎级候选动作排序、自动审计、调度解释与回退建议。 | EM 负责扫描时间步推进、逻辑时间步编排、决策落库、运行日志落库与幂等调度。 |
| AA / AM | AA 负责事务完成后的语义解释、质量判断、标准回执建议与补救建议。 | AM 负责事务回执归一化、执行重试、输入输出契约、产物登记与执行幂等。 |
| TA / TM | TA 负责任务级上下文理解、子任务建议、任务摘要与局部风险解释。 | TM 负责任务表、请求表、父子任务关系、任务状态推进与任务快照。 |

补充说明：

1. PA/PM 是项目层外部角色，默认不随 AOE 每一拍自动常驻运行。
2. EA/EM/AA/AM/TA/TM 是 AOE 内嵌角色，会在扫描时间步或逻辑时间步中被程序性调用。
3. 因此“项目经理”与“引擎经理”虽然都叫 manager，但并不位于同一系统层级。

### 40.3 审计、决策、日志、任务记录的职责分工

节点运行结束后，不同类型记录不应再混成“某一个角色全包”。更稳定的口径应如下。

1. 自动审计由 EA 和 AA 共同承担：EA 负责跨节点、跨候选的引擎级审计与裁决倾向，AA 负责事务完成后的领域语义审计与质量判断。
2. 审计记录的正式写入由 EM 和 AM 承担：EM 负责把引擎级审计结果写入运行事件或决策结构，AM 负责把事务级证据、回执和失败原因写成可消费契约。
3. 决策记录的最终责任主体是决策部门；在默认热路径中，EA 或 PA 可以给出建议动作，EM 负责把最终裁决结构化写入决策账本，必要时由项目层的 PM 触发升级、人工门控或项目级 override。
4. 日志记录以 M 为主：EM 负责控制面运行日志与扫描拍次日志，AM 负责事务执行日志与回执日志，TM 负责任务状态变化与任务关系日志。A 侧可以补充语义摘要，但不应替代 M 的正式账本职责。
5. 任务记录以 TM 为主、TA 为辅：TM 维护任务表、请求表、父子任务和状态推进；TA 负责补充任务摘要、任务语义解释和子任务建议。

### 40.4 角色协同原则

1. A 负责让系统“知道当前意味着什么”。
2. M 负责让系统“稳定地把结果记下来并可重复执行”。
3. A 可以给出建议、审计和裁决，但单独 A 不能替代 M 直接承担状态推进与落库主责。
4. M 可以在 A 不可用时维持最小可运行闭环，因此 M 是默认常驻底座，而不是可选插件。

## 41. 形式化补充：双轨角色约束

### 41.1 扩展角色集合

在 v4 语义下，可把角色集合扩展为：

$$
\mathcal{R}_{v4}^{dual}=\{PA,EA,AA,TA,PM,EM,AM,TM\}
$$

其中 A 侧负责语义性决策与建议，M 侧负责程序性推进与幂等治理；但 `PA/PM` 属于项目层外部角色，`EA/EM/AA/AM/TA/TM` 属于 AOE 内嵌角色。

### 41.2 扩展约束命题

**命题 5（双轨协同约束）**：任一进入正式账本的状态推进，必须至少经过一个 M 侧角色负责落库与幂等约束。

**命题 6（审计双归因约束）**：任一自动审计事件应同时能追溯到语义审计角色与程序管理角色，不允许只保留“模型说了什么”而丢失“谁负责把它写成正式记录”。

**命题 7（默认常驻约束）**：AOE 默认允许 A 参与，但不得以关闭 M 为代价换取灵活性；当 A 不可用时，M 必须能够维持保守但可运行的最小闭环。

这些补充命题的作用，是把“Agent 更聪明、Manager 更稳健”从经验描述提升为制度化约束。
