# 20260306-任务事务运作流程图：以学术项目为例-想法-001





学术研究任务可以分为两个维度：项目、事务（使用情景）两个维度。项目对应于一次完整或者半完整的学术运作流程。每个项目可以有不同的任务，这些任务串起来顺序运行。任务根据不同的使用情景（事务）分为不同类型的任务。这些任务有不同的类型。举一个例子。项目1是一个流程。每一个流程包括多个任务串行组成。这些任务类型不同，对应的事务不同（使用情景）。这些任务分别是：1. 自动化导入知网研学的文献到专题； 2. 手动提取专题的文献原文PDF文件和导出题录元数据； 3. 将导出的题录元数据和文献原文导入和预处理以生成文献元数据； 4. 根据关键词筛选查阅相关的文献元数据获取相关文献的信息； 诸如此类的各种事务。这些类型的事务对应的任务串起来运行形成了一次学术流程。项目1对应的这一次学术运作流程。




autodo-kit （简称 AOK）的流程图是允许用户或者 opencode 自行搭建流程图、如果已有的事务不够的化，也可以自行新建相关的事务，然后搭载到节点上。另外， AOK 也允许调用两类大模型：事务大模型、管理官大模型。

我们应该思考 AcademicResearch-auto-workflow （简称 ARW） 应该以什么框架为主：
- 以 opencode （简称 CC）为代表的 AI Agent 为主，每个 agent 调用技能的时候，技能脚本用 AOK 为辅。同时 CC 的项目总经理 Agent 和项目总设计 Agent 负责对所有 Agent 进行调度；
- 以 AOK 为代表的传统结合大模型的工作流为主，流程图/节点/事务调用 CC 的 AI Agent 的技能在流程图的大模型上为辅。同时 CC 的项目总经理 Agent 和项目总设计 Agent 负责全盘设计、实现、调度 AOK 工作流及其事务；

这两类框架其实有点类比两种工作模式：
- 前者是 Agent 自由流动式
- 后者是大工厂流水线式




我感觉其实学术研究有时候上述过程还会反复进行。也就是任意穿插。我们可不可以设计多层流程？其中第一层是【事务运作层】，第二层是【任务层】。任务层可以嵌套、可以连接，像一个有机的、动态的流程图一样。事务层也可以细分【分级事务】。【事务运作流】是由一个或者多个事务串成的一个流程。学术研究的实际运作过程可以用一个【事务属性表】、一个【任务属性表】、一个【任务-事务表】和一个【任务有向关系图】表示。

其实我们刚才讲的通用流程只是事务运作层。也就是：
- 事务运作流1：研究问题定义 -> 文献检索 -> 知识管理：整理文献；
- 事务运作流2：知识管理：查看文献 -> 思考 -> 检索数据 -> 数据管理：整理数据 -> 
举例：

初始状态：

任务1：代入研究问题1，然后走事务运作流1。然后中间知识管理的时候发现问题1可以细化为问题1-1，问题1-2，于是新建任务1-1，任务1-2：

挂起任务1，激活任务1-1：假设研究问题1-1，然后走事务运作1。然后中间知识管理的时候发现问题1-1不合适，排除。于是任务2状态失败，任务完成，注销任务1-1。激活任务1；

挂起任务1，激活任务1-2：假设研究问题1-2，然后走事务运作流1。然后中间知识管理的时候发现问题1-2可以继续。于是任务3状态成功，任务完成，注销任务1-2。激活任务1；

任务1生成任务2，走事务运作2。挂起任务1，激活任务2。任务2走事务运作流2。然后以此类推继续运作……

形象但是不一定精准的比喻：
- 事务层相当于路网上面的路段。
- 分级的事务相当于细分的路网上的路段。
- 事务运作流相当于几条连续的路段连成的一条长的路径，连接出发地和目的地。
- 任务相当于车辆。
- agent 就是驾驶员。
- agent 在某个事务运作中执行任务，相当于驾驶员开着车辆在路网上的路径上行驶。
- 激活任务相当于驾驶员进入驾驶室开始驾驶。
- 挂起任务相当于驾驶员离开驾驶室停止驾驶。
- 生成任务相当于从附近车库调出一辆车准备驾驶。
- 完成任务相当于车回到附近车库。
- 不同的 agent 根据不同的技能执行一个任务，走一个事务运作的时候，可能需要交接任务。相当于不同路段上同一辆车由不同的驾驶员来交接负责该路段的驾驶。
- 数据相当于车辆上运载的货物。
- 文献相当于车辆上运载的乘客。
- 各事务的审计 agent 相当于各路段的交通员，评判运载的货物或者乘客是否继续驾驶。
- 子任务相当于一辆车上的货物分到更多的车辆上同时或者分别运输。

【任务属性表】行表示任务项，列表示任务的属性：
- uid
- 名称
- 状态
- 前向任务
- 后向任务
- 父任务
- 子任务

【事务属性表】行表示事务项，列表示事务属性：
- uid
- 名称


【任务-事务关系表】行表示任务项，列表示该任务走的事务运作流。


【任务有向关系图】表示任务之间的关系，包括连接关系、上下级关系等。





一般来说38条建议的事务流还是繁多了。一级事务构成的流程（主路网）应该要简单一些。一级事务可以细化二级事务。例如文献检索事务是一级事务，可以细化成检索国内闭源文献事务这类二级事务。我建议事务流应该简化一下。只有简化了，才能大幅度减少事务流程图（事务节点的全集）的子集（事务运作流）的个数，否则排列组合事务节点，事务运作流数量爆炸式增长。

建议一级事务包括：
- 提出研究问题
- 确定研究目标
- 确定研究方法/数据
- 文献检索
- 数据检索
- 文献管理
- 文献阅读
- 数据管理
- 实证
- 实验
- 写作与修订
- 评审
- 事务管理
- 任务管理
- 总管理调度

然后，一级事务之间形成可回环（非 DAG ）的流程图。

流程图包括一些常见事务运作流：
- 提出研究问题 -> 文献检索 -> 文献管理；
- 文献管理 -> 文献阅读；
- 文献阅读 -> 思考 -> 确定研究目标；
- 文献阅读 -> 思考 -> 数据检索 -> 实证；
- 文献检索 -> 文献管理；
- 数据检索 -> 数据管理；

事务运作流也不一定是线性的，也可以是一个子流程图，甚至是贯穿整个学术科研事务流程图。

所以，你觉得具体执行一个任务的时候，走的事务运作流是不是也不是事先确定的，而是在每一个事务走的时候，下一个事务走什么都需要重新规划呢？就好像下棋，棋子走一个格子的时候，下一个格子走到哪里，甚至是否被吃掉，都是动态规划的。你觉得呢？


当然，如果要写入 AOK 的事务/流程图库，可以考虑是否还需要每一个细化的事务都写一个。


agents 分为三大类：
- 总体管理类：
	- 项目经理  PA （Project Agent）
	- 引擎经理 EA （Engine Agent）
	- 项目设计师 PD （Project Designer）
- 事务类：
	- 负责各事务 AA（Affair Agent）
- 任务类：
	- 负责具体任务 TA（Task Agent）




建议在设计一级事务关系图的流向的时候，设计一个基本的流向倾向功能。也就是用一个关系图来刻画一个事务流向下一个事务具体是哪一个事务的基本的倾向分值。如果基本的倾向分值大的，那么流向的概率大。这样就能设计动态的事务运作流，而不是穷举每一个固定的事务运作流。
