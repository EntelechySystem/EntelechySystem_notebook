# design-统一五维配置编译模型与四类范围理论设计-20260527-001

## 一、目标与范围

本文定义统一配置编译模型在既有四维基础上的第五个维度：范围。新的统一模型由以下五个维度组成：

1. AI 引擎供应商。
2. IDE 供应商。
3. 操作系统。
4. AI 内容类型。
5. 应用范围。

本文覆盖以下对象：

1. AOE 侧的 canonical 语义层与编译模型。
2. AOC 侧的 source profile、target profile 与 carrier mapping。
3. AOB 侧的聚合、发布、备份、同步四条运行链。
4. AOK 事务入口对范围维度的参数化接入。

本文不覆盖以下对象：

1. 跨设备账户注册中心的真实云端实现。
2. 任一单一供应商的全部底层 emitter 语法细则。
3. 与范围维度无关的其他 AOB 子命令重构。

## 二、问题定义

既有模型把 AI 内容的差异主要解释为引擎、IDE、操作系统和内容类型差异，但在实际运行中，真正决定“应发布到哪里、应从哪里聚合、应以什么语义参与同步”的还有一个长期被弱化的维度：范围。

若范围维度缺失，会持续出现以下问题：

1. 把系统级和用户级路径混为同一类目录。
2. 把项目级工作区错误地当作用户主目录下的私有壳子目录处理。
3. 把“canonical 真源”与“实际安装位置”混成同一层语义。
4. 在同步时无法区分“应在本机生效”与“应跨设备共享”的资产边界。

因此，统一配置编译模型必须从四维升级为五维，并要求范围维度进入 profile、resolver、统计、审计、文档与事务参数层。

## 三、五维模型定义

### 3.1 五维坐标

任一 AI 内容投影目标都必须由如下五元组唯一描述：

1. `engine_vendor`：语义最终面向的 AI 引擎供应商。
2. `ide_vendor`：承载该内容的 IDE 或宿主环境。
3. `os_family`：路径模板与系统载体约束所属的操作系统家族。
4. `content_type`：Agent、Skill、Instruction、Prompt、Rule、Command、Hook、Settings、MCP、Policy、Engine Native 等内容类型。
5. `scope`：内容最终生效的范围层级。

### 3.2 范围枚举

统一模型中的 `scope` 固定使用以下四个值：

1. `global`：全局级。语义上指向跨系统、跨设备、跨单机安装位置的共享真源，适合承载“同一注册用户在多端复用同一套配置”的上层同步锚点。
2. `system`：系统级。内容安装在机器级、管理员级或全局系统目录，对同一设备上的多个用户或会话生效。
3. `user`：用户级。内容安装在当前用户主目录或当前用户 IDE 数据目录，只对当前用户生效。
4. `project`：项目级。内容安装在某个项目、仓库或工作区目录中，与项目代码、文档和局部协作约束一起生效。

### 3.3 范围的核心判定标准

范围不是按目录名字面判断，而应按“作用对象”判断：

1. 若作用对象是跨设备共享配置，则为 `global`。
2. 若作用对象是整台机器或系统安装位，则为 `system`。
3. 若作用对象是某个本地用户，则为 `user`。
4. 若作用对象是某个项目或仓库，则为 `project`。

## 四、四类范围的语义边界

### 4.1 global

`global` 不是某一个固定本地目录，而是高于本机目录结构的共享语义层。其职责如下：

1. 承载跨设备统一收敛后的配置真源。
2. 作为多台设备、多套用户级和项目级资产的上游对齐锚点。
3. 允许由注册用户在不同系统和不同 IDE 上复用同一套配置。

在当前阶段，`global` 可以先通过 canonical AOL 或显式指定的共享目录模拟，不要求立即引入真实云端后端。

### 4.2 system

`system` 指机器级或管理员级安装位置。其职责如下：

1. 承载对同机多个用户可见的配置。
2. 表达必须放在系统路径、程序数据目录或全局配置目录中的载体。
3. 区分与用户主目录相似但权限模型不同的安装位置。

### 4.3 user

`user` 仍是当前 AOB 运行时最成熟的范围。其职责如下：

1. 承载 `~/.claude`、`~/.qwen`、`~/.copilot` 以及 IDE 用户 prompts 根目录等用户私有办公区。
2. 作为本机单用户同步、备份与恢复的主要对象。
3. 为项目级和系统级之外的个人配置提供默认落点。

### 4.4 project

`project` 指项目、仓库或工作区级载体。其职责如下：

1. 承载 `.github/copilot-instructions.md`、`.claude/`、`.cursor/rules/`、`CLAUDE.md`、`GEMINI.md`、`AGENTS.md` 等项目内约束。
2. 把 AI 内容与项目源码、测试、文档、协作规范放在同一版本控制边界内。
3. 允许同一项目同时存在多个引擎/IDE 供应商的工作区投影。

项目级是本轮新增范围中的重点，因为它直接决定跨仓库协作、仓库级规范与工作区转换的统一口径。

## 五、范围与 profile 的关系

### 5.1 install_scope 是 profile 的一等字段

工作区 target profile 不应只描述引擎、IDE 和路径模板，还必须显式声明 `install_scope`。其作用如下：

1. 指明该 profile 默认投影到哪一类范围。
2. 约束 resolver 的自动发现口径。
3. 约束发布与备份时的目标集合。
4. 约束同步时 side 的参与边界。

### 5.2 scope 与 layout 的关系

`scope` 与 `layout` 是两个不同维度：

1. `scope` 回答“内容在哪一层生效”。
2. `layout` 回答“该层内部如何组织文件与目录”。

因此，`project` 与 `user` 可以同时使用 `structured_root` 布局；差异不在目录结构形状，而在安装边界、发现规则和审计口径。

## 六、范围进入 AOB 四大功能的要求

### 6.1 聚合

聚合阶段必须把来源对象扩展为五维来源：

1. `source_path`
2. `source_label`
3. `layout`
4. `engine_vendor`
5. `ide_vendor`
6. `scope`

聚合不再默认只扫描用户级目录，而是按照显式路径、显式 project 目录和 scope 过滤决定参与来源。

### 6.2 发布

发布阶段必须把目标对象扩展为五维目标：

1. `target_path`
2. `target_label`
3. `layout`
4. `engine_vendor`
5. `ide_vendor`
6. `scope`

发布时同一项目根目录可以承载多个 `project` 目标实例，每个实例对应一个 profile 投影。

### 6.3 备份

备份清单必须记录范围维度，至少包含：

1. `scope`
2. `layout`
3. `source_path`
4. `destination_path`
5. `status`

这样才能在恢复时区分“备份的是项目级副本还是用户级副本”。

### 6.4 同步

同步阶段必须把范围显式进入 side 审计：

1. 每个 side summary 都应记录 `scope`。
2. `target_paths`、`project_dirs` 与 `scope` 过滤共同决定参与方集合。
3. `libs` canonical 仍是语义真源，但不应把所有安装层默认折叠为用户级 side。

## 七、范围发现与解析原则

### 7.1 显式优先

只要用户显式给出路径，运行时就应优先解析显式路径，并根据路径位置与载体特征推断范围；不得先自动扫描一批用户级目录再回头覆盖显式目标。

### 7.2 项目级发现

项目级发现应基于 profile 真源与项目根目录共同完成。最小策略如下：

1. 由调用方显式给出 `project_dirs`。
2. 读取 `workspace_target_profiles.json` 中 `install_scope=workspace` 的 profile。
3. 对每个项目根目录检测 `workspace_dir_name`、`instruction_paths`、`project_config_paths` 对应的标记是否存在。
4. 为每个命中的 profile 生成单独的 `project` 范围来源或目标。

### 7.3 系统级与全局级发现

系统级与全局级的自动发现必须保守进行：

1. 没有可靠路径契约时，允许只支持显式路径接入。
2. 系统级路径不得错误地因为位于用户主目录附近就被当成用户级。
3. 全局级路径不得错误地因为存在于本地磁盘就被当成本机用户级。

## 八、范围与同步安全

范围维度的引入不仅是建模问题，也是安全问题。必须遵守以下原则：

1. 不同范围的备份与恢复清单必须可区分。
2. 项目级发布不得默认覆盖用户级目录。
3. 用户级同步不得把项目级文件误判为用户级私有副本并删除。
4. 对 `global` 与 `system` 的写入必须保持显式、可审计、可回滚。

## 九、阶段性落地策略

本轮落地采用“范围先入模，再扩自动发现”的策略：

1. 第一阶段，把 `scope` 接入 AOB 四大功能的数据结构、参数、统计和事务入口。
2. 第二阶段，把 `project` 范围接入 profile 驱动的自动发现。
3. 第三阶段，把 `system` 与 `global` 范围收敛到更稳定的 profile registry 和共享后端。

## 十、验收标准

完成本设计后的实现至少应满足：

1. AOB 聚合、发布、备份、同步的来源/目标摘要中存在 `scope` 字段。
2. `project` 范围可通过显式项目目录进入 AOB 主链。
3. 同一项目根目录可为多个引擎/IDE profile 生成独立目标实例。
4. 备份 manifest、同步 side summary 与发布统计能区分 `global/system/user/project`。
5. 文档、事务手册与 API 手册都显式说明范围维度，而不再把全部行为描述为“用户级目录同步”。
