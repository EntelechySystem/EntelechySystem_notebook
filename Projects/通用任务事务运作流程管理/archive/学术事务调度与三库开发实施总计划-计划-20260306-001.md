# 学术事务调度与三库开发实施总计划-计划-20260306-001

## 1. 背景与输入

本计划整合以下思考文档：

1. `think-学术事务运作流库与多层调度设计-20260305-002.md`
2. `think-事务任务知识检索开发设计-20260306-001.md`
3. `think-数据库选型分析-20260306-001.md`
4. `think-事务任务调度功能开发设计-20260306-001.md`
5. `think-检索子流程设计-20260305-001.md`

计划目标：在“原型优先、学术任务优先”的前提下，快速落地可运行的学术研究工作流事务调度与三类数据库体系。

## 2. 总体分析

### 2.1 统一架构

1. 控制平面：`项目经理 agent`（CC 主控）负责任务拆解、路由决策、回退裁决。
2. 执行平面：AOK 事务/流程图负责可复用执行动作。
3. 桥接平面：skills 的 `scripts` 承担调度桥接与参数适配。
4. 数据平面：`database/tasks`、`database/references`、`database/knowledge`。

### 2.2 原型期边界

1. 数据库主存储：`pandas + CSV/JSONL + 文件系统`。
2. 暂不做全量 SQLite 化，仅预留迁移接口。
3. 优先完成“可运行闭环”，再做工程化增强。

### 2.3 关键原则

1. 先跑通：先让系统能稳定执行科研任务。
2. 少而稳：一级事务主路网固定，二级事务按需扩展。
3. 可追溯：每步调度、执行、审计均留痕。
4. 可迁移：字段设计从一开始兼容后续 SQLite。

### 2.4 学术研究多层工作流整体架构

为覆盖“从研究构思到评审修订”的完整学术研究生命周期，采用“五层协同架构”。

1. `L0 治理层`（Governance）
- 角色：`项目经理 agent` + 审计策略集。
- 职责：目标分解、优先级裁决、风险闸门、结果码路由总控。

2. `L1 任务层`（Task Graph）
- 单元：研究任务包（问题定义、方法路线、实证子任务、写作子任务）。
- 职责：维护任务依赖图、父子任务关系、任务状态迁移。

3. `L2 事务层`（Transaction Graph）
- 单元：15 个一级事务主节点 + 按需展开的二级事务。
- 职责：形成可回环、可重规划的事务主路网，不强制固定全路径。

4. `L3 执行层`（Execution Flow）
- 单元：AOK workflows + skills scripts。
- 职责：把事务决策映射为可复用执行流，返回结构化结果码。

5. `L4 数据与证据层`（Data & Evidence）
- 单元：`database/tasks`、`database/references`、`database/knowledge` + `logs/run` + `logs/audit`。
- 职责：持久化状态、证据、日志，支撑回放、审计和迁移。

#### 2.4.1 全局运行主链路

1. `L0` 接收任务目标并拆解到 `L1`。
2. `L1` 选择当前活跃任务并请求 `L2` 计算下一事务。
3. `L2` 基于主路网倾向分值和实时上下文生成候选集。
4. `L0` 对候选集执行策略裁决并下发到 `L3`。
5. `L3` 调用 AOK 执行事务，返回 `PASS/RETRY/BACKTRACK/BLOCKED`。
6. `L0` 触发审计并根据结果码做继续、重试、回退或阻断。
7. `L4` 写入状态、日志和证据，然后回到步骤 2 进入下一轮。

#### 2.4.2 一级事务主路网与多分支研究路径

1. 主路网节点保持 15 个一级事务（已在 think 文档冻结）。
2. 支持三类常用研究路径：
- 文献驱动链：`提出研究问题 -> 文献检索 -> 文献管理 -> 文献阅读 -> 确定研究目标 -> 写作与修订`。
- 数据驱动链：`确定研究方法/数据 -> 数据检索 -> 数据管理 -> 实证/实验 -> 写作与修订`。
- 评审回环链：`写作与修订 -> 评审 -> 写作与修订`。
3. 三类路径可以并行或交叉，不要求单一线性 DAG。

#### 2.4.3 动态重规划与路由机制

1. 候选边评分：`score(i,j)=w_b*b(i,j)+w_g*goal_gain+w_r*risk_penalty+w_c*cost_penalty+w_t*time_penalty+w_a*audit_bonus`。
2. 路由策略：`argmax(score)` 或 `softmax(score)` 采样。
3. 审计硬约束：不合规边直接置零，不进入候选。
4. 闭源/高风险链路强制插入人工闸门，不得跳过。

#### 2.4.4 多层职责边界（防止耦合）

1. `L0/L1` 负责“做什么、何时做、谁来做”。
2. `L2` 负责“下一步事务去哪”。
3. `L3` 负责“具体怎么执行”。
4. `L4` 负责“执行后如何留痕与复现”。
5. 禁止把全局调度策略硬编码到单个 AOK workflow。

## 3. 开发方案

### 3.1 模块化方案

1. 调度内核（独立开发）：`src/scheduler_core/`
- `candidate_builder.py`
- `edge_scorer.py`
- `route_selector.py`
- `route_guard.py`
- `dispatch_executor.py`
- `types.py`

2. skill 桥接脚本：`.opencode/skills/scheduler-dispatch/scripts/`
- `run_scheduler_dispatch.py`
- `run_route_guard.py`
- `emit_dispatch_logs.py`

3. AOK 执行流定义：`.opencode/workflows/`
- 存放可复用事务流程图定义
- 不存放全局调度策略

4. 数据目录（原型期）：
- `database/tasks/`
- `database/references/`
- `database/knowledge/`

### 3.2 三类数据库方案

1. 事务/任务数据库（`database/tasks`）
- 文件：`tasks.csv`、`transactions.csv`、`task_transaction_map.csv`、`task_edges.csv`、`execution_runs.jsonl`、`manifests.json`
- 功能：任务状态迁移、事务边权、回退与审计留痕

2. 文献数据库（`database/references`）
- 文件：`literature_items.csv`、`literature_files.csv`、`literature_manifest.json`
- 子目录：`unit_db/`、`vector_index/`
- 功能：条目 CRUD、原文切分索引、向量映射

3. 知识数据库（`database/knowledge`）
- 文件：`knowledge_notes.csv`、`knowledge_links.csv`、`knowledge_evidence_map.csv`、`knowledge_manifest.json`
- 子目录：`notes/`、`vector_index/`
- 功能：任务驱动知识提炼、证据链与双链关系管理

### 3.4 事务/任务数据库管理系统设计开发

目标：在原型期建立一个轻量但完整的“任务-事务状态管理系统”，支持 CSV 主存储下的稳定写入、查询、回放与审计。

#### 3.4.1 管理系统功能边界

1. Schema 管理：统一字段定义、字段版本、必填约束。
2. CRUD 管理：对 `tasks/transactions/task_transaction_map/task_edges` 的增删改查。
3. 状态迁移管理：任务状态、事务步骤状态、结果码迁移规则。
4. 快照与回放：按运行批次生成快照并支持回放恢复。
5. 数据校验：主键唯一性、引用完整性、状态机合法性校验。
6. 导出接口：为审计与后续 SQLite 迁移导出标准化文件。

#### 3.4.2 管理系统实现模块（原型期）

建议新增 `src/tasking_db/`：

1. `schema_registry.py`
- 管理字段清单、默认值、版本号。

2. `csv_store.py`
- 封装 CSV 读写、批量写入、原子替换。

3. `state_machine.py`
- 管理状态迁移规则（含 `PASS/RETRY/BACKTRACK/BLOCKED`）。

4. `integrity_checks.py`
- 执行唯一键、外键映射、非法状态流转校验。

5. `snapshot_manager.py`
- 生成与恢复 `database/tasks/snapshots/` 快照。

6. `replay_engine.py`
- 基于 `execution_runs.jsonl` 回放任务与事务状态。

#### 3.4.3 与 skill/agent 的连接方式

1. `table-maintenance` skill 调用 `src/tasking_db` 完成所有表操作。
2. `task-state-manager` 与 `transaction-state-manager` 不直接写 CSV，只调用 `table-maintenance`。
3. `项目经理 agent` 触发调度后，由桥接脚本调用 `table-maintenance` 记录状态变更。

### 3.5 事务/任务数据表设计开发（补充）

#### 3.5.1 表设计原则

1. 字段先稳后全：原型期保留最小必要字段。
2. 关系可追溯：任务、事务、边、执行日志必须可串联。
3. 迁移友好：字段命名和类型约束兼容未来 SQLite。

#### 3.5.2 原型期核心表字段（建议）

1. `tasks.csv`
- `task_uid,name,status,parent_task_uid,priority,current_transaction_uid,owner_agent,created_at,updated_at`

2. `transactions.csv`
- `transaction_uid,name,level,input_schema_ref,output_schema_ref,retry_policy,audit_policy,version,enabled`

3. `task_transaction_map.csv`
- `map_uid,task_uid,step_order,transaction_uid,step_status,last_result_code,started_at,ended_at`

4. `task_edges.csv`
- `edge_uid,from_transaction_uid,to_transaction_uid,condition,active,base_tendency_score,dynamic_delta,transition_prob,version`

5. `execution_runs.jsonl`
- `run_uid,task_uid,transaction_uid,selected_edge_uid,result_code,audit_result,executor_agent,skill_name,started_at,ended_at,error_message`

6. `manifests.json`
- `schema_version,generated_at,row_counts,hashes,snapshot_id`

#### 3.5.3 关键约束规则

1. 主键唯一：`task_uid/transaction_uid/map_uid/edge_uid/run_uid` 必须唯一。
2. 引用完整：`task_transaction_map.task_uid` 必须存在于 `tasks`。
3. 状态合法：`step_status` 只能在定义状态集合中流转。
4. 边权合法：`base_tendency_score` 范围 `0-100`。
5. 概率字段合法：`transition_prob` 范围 `0-1`。

### 3.6 检索子流程专项集成

目标：把检索子流程设计中的“16 组合 + 统一状态机 + 差异化审计 + 闭源人工闸门”落地到本计划实施链路。

#### 3.6.1 检索状态机接入策略

统一检索状态机链路：

1. `R0` 检索请求输入。
2. `R1` 四维标注（文献/数据、离线/在线、国内/国外、开源/闭源）。
3. `R2` 授权判定（闭源进入人工闸门）。
4. `R3` 检索执行。
5. `R4` 规范化入库。
6. `R5` 审计判定。
7. `R6` 路由输出到下一研究节点。

说明：

1. 16 种组合共享同一状态机模板，不单独造 16 套系统。
2. 闭源链路必须进入人工授权闸门，不允许绕过。

#### 3.6.2 16 组合实现策略

1. 文献 8 组合与数据 8 组合共用同一执行骨架。
2. 差异主要在来源适配器、审计规则与回退策略。
3. 通过 `retrieval-governance` 输出统一结果码：`PASS/RETRY/BACKTRACK/BLOCKED`。

#### 3.6.3 检索到知识管理的输入契约

检索输出统一对象 `retrieval_bundle`：

1. `bundle_id`
2. `object_type`
3. `source_type`
4. `file_paths`
5. `manifest_patch`
6. `permission_status`
7. `result_code`

消费规则：

1. 仅 `PASS` 或 `RETRY后PASS` 可进入知识采集流程。
2. `BLOCKED` 进入候选池，等待人工处置。

#### 3.6.4 产物与日志落位

1. 文献检索规范化台账：`database/references/literature_manifest.json`。
2. 检索运行日志：`logs/run/`。
3. 检索审计日志：`logs/audit/`。
4. 检索到知识管理的 bundle 清单：`database/references/retrieval_bundles.jsonl`（原型期建议）。

### 3.7 非数据库调度管理系统详细开发方案（补充）

目标：补齐“除数据库 CRUD 之外”的调度管理能力，形成可测试、可扩展、可观测的调度子系统。

#### 3.7.1 功能范围与非功能要求

1. 功能范围：候选构建、边评分、路由选择、结果码守卫、执行派发、调度日志。
2. 非功能要求：
- 单次调度决策可观测（输入、候选、评分、输出必须可追溯）。
- 调度组件可替换（评分器和选择器支持策略切换）。
- 与存储解耦（调度内核不直接读写 CSV 文件）。

#### 3.7.2 调度内核接口契约（`src/scheduler_core`）

1. `candidate_builder.build_candidates(context) -> CandidateSet`
- 输入：任务上下文、当前事务、可用边、审计约束。
- 输出：可执行候选事务集合。

2. `edge_scorer.score_edges(candidates, context, weights) -> ScoredCandidates`
- 输入：候选集合、运行时特征、权重参数。
- 输出：含 `score` 与解释字段的候选集合。

3. `route_selector.select_next(scored, strategy) -> SelectionResult`
- 输入：评分结果、选择策略（`argmax|softmax`）。
- 输出：下一事务、备选列表、选择理由。

4. `route_guard.apply(result_code, audit_result, selection) -> GuardDecision`
- 输入：执行结果码、审计结果、当前选择。
- 输出：`continue|retry|backtrack|block`。

5. `dispatch_executor.dispatch(selection, execution_profile) -> DispatchReceipt`
- 输入：下一事务选择、执行映射配置。
- 输出：调用回执（目标 workflow、参数、执行句柄）。

#### 3.7.3 运行时时序（端到端）

1. 读取当前任务上下文（由桥接层提供）。
2. 构建候选事务集合。
3. 过滤不合规候选（审计/授权硬约束）。
4. 对候选边评分并生成可解释特征。
5. 选择下一事务并输出备选排序。
6. 映射到 AOK workflow 并触发执行。
7. 获取结果码并执行 `route_guard`。
8. 产出结构化调度事件（供日志模块写入）。
9. 返回给 `项目经理 agent` 做下一轮决策。

#### 3.7.4 异常与降级机制

1. 无可用候选：返回 `BLOCKED`，并附“阻断原因 + 建议人工动作”。
2. 执行超时：返回 `RETRY`，附退避参数与最大重试次数。
3. 连续重试失败：升级为 `BACKTRACK`，回退到最近稳定事务。
4. 审计失败：强制 `BLOCKED`，禁止进入后续高风险链路。
5. 路由冲突：由 `项目经理 agent` 执行优先级裁决后重算。

#### 3.7.5 配置与策略文件

建议新增 `config/scheduler/`（或同等目录）：

1. `edge_weights.yaml`：评分权重与默认阈值。
2. `selection_policy.yaml`：`argmax/softmax` 与温度参数。
3. `guard_policy.yaml`：结果码映射与回退策略。
4. `dispatch_map.yaml`：事务到 workflow/skill 的映射关系。

#### 3.7.6 测试与验收细案

1. 单元测试：
- 候选生成正确性。
- 评分结果可重复性。
- 路由选择确定性（固定随机种子）。

2. 集成测试：
- `项目经理 agent -> scheduler-dispatch -> AOK workflow -> route_guard` 全链路。

3. 回归测试：
- 文献驱动链与数据驱动链各至少 1 条样例链路。

4. 验收标准：
- 决策日志字段完整率 100%。
- 异常路径均返回结构化结果码。
- 调度内核无直接 CSV 写操作。

### 3.8 agent 与 skill 调用关系

1. `项目经理 agent`
- 调用 `scheduler-dispatch` skill 完成调度决策与执行触发。

2. `task-state-manager`（新建）
- 调用 `table-maintenance` skill 更新任务状态。

3. `transaction-state-manager`（新建）
- 调用 `table-maintenance` skill 更新事务状态和边权。

4. 事务执行类 agents
- 按调度结果执行，不承担全局路由职责。

## 4. 分阶段开发步骤

### 阶段 0：初始化（0.5 天）

1. 创建目录：`database/tasks`、`database/references`、`database/knowledge`、`.opencode/workflows`、`src/scheduler_core`。
2. 建立 CSV 文件模板、字段注释文档、状态迁移规则文档。
3. 定义统一结果码：`PASS/RETRY/BACKTRACK/BLOCKED`。

验收：目录与模板文件齐备，能被脚本读取。

### 阶段 1：调度闭环 MVP（2-3 天）

1. 开发 `candidate_builder + edge_scorer + route_selector + route_guard + dispatch_executor`。
2. 开发 `run_scheduler_dispatch.py`、`run_route_guard.py`、`emit_dispatch_logs.py`。
3. 由 `项目经理 agent` 调用 skill，返回下一事务与候选解释。
4. 执行后写入 `execution_runs.jsonl` 与状态 CSV。
5. 接入配置文件：`edge_weights/selection_policy/guard_policy/dispatch_map`。

验收：完成“调度 -> 执行 -> 守卫 -> 回传 -> 记录”最小闭环，且日志字段完整。

### 阶段 2：事务/任务管理完善（2 天）

1. 开发 `src/tasking_db`（schema、store、state_machine、integrity_checks、snapshot、replay）。
2. 开发 `table-maintenance` 的 CSV CRUD 与约束校验。
3. 开发 `task-state-manager`、`transaction-state-manager` 调用协议。
4. 增加快照与回放脚本。

验收：任务状态可追踪、可回放、可对账，且约束校验可自动执行。

### 阶段 3：文献管理落地（3 天）

1. 实现文献条目 CRUD 和引用键映射。
2. 对接 AOK 原文切分与向量索引事务。
3. 更新 `database/references` 索引与 manifest。

验收：文献资产可增删查改、可检索、可追溯。

### 阶段 4：知识管理落地（3 天）

1. 实现知识笔记入库、双链关系、证据映射。
2. 实现知识向量索引构建与更新。
3. 打通任务-事务-知识关联。

验收：知识可回链到文献证据，支持任务驱动查询。

### 阶段 5：检索治理接入（2 天）

1. 接入 `retrieval-governance` 与 `retrieval-router`，按统一状态机执行。
2. 固化 16 组合四维标注规则与闭源人工闸门。
3. 接入差异化审计模板（文献审计/数据审计）。
4. 输出 `retrieval_bundle` 并接线知识管理入口。

验收：检索链路具备治理规则、统一结果码、16 组合可复用模板与 bundle 输出。

## 5. 风险与应对

1. 风险：CSV 并发冲突。
- 应对：单写入队列 + 批量落盘 + 快照回滚。

2. 风险：调度策略频繁变更。
- 应对：保持调度内核独立，不下沉到流程图。

3. 风险：字段漂移导致对账困难。
- 应对：字段冻结窗口 + schema 版本标识。

4. 风险：日志留痕不完整。
- 应对：无日志不流转，强制写入后再进入下一步。

## 6. 验收标准

1. 能从 `提出研究问题` 跑到至少一个“检索->管理->阅读/实证”子链路。
2. 所有关键步骤均有 run/audit 日志。
3. 三类数据库均可独立查询、导出快照与回放。
4. agent/skill/事务调用链有文档化说明并可复现。
5. 事务/任务核心表具备字段约束、状态迁移校验与快照恢复能力。
6. 检索子流程完成 16 组合模板接入，并通过至少 2 条样例链路（文献1条、数据1条）。
7. 非数据库调度系统完成端到端联调，覆盖候选生成、评分、选择、守卫、派发、异常降级。
8. 多层工作流架构在样例任务中可观测到 `L0-L4` 闭环留痕。

## 7. 后续迁移门槛（SQLite）

满足任意两条时启动对应模块迁移：

1. 单表数据量持续超 `10-20 万` 且查询明显变慢。
2. 每日写入批次超 `50` 且冲突频发。
3. pandas 查询脚本维护成本显著上升。
4. 数据一致性问题频繁出现。
