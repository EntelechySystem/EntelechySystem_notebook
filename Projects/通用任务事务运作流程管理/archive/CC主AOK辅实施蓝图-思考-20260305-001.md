# CC主AOK辅实施蓝图-思考-20260305-001

## 1. 需求分析和目标分析

### 1.1 需求分析
在已确定采用“CC 主 + AOK 辅”框架后，需要一份可实施蓝图，回答以下问题：

1. OpenCode（CC）与 AOK 的职责边界如何划分。
2. 如何支持“项目启动前预设计流程图/事务”与“项目接管后动态新增流程图/事务”两种模式。
3. 如何将检索子流程纳入整体学术科研状态机而不破坏现有命令体系。
4. 如何通过审计结果驱动路由，而不是只记录日志。

### 1.2 目标分析
本轮目标是建立一份“架构可执行说明书”，作为后续工程实现依据：

1. 定义控制面、执行面、审计面的分层架构。
2. 定义路由输入、路由结果码、回退策略。
3. 定义事务与流程图资产的版本治理规则。
4. 给出分阶段落地路线与验收标准。

### 1.3 可行性与挑战
可行性：高。

1. ARW 已有完整 Agent/Command/Rule 控制面。
2. AOK 已有节点中心编排与事务扩展能力。

挑战：

1. 边界不清会导致 CC 与 AOK 双重调度冲突。
2. 若过早把高不确定阶段固化为流程图，会降低探索效率。
3. 若缺少统一结果码，会导致回退策略不可自动化。

## 2. 决策和计划

### 2.1 架构决策
采用“三层架构 + 双阶段实施”：

1. 控制面（CC）：负责规划、路由、异常升级、审计裁决。
2. 执行面（AOK）：负责稳定重复段事务执行。
3. 审计面（CC 双审计）：负责治理与复现双重判定。

### 2.2 分层职责

控制面（CC）职责：
1. 按学术状态机 N1-N12 管理阶段。
2. 在检索节点触发四维路由（文献/数据、离线/在线、国内/国外、开源/闭源）。
3. 调用 AOK 执行指定 workflow，并汇总结果。

执行面（AOK）职责：
1. 执行标准化动作：检索、去重、规范化、manifest 更新、批次日志。
2. 允许新增事务并挂载节点。
3. 输出结构化结果码与产物摘要。

审计面职责：
1. `whitelist-auditor`：权限与越权审计。
2. `reproducibility-auditor`：证据链与可复现审计。
3. 审计结果回传 `orchestrator` 决定 `PASS/RETRY/BACKTRACK/BLOCKED`。

### 2.3 实施计划（双阶段）

阶段 1：检索试点（低风险）
1. 保持现有命令不变。
2. 将检索子流程接入 AOK。
3. 验证产物、日志、结果码一致性。

阶段 2：增量扩展（稳定后）
1. 扩展到数据规范化、图表批处理。
2. 建立事务注册表与版本策略。
3. 引入自动回退模板与风险阈值。

### 2.4 验收标准

1. 路由准确：16 检索路由匹配正确率可验证。
2. 产物合规：路径符合 workspace 规则。
3. 审计闭环：每轮都有治理+复现双审计结论。
4. 回退可用：`RETRY/BACKTRACK/BLOCKED` 都有可执行动作。

## 3. 任务分配

### 3.1 分配给任务运作智能体

任务 A：控制面改造
1. 内容：定义 `orchestrator` 的路由输入输出契约。
2. 产物：`docs/command-node-mapping.md` 更新版。

任务 B：执行面接入
1. 内容：为检索流程定义 AOK workflow 与事务清单。
2. 产物：AOK workflow 配置与事务规范文档。

任务 C：审计联动
1. 内容：将审计结果码映射到回退策略。
2. 产物：`logs/audit/` 模板与策略说明。

任务 D：版本治理
1. 内容：建立 workflow/affair 版本号、兼容范围、回滚策略。
2. 产物：流程图资产治理清单。

## 4. 监控和调整

### 4.1 监控指标

1. 路由命中率：输入标签与实际执行路线的一致率。
2. 回退健康度：`RETRY/BACKTRACK` 占比与平均回退层级。
3. 审计通过率：治理审计与复现审计通过率。
4. 交付稳定性：同样输入的可复现一致性。

### 4.2 调整机制

1. 若路由冲突频繁：收敛路由规则，减少歧义标签。
2. 若回退过多：把问题前移到设计或检索阶段。
3. 若审计失败集中在同类事务：优先重构该事务而非改主流程。

### 4.3 本轮结论

当前最优路径是“CC 主控决策 + AOK 标准执行 + 双审计裁决”。该路径兼顾学术探索弹性与工程化稳定性，适合作为 ARW 的主实施蓝图。

## 5. 补充：检索、知识管理与 AOK 事务治理一体化

### 5.1 一体化链路

建议把“检索 -> K1 知识采集 -> 知识双分支”写成统一链路：

1. R 状态机（检索）输出 `retrieval_bundle`。
2. K1 消费 `retrieval_bundle` 生成 `knowledge_bundle`。
3. `knowledge_bundle` 按类型分流到：
- KM-L（文献管理）
- KM-D（数据管理）

### 5.2 AOK 事务使用策略

原则：`复用优先，缺口新增，统一注册`。

1. 复用：先使用 AOK 已有文献/解析/去重相关事务。
2. 新增：只补“ARW 特有缺口事务”（如证据等级、冲突对账、变量映射）。
3. 注册：新增事务必须进入事务注册表并标注版本、输入输出契约、审计要求。

### 5.3 路由调度责任

1. `orchestrator` 负责决定走哪条 R 路由与 KM 分支。
2. 文献分支执行由 `cn-literature-retriever` 主责。
3. 数据分支执行由 `cn-data-retriever` + `data-engineer` 主责。
4. 审计代理只判定，不改业务结果。

### 5.4 启动前/接管后两类工作模式

启动前（预建设）：
1. 预设计高频 workflow 与核心事务。
2. 先上线最小闭环（检索 + K1 + KM-L/KM-D）。

接管后（动态扩展）：
1. 依据运行缺口新增事务与流程图。
2. 每次新增都要通过契约检查、权限审计、可复现审计。

### 5.5 新增事务的准入门槛

1. 必须定义输入输出 schema。
2. 必须定义失败结果码与回退策略。
3. 必须定义日志字段和留痕路径。
4. 必须定义兼容版本与回滚方案。

### 5.6 补充结论

在 `CC 主 + AOK 辅` 框架下，检索与知识管理应按“供给层-转化层-治理层”一体化设计，确保新增事务可控、可审计、可回退，避免流程图与 Agent 双系统各自演化导致漂移。
