# 事务任务调度功能开发设计-思考-20260306-001

## 1. 需求分析和目标分析

### 1.1 需求分析
当前讨论对象是“事务/任务调度功能中，除数据库管理之外的能力”，包括：

1. 调度决策内核（下一跳选择、回退策略、优先级裁决）。
2. 任务图与事务图联合编排逻辑。
3. 候选事务生成、评分、结果码路由。
4. 调度日志与审计触发流程（不含底层数据库 CRUD）。

核心问题：

1. 这些能力是否全部用 AOK 开发？
2. 还是自行独立开发调度内核，再调用 AOK？
3. 代码放在哪、由哪个 skill 调用、由哪个 agent 触发？

### 1.2 目标分析

1. 保持 `CC 主控` 的决策权。
2. 保持 `AOK` 在事务执行与流程复用上的优势。
3. 避免过早复杂化，支持原型期快速落地。
4. 保证后续可平滑迁移到更工程化架构。

## 2. 决策和计划

### 2.1 架构结论（客观建议）

采用“混合开发”最合适：

1. 调度决策内核：独立开发（Python 模块）。
2. 事务执行动作：复用 AOK 事务/流程图。
3. skill 作为桥接层：把 CC 调度指令转换为 AOK 可执行调用。
4. agent 只做策略与编排，不承载底层执行细节。

简化表述：

`CC agent（决策） -> 调度 skill（桥接） -> AOK 事务（执行）`

### 2.2 为什么不建议“全 AOK”

1. AOK 擅长标准化事务执行，不擅长承载高频变动的全局调度策略。
2. 调度策略在原型期变化很快，写在独立 Python 内核迭代速度更高。
3. 把调度逻辑全放流程图会导致可读性和维护成本上升。

### 2.3 为什么不建议“全独立开发”

1. 会损失 AOK 现有事务复用资产。
2. 会重复建设事务执行链（检索、分块、索引等）。
3. 与当前“CC 主 + AOK 辅”的既定方向不一致。

### 2.4 非数据库调度功能的模块划分

建议拆成 5 个模块：

1. `candidate_builder`
- 输入当前任务状态，输出可选下一事务集合。

2. `edge_scorer`
- 根据倾向分值和实时特征计算 `score(i,j)`。

3. `route_selector`
- 根据策略选择下一跳（argmax 或采样）。

4. `route_guard`
- 处理 `PASS/RETRY/BACKTRACK/BLOCKED` 结果码与审计硬约束。

5. `dispatch_executor`
- 把决策结果映射到具体 AOK 事务调用。

### 2.5 开发位置建议（文件夹落位）

#### 2.5.1 调度内核代码（独立开发）

建议放在仓库源码目录：

1. `src/scheduler_core/`
- `candidate_builder.py`
- `edge_scorer.py`
- `route_selector.py`
- `route_guard.py`
- `dispatch_executor.py`
- `types.py`

原因：

1. 属于项目核心业务逻辑，不应埋在 prompt 层。
2. 便于测试、版本化和未来重构。

#### 2.5.2 skill 桥接脚本（调用 AOK）

建议放在：

1. `.opencode/skills/model-routing-dispatch/scripts/`（短期复用现有 skill 目录）
2. 后续新建更清晰目录：`.opencode/skills/scheduler-dispatch/scripts/`

建议脚本：

1. `run_scheduler_dispatch.py`：读取调度输入，调用 `src/scheduler_core`，触发 AOK 事务。
2. `run_route_guard.py`：处理结果码回退和审计闸门。
3. `emit_dispatch_logs.py`：写调度事件日志（run/audit）。

#### 2.5.3 AOK 工作流定义

建议放在：

1. `.opencode/workflows/`

用途：

1. 存放“被调度调用”的事务流程图定义。
2. 不放全局调度策略，只放可复用执行流。

### 2.6 谁调用哪个 skill（agent -> skill 关系）

建议关系：

1. `项目经理 agent`
- 调用 `scheduler-dispatch` skill，触发一次调度决策与执行。

2. `transaction-state-manager`（新建）
- 调用 `table-maintenance` skill 更新事务状态与边权增量。

3. `task-state-manager`（新建）
- 调用 `table-maintenance` skill 更新任务状态迁移。

4. 事务执行类 agent（如 `cn-literature-retriever`、`cn-data-retriever`）
- 由调度结果触发，不直接负责全局路由。

### 2.7 原型期最小可行实现（MVP）

第一批只做以下最小链路：

1. 在 `src/scheduler_core` 实现 `candidate_builder + edge_scorer + route_selector`。
2. 在 `.opencode/skills/.../scripts/` 提供 `run_scheduler_dispatch.py` 桥接脚本。
3. 由 `项目经理 agent` 调用该 skill，返回下一事务与调用参数。
4. 由 AOK 执行对应事务，并回传结果码。
5. 用 CSV/JSONL 写入调度日志与状态变更（符合原型期轻量化原则）。

## 3. 任务分配

### 3.1 分配给任务运作智能体

任务 A：调度内核最小模块开发
1. 内容：实现 `candidate_builder`、`edge_scorer`、`route_selector`。
2. 产物：`src/scheduler_core/` 初版模块。

任务 B：skill 桥接脚本开发
1. 内容：实现 `run_scheduler_dispatch.py` 与 `run_route_guard.py`。
2. 产物：`.opencode/skills/scheduler-dispatch/scripts/`（或短期放在现有 skill scripts）。

任务 C：AOK 工作流目录初始化
1. 内容：创建 `.opencode/workflows/` 并登记可调事务流。
2. 产物：工作流定义文件与调用映射清单。

任务 D：agent 调用关系接线
1. 内容：让 `项目经理 agent` 调用调度 skill，其他 agent 接受调度结果执行。
2. 产物：agent 调用协议与回传格式。

## 4. 监控和调整

### 4.1 监控指标

1. 调度决策耗时。
2. 下一跳命中率（选中后执行成功比例）。
3. 回退触发率（`RETRY/BACKTRACK/BLOCKED`）。
4. 调度-执行链路日志完整率。

### 4.2 调整机制

1. 若调度模块改动频繁：保持独立内核，不下沉到 AOK 流程图。
2. 若 AOK 执行复用率低：补齐工作流模板，而不是增强 agent 硬编码。
3. 若桥接层复杂度升高：拆分 skill（dispatch/guard/logging）。

### 4.3 本轮结论

1. 非数据库调度功能应采用“独立调度内核 + AOK 执行流复用”的混合开发。
2. 调度核心代码放 `src/scheduler_core/`，不建议放在单个 skill 脚本里硬编码。
3. skill 的 `scripts/` 负责桥接调用，AOK `workflows/` 负责执行流定义。
4. 由 `项目经理 agent` 触发调度 skill 最合适，事务类 agent 按调度结果执行。
