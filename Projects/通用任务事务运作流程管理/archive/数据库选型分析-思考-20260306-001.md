# 数据库选型分析-思考-20260306-001

## 1. 需求分析和目标分析

### 1.1 需求分析
当前需要为三类核心数据库选择存储方案：

1. 事务/任务数据库（调度状态、边权、执行日志）。
2. 文献数据库（条目、附件映射、单元索引、向量映射元数据）。
3. 知识数据库（任务驱动笔记、双链关系、证据映射、向量映射元数据）。

候选技术路线：

1. `SQLite`。
2. `pandas + CSV/JSONL`。

目标不是只选一种，而是选择“最合适的主方案 + 过渡方案”。

### 1.2 目标分析

1. 保证 CC 调度下每一步操作可追溯、可查询、可审计。
2. 兼顾开发早期速度与后期稳定性。
3. 为 AOK 事务化执行提供稳定的数据接口。
4. 降低并发写入、数据一致性和索引维护风险。

### 1.3 关键约束

1. 当前仓库已存在 `database/tasks`、`database/references`、`database/knowledge`。
2. 流程将逐步扩展，日志和关联关系会快速增长。
3. 未来需要支持回放、审计和条件查询，而不仅是离线统计。

## 2. 决策和计划

### 2.1 我的看法（先给结论）

推荐采用“原型优先、分阶段升级”方案：

1. 原型期（当前）：三类数据库统一以 `pandas + CSV/JSONL + 文件系统` 为主。
2. 稳定期（后续）：按触发条件把部分高频模块迁移到 `SQLite`。
3. 文献原文、切分文本、知识笔记正文始终保留文件系统存储。
4. 迁移目标是“最小必要迁移”，不是一次性全量重构。

原因：

1. 目前阶段以“尽快支持学术科研任务”优先，交付速度高于工程完备性。
2. pandas+CSV 在单机、单人或低并发场景下足以支撑原型运行。
3. 先跑通任务链路，后按瓶颈迁移，能避免过早工程化。

### 2.2 SQLite 与 pandas+CSV 对比分析

| 维度 | SQLite | pandas + CSV/JSONL |
|---|---|---|
| 数据一致性 | 支持事务（ACID），回滚明确 | 无原生事务，易出现半写入/覆盖 |
| 并发写入 | 支持有限并发，单机可控 | 并发风险高，文件锁与冲突难控 |
| 关系查询 | SQL 强，适合多表关联 | 需手写合并逻辑，复杂度高 |
| 索引能力 | 原生索引，查询性能稳定 | 依赖全量读入，数据大时慢 |
| 审计追踪 | 可通过日志表与触发器实现 | 需额外约定，易分散 |
| 演进维护 | schema 可迁移、可版本化 | 列变更与兼容维护成本高 |
| 上手速度 | 中等 | 快（MVP 很快） |
| 人工可读性 | 中（需工具查看） | 高（直接打开 CSV） |
| 适合场景 | 长期运行系统、调度状态面 | 快速原型、一次性分析、导入导出 |

### 2.3 三类数据库作用、区别与选型建议

| 数据库类型 | 核心作用 | 数据特征 | 主要操作 | 推荐主存储 | 过渡/辅助 |
|---|---|---|---|---|---|
| 事务/任务数据库 | 管理任务状态机与事务路由 | 高频更新、强一致、可追溯 | 状态迁移、边权更新、日志关联查询 | 原型期：CSV/JSONL；稳定期：SQLite | `execution_runs.jsonl`、SQL 回放模板预留 |
| 文献数据库 | 管理文献条目与原文索引 | 条目稳定增长、附件映射、索引查询 | 条目 CRUD、去重、引用键映射、单元索引检索 | 原型期：CSV + 文件系统；稳定期：SQLite + 文件系统 | CSV 导入导出 |
| 知识数据库 | 管理知识笔记与证据链 | 多关系网络、任务驱动增量、语义关联 | 笔记创建、双链维护、证据回链、版本快照 | 原型期：CSV/Markdown；稳定期：SQLite + Markdown | CSV 快照导出 |

### 2.4 为什么不是三库都用 CSV

1. 事务/任务库需要“状态一致性 + 回滚 + 条件查询”，CSV 很难稳态支持。
2. 文献库需要去重、映射和索引查询，CSV 在规模增长后性能与维护劣化。
3. 知识库天然是图状关系，CSV 可表达但维护复杂，容易产生孤立引用。

### 2.5 为什么不是三库都纯 SQLite（不落文件）

1. 文献原文、切分文本、知识笔记正文适合文件系统管理，便于审阅与版本控制。
2. 数据库更适合存元数据、关系、索引和状态，不适合承载全部大文本附件。
3. 最优是“数据库管结构，文件系统管正文/附件”。

### 2.6 分阶段落地策略

阶段 A（MVP）

1. 先建 CSV/JSONL 原型，验证字段与流程。
2. 用 `pandas` 做一次批处理清洗与对账。
3. 约定统一文件路径：`database/tasks`、`database/references`、`database/knowledge`。

阶段 B（稳定增强）

1. 保持 CSV/JSONL 主路径，补齐数据校验、快照、回放脚本。
2. 仅对最痛点模块做局部 SQLite 试点（例如 `tasks` 状态查询）。

阶段 C（按阈值迁移）

1. 当达到迁移阈值时，再将对应数据库切换到 SQLite。
2. 形成 schema 版本管理、迁移脚本与双写校验策略。

### 2.7 迁移触发阈值（从 CSV 到 SQLite）

满足任意两条时，启动对应模块迁移：

1. 单表记录量长期超过 `10-20 万` 且查询显著变慢。
2. 每日写入批次明显增多（例如 `>50` 批）且合并冲突频发。
3. 审计查询需要高频多表关联，pandas 脚本维护成本过高。
4. 发生数据一致性问题（重复键、孤立映射）且人工修复频繁。
5. 团队并行写入增加，CSV 文件锁冲突影响任务推进。

## 3. 任务分配

### 3.1 分配给任务运作智能体

任务 A：数据库选型落地规范
1. 内容：确定原型期三库主存储为 pandas+CSV/JSONL，定义迁移阈值。
2. 预期结果：统一轻量化路线与后续升级边界。

任务 B：三库 schema 初版
1. 内容：输出 tasks/references/knowledge 三库 CSV schema 与键约束规则。
2. 预期结果：可执行建库脚本。

任务 C：迁移与导出脚本
1. 内容：实现 CSV 校验、快照导出、以及预留 CSV -> SQLite 迁移脚本。
2. 预期结果：可逆迁移链路。

任务 D：查询与审计模板
1. 内容：先实现 pandas 查询模板（状态回放、边权追踪、证据回链），并预留 SQL 版本。
2. 预期结果：可复用审计查询集与未来迁移接口。

## 4. 监控和调整

### 4.1 监控指标

1. 写入失败率（按库分开统计）。
2. 查询耗时（任务状态查询、文献映射查询、知识回链查询）。
3. 数据一致性错误数（孤立外键、重复键、缺失映射）。
4. 导出快照成功率与可回放率。

### 4.2 调整机制

1. 若 CSV 写入冲突升高：引入单写入队列、分库分表与批量落盘策略。
2. 若 schema 变化频繁：先冻结字段，再做 CSV 字段版本化。
3. 若 pandas 查询慢：先优化分层快照与索引列，再决定 SQLite 迁移。
4. 若人工排查困难：增强 CSV 快照导出粒度和周期。

### 4.3 本轮结论

1. 原型期三类数据库统一建议先采用 `pandas + CSV/JSONL + 文件系统`。
2. 当前阶段优先“快速落地学术科研任务”，避免过早工程化。
3. 当达到迁移阈值时，再把高频模块分步切换到 SQLite。
4. 该渐进式方案兼容 CC 主控与 AOK 事务执行，且风险可控。
