# AOK代码结构分层统一重构方案-计划-20260308-001

## 1. 计划背景

当前 `academicresearch_kit` 已完成部分结构演进：

1. 领域能力（`knowledge_prescreen`、`literature_reading`、`local_reference_ingestion`、`retrieval_governance`）已集中到 `domains/`。
2. 仍存在历史结构并存：根目录门面模块、`scheduler_core/`、`tasking_db/`、`workflow_*` 与 `main.py` 混放。
3. 后续还有大量能力待开发，需要先稳定结构语义，避免“边开发边漂移”。

本计划目标：在不破坏现有可运行能力的前提下，统一 AOK 的分层结构、公开 API 契约与迁移路径。

## 2. 设计原则（理论对齐）

基于“任务/事务双层工作流 + 控制面/事务路由面/执行面/数据与证据面”理论，采用以下原则：

1. 公开契约先于内部整理：优先稳定外部导入与调用路径。
2. 分层优先于命名：先明确职责边界，再收敛目录命名。
3. 渐进迁移优先于一次性重构：每次只迁一个能力簇，确保可回滚。
4. 领域实现与应用编排分离：`domains` 不承载 CLI 与全局流程总控。
5. 数据与证据能力单独成层：任务数据库与日志回放能力从业务域中抽离为平台层。

## 3. 目标结构（建议）

```text
academicresearch_kit/
  __init__.py
  api/                         # 对外稳定门面层（Facade）
    __init__.py
    retrieval.py
    scheduler.py
    taskdb.py
  application/                 # 应用层：总入口与跨域流程编排
    __init__.py
    main.py
    workflow_executor.py
    workflow_runtime.py
  domains/                     # 领域层：事务能力与规则
    __init__.py
    knowledge_prescreen/
    literature_reading/
    local_reference_ingestion/
    retrieval_governance/
    scheduling/                # 由 scheduler_core 迁入
  platform/                    # 平台层：数据与证据能力
    __init__.py
    taskdb/                    # 由 tasking_db 迁入
  skills/                      # skill 桥接层
  cli/                         # CLI 层
  tools/                       # 通用工具层
```

说明：

1. 若短期不引入 `platform/`，可先迁到 `domains/taskdb/`，后续再二次迁移到 `platform/taskdb/`。
2. 根目录仅保留 `__init__.py` 与少量兼容转发入口，不再持续堆叠新实现文件。

## 5. 对外 API 契约方案

### 5.1 稳定导入路径（长期承诺）

1. `academicresearch_kit.api.retrieval`
2. `academicresearch_kit.api.scheduler`
3. `academicresearch_kit.api.taskdb`
4. `academicresearch_kit.skills.*`
5. `academicresearch_kit.main.run`（兼容入口，内部可转发）

### 5.2 内部实现路径（不承诺稳定）

1. `academicresearch_kit.domains.*`
2. `academicresearch_kit.platform.*`
3. `academicresearch_kit.application.*`

### 5.3 兼容策略

1. 保留旧路径转发至少 1 个版本周期。
2. 在旧入口发出废弃提示（文档先行，代码后收）。
3. 版本切换时同步更新 `docs/API手册.md` 与 `docs/开发者指南.md`。

## 6. 分阶段实施计划

### 阶段 A：契约冻结（低风险）

1. 新建 `api/`、`application/`、`platform/` 目录与 `__init__.py`。
2. 先复制门面文件到 `api/`，并在旧路径保留转发。
3. 更新文档中的推荐导入路径为 `academicresearch_kit.api.*`。

验收：

1. 现有 CLI 与 skills 脚本可用。
2. `import academicresearch_kit as ark` 的对外能力无回归。

### 阶段 B：调度域迁移

1. 迁移 `scheduler_core/` 到 `domains/scheduling/`。
2. 修改内部 import 到新路径。
3. 保留 `scheduler_core` 兼容转发层（短期）。

验收：

1. `scheduler-dispatch` 技能执行通过。
2. `config/scheduler/dispatch_map.json` 路径解析无异常。

### 阶段 C：任务数据库平台化

1. 迁移 `tasking_db/` 到 `platform/taskdb/`。
2. 调整 `api/taskdb.py` 的 re-export 来源。
3. 保留 `tasking_db` 兼容转发层（短期）。

验收：

1. `taskdb-bootstrap`、`taskdb-validate`、`taskdb-replay` 三个技能通过。
2. CSV/JSONL 落盘路径与格式不变。

### 阶段 D：应用层归位

1. 迁移 `main.py`、`workflow_executor.py`、`workflow_runtime.py` 到 `application/`。
2. 根级入口改为轻量转发。

验收：

1. `academic-research-kit --dry-run` 与真实执行链路通过。
2. `workflow_count`、`execution_result_count` 等关键输出字段一致。

### 阶段 E：收口与清理

1. 删除过期兼容层（达到约定版本后）。
2. 更新开发文档与目录说明。
3. 固化“新代码落点规则”。

验收：

1. 目录语义清晰且无重复实现。
2. 文档、代码、技能入口保持一致。

## 7. 开发治理规则（新增）

1. 新增领域能力：必须放入 `domains/<domain>/`。
2. 新增公开入口：必须放入 `api/`，并在 `__all__` 显式导出。
3. 新增流程总控逻辑：必须放入 `application/`。
4. 新增任务数据库/日志回放/证据能力：必须放入 `platform/`。
5. 禁止在 `skills/` 写入不可复用业务核心实现，`skills` 仅做桥接封装。

## 8. 风险与回滚

### 8.1 主要风险

1. 深层 import 路径遗漏导致运行时报错。
2. `dispatch_map` 中的模块字符串路径失效。
3. 文档与代码路径不同步，导致协作误用。

### 8.2 回滚建议

1. 每阶段单独提交并打标签。
2. 保留旧路径兼容层，出现问题可快速切回旧入口。
3. 每阶段都保留可执行 smoke test 脚本。

## 9. 验收口径

本计划完成后需满足：

1. 结构上：`api/application/domains/platform` 四层语义明确。
2. 能力上：现有技能与 CLI 行为与迁移前一致。
3. 文档上：`academicresearch_kit/docs/开发者指南.md` 与 `academicresearch_kit/docs/API手册.md` 完整更新。
4. 治理上：新增代码可按目录规则自动判断落点，减少后续结构漂移。
