# CNKI技能对OpenCode与ARK借鉴分析-报告-20260308-001

## 1. 背景

本汇报针对 `cnki-skills` 仓库进行定向借鉴分析，回答两个问题：

1. 它对我们当前 `OpenCode` 学术研究模板与 `academicresearch_kit`（ARK）在【检索】事务中“联网检索国内中文文献”的子事务设计，有哪些可直接借鉴之处。
2. 除检索事务之外，它对我们其他层面的流程、技能拆分与能力封装，还有哪些可借鉴之处。

本次分析采用“对方仓库能力颗粒度”对照“我方仓库当前已实现骨架”的方式，不讨论 Claude 运行时本身，只讨论对我们现有 OpenCode + ARK 体系可复用的设计。

## 2. 当前根据既有计划的开发状态

结合 `plan-学术事务调度与三库开发实施总计划-20260306-001.md` 与 `plan-OC代理与ARK桥接联调计划-20260307-001.md`，当前与本议题直接相关的状态如下：

1. OpenCode 侧已经有检索治理骨架：
- 已有 `retrieval-governance` skill。
- 已有 `cn-web-acquisition`、`cn-subscribed-literature-access` 两个检索相关 skill 说明。
- 已有 `cn-literature-retriever` 代理，职责上已经覆盖“本地优先 -> 开放联网 -> 订阅库人工授权”。

2. ARK 侧已经有最小检索状态机：
- `academicresearch_kit/domains/retrieval_governance/engine.py` 已实现 `RetrievalRequest -> RetrievalBundle -> next_node`。
- 当前能处理开放/闭源、国内/国外、在线/离线等治理维度。

3. 现阶段缺口不在“是否有检索流程概念”，而在“是否有面向具体中文数据库的细粒度执行协议”：
- 当前 `cn-web-acquisition` 更像通用中文联网采集规划器。
- 当前 `cn-subscribed-literature-access` 更像合规门禁说明与产物约束。
- 当前 ARK 检索治理更像状态机与路由器，还不是“CNKI 专项执行器”。

结论：我们已经有“治理层”和“流程层”的最小骨架，但缺少 `cnki-skills` 这种“面向单一中文数据库的高颗粒度操作能力层”。

## 3. 对齐表

对方仓库与我们的仓库的对齐表：

| 各项 | 对方仓库的描述-1 | 对方仓库的描述-2 | 我们的仓库的描述-1 | 我们的仓库的描述-2 |
| --- | --- | --- | --- | --- |
| 检索对象 | 聚焦 CNKI 单站点中文文献与期刊 | 包含论文、期刊、收录、目录、下载、导出 | 聚焦“文献/数据”统一检索治理 | 尚未细化到单站点 CNKI 专项执行 |
| 技能粒度 | 10 个细粒度技能 | 检索、解析、翻页、详情、收录、目录、下载、导出拆开 | 目前以 `cn-web-acquisition`、`cn-subscribed-literature-access` 为粗粒度封装 | 缺少面向 CNKI 的子事务切片 |
| 编排方式 | `cnki-researcher` 统一调度 10 个技能 | 内置验证码暂停、标签页管理、多步工作流 | `cn-literature-retriever` 已定义总流程 | 但没有面向 CNKI 页面状态的细粒度编排协议 |
| 合规门禁 | 明确要求人工登录、人工过验证码 | 不绕过授权，只在已登录会话中工作 | 已有 `run-campus-auth-human-gate` 与订阅访问 skill | 合规原则已到位，但执行细节仍偏抽象 |

| 输出结构 | 每步输出结构化字段 | 包含结果数、页码、导出 ID、期刊收录、详情元数据 | 当前 bundle 主要记录治理元数据与路由 | 缺少 CNKI 结果项级字段标准 |
| 下游衔接 | 支持下载、RIS、GB/T、Zotero | 检索结果可直接进入文献管理 | 我们已有本地导入与知识预筛选引擎 | 缺少“联网结果 -> 入库”的直接桥接格式 |
| 期刊能力 | 独立支持期刊检索、收录查询、目录浏览 | 能支撑中文期刊级别判断 | 我们当前检索事务主要盯文献本身 | 缺少“期刊评价/刊期目录”子事务 |
| 运行时依赖 | 强依赖 Chrome DevTools MCP 与人工浏览器会话 | 偏前端页面自动化协议 | 我们核心是 OpenCode 规则 + ARK Python 包 | 适合借鉴协议，不适合把实现直接搬进 ARK 核心 |

## 4. 对检索事务的直接借鉴

### 4.1 最值得借鉴的是“子事务拆分方式”

`cnki-skills` 最大价值，不是它用了 Claude，而是它把“中文订阅文献联网检索”拆成了可控、可组合、可中断恢复的子事务：

1. 检索：`cnki-search`
2. 高级检索：`cnki-advanced-search`
3. 结果页重解析：`cnki-parse-results`
4. 翻页与排序：`cnki-navigate-pages`
5. 单篇详情：`cnki-paper-detail`
6. 期刊检索：`cnki-journal-search`
7. 期刊收录判断：`cnki-journal-index`
8. 期刊目录浏览：`cnki-journal-toc`
9. 下载：`cnki-download`
10. 导出：`cnki-export`

这套拆法非常适合我们当前 ARK 的事务设计思路，因为它与“一级事务/二级子事务/可审计产物”的方向一致。

### 4.2 对 OpenCode 学术模板的借鉴

对 `.opencode/` 侧，最直接的借鉴不是复制原技能文本，而是补出一组面向国内中文文献的专门 skill：

1. 在 `cn-literature-retriever` 下面新增 CNKI 专项子技能，而不是继续把所有中文联网检索都塞进 `cn-web-acquisition`。
2. 把“开放来源补充”和“订阅库检索执行”彻底拆开。
3. 把“期刊级查询”从“论文级检索”中分离出来，形成单独子事务。
4. 把“导出到 Zotero / RIS / GB/T 引用”定义成标准后处理节点，而不是额外手工操作。

建议中的 OpenCode 子事务最小集合：

1. `cnki-search`
2. `cnki-advanced-search`
3. `cnki-paper-detail`
4. `cnki-journal-index`
5. `cnki-journal-toc`
6. `cnki-export`
7. `cnki-download`

其中：

1. `cnki-search`、`cnki-advanced-search` 负责候选发现。
2. `cnki-paper-detail` 负责题录补全。
3. `cnki-journal-index` 负责期刊级别与收录判断。
4. `cnki-journal-toc` 负责按刊期补齐某期全量条目。
5. `cnki-export` 与 `cnki-download` 负责入库前的材料获取。

### 4.3 对 ARK 的借鉴

ARK 不适合直接塞入浏览器页面选择器和站点脚本，但非常适合吸收 `cnki-skills` 的“标准输入输出契约”。

建议 ARK 在检索治理之上补 3 类结构：

1. CNKI 检索候选结果结构
- 字段至少包含：标题、作者、来源期刊、日期、被引、下载量、结果页 URL、详情页 URL、导出 ID、权限状态。

2. CNKI 期刊评价结构
- 字段至少包含：期刊中文名、英文名、ISSN、CN 号、主办单位、出版周期、收录标签、复合影响因子、综合影响因子、刊期目录 URL。

3. CNKI 获取结果结构
- 字段至少包含：是否已登录、是否触发验证码、是否允许下载、下载格式、RIS/GBT 导出状态、受限说明、会话时间戳。

这样一来，OpenCode 技能层负责与站点交互，ARK 只负责：

1. 治理判定
2. 结构化接收
3. 入库路由
4. 下游知识流程衔接

这符合我们当前“ARK 是稳定能力层，`.opencode/skills/*/scripts` 是适配层”的总体方向。

### 4.4 对合规流程的借鉴

`cnki-skills` 明确把下列情况视为必须暂停并等待人工：

1. 滑块验证码
2. 未登录
3. 需要下载权限
4. 新标签页切换后的人工确认

这与我们现有合规原则完全一致，但它比我们更具体。可借鉴之处在于：

1. 把“人工授权闸门”从抽象命令，落成可枚举的页面状态。
2. 把“暂停原因”标准化，写进日志和 bundle。
3. 把“允许继续执行的人工确认点”变成固定节点，而不是自由文本约定。

建议新增的暂停原因枚举：

1. `captcha_required`
2. `login_required`
3. `institution_auth_required`
4. `download_permission_required`

### 4.5 对性能与可维护性的借鉴

`cnki-skills` 的几个设计选择，对我们非常有价值：

1. 单操作尽量压缩为一次脚本执行，而不是多轮截图-点击-等待。
2. 直接导航优于点击链接，减少标签页噪音。
3. 批量导出优于逐篇进入详情页。
4. 每个技能都附带“已验证选择器”和“输出格式”。

这意味着我们后续如果做 OpenCode CNKI 技能，不应只写自然语言说明，而应同步维护：

1. 页面字段协议
2. 输出 JSON 协议
3. 错误状态协议
4. 人工中断协议

## 5. 对其他地方的借鉴

### 5.1 对代理设计的借鉴

`cnki-researcher` 的借鉴点不在“它是一个 agent”，而在它把复杂浏览器操作约束为一个专题代理，避免让上层总调度直接面向页面细节。

这对我们有两个启发：

1. `orchestrator` 不应该直接调站点页面动作，只调专题代理。
2. `cn-literature-retriever` 可以继续作为总代理，但其下应有更专门的“中文订阅库执行能力”，而不是自己承担全部页面协议。

### 5.2 对流程阶段划分的借鉴

`cnki-skills` 实际形成了一条很清晰的链：

1. 搜索
2. 结果解析
3. 详情补全
4. 期刊评价
5. 下载或导出
6. 进入 Zotero 或本地管理

对我们来说，可以映射为：

1. 检索治理
2. 文献候选发现
3. 条目元数据补齐
4. 期刊层质量标注
5. 合规获取
6. 本地导入
7. 知识预筛选
8. 文献阅读

这说明 `cnki-skills` 可以作为我们“国内中文文献子链路”的前半段蓝本，而 ARK 现有 `local_reference_ingestion -> knowledge_prescreen -> literature_reading` 可以接后半段。

### 5.3 对文献管理接口的借鉴

`cnki-export` 支持 RIS、GB/T、Zotero，这对我们不是小功能，而是“研究者真实工作流接口”。

可借鉴之处：

1. 在检索阶段就保留导出所需标识，不等到后面再重新查。
2. 输出既服务机器入库，也服务人工写作引用。
3. 将 Zotero 视为外部协作系统，而不是仅仅视为附件仓库。

这对我方意味着：后续 `references/` 与 `database/references/` 的设计，应该允许保存：

1. 外部文献系统标识
2. 可再导出引用文本
3. 受限全文与公开题录的分离状态

### 5.4 对期刊层知识的借鉴

`cnki-journal-index` 和 `cnki-journal-toc` 提醒我们一个目前的薄弱点：

1. 我们现在更重“文章题录”，较少显式处理“期刊质量与刊期上下文”。
2. 但在中文研究场景中，期刊级别、是否 CSSCI、是否北大核心、某期专题目录，常常本身就是筛选条件。

因此，这部分应进入我们的方法论与证据治理，而不是仅作为附加信息。

### 5.5 对技能文档写法的借鉴

`cnki-skills` 的文档写法很工程化：

1. 明确参数
2. 明确步骤
3. 明确已验证选择器
4. 明确工具调用次数
5. 明确错误条件

这对我们所有高风险、高交互技能都适用，不只适用于 CNKI。后续以下技能都应参考这种写法升级：

1. `cn-subscribed-literature-access`
2. `cn-web-acquisition`
3. `cn-local-library-manager`
4. 与外部系统交互的导出/下载类技能

## 6. 不宜直接照搬的部分

以下内容应明确区分“可借鉴”与“不可直接迁入”：

1. 不能把 Claude 专用的 Chrome DevTools MCP 指令文本直接当成 OpenCode 可执行协议。
2. 不能把站点选择器、页面脚本直接塞进 ARK 核心包。
3. 不能把“CNKI 专项页面自动化”误当成“通用检索治理”的一部分。
4. 不能因为它支持下载，就弱化我们已有的授权、日志、受限目录约束。

正确做法应是：

1. 抄它的能力切片。
2. 抄它的状态协议。
3. 抄它的输入输出结构。
4. 不抄它的运行时绑定方式。

## 7. 综合结论

结论可以直接概括为三句话：

1. `cnki-skills` 对我们最大的借鉴，不是“Claude 技能”，而是“把 CNKI 检索流程拆成了一组可审计、可暂停、可组合的子事务”。
2. 对 OpenCode 学术模板而言，应借鉴它的技能切片、验证码/登录暂停协议、期刊子链路和批量导出设计。
3. 对 ARK 而言，应借鉴它的结构化结果模型与下游衔接字段，而不是把浏览器自动化直接塞进 ARK 本体。

因此，后续最合理的方向不是继续扩写抽象说明，而是把“中文订阅文献检索”从粗粒度规则，推进到“OpenCode 适配层细粒度技能 + ARK 结构化入库契约”的正式实现。
