# paper-AI-Agents任务事务工作流通用原理论著-附录-任务-20260312-001

## 附录 A. v3 最小实践框架

本附录不讨论具体业务场景，而讨论如何把主论著中的理论最小化为可实践框架。v3 的核心原则不是“大而全”，而是“先冻结主协议，再扩展局部能力”。因此，v3 实践框架应遵循以下顺序：

1. 冻结结果码协议。
2. 冻结任务状态机。
3. 冻结结构化决策记录格式。
4. 冻结四类核心数据库。
5. 在此基础上再逐步扩展节点类型、事务类型和多级图能力。

## 附录 B. 结果码协议最小枚举

### B.1 结果码

1. `PASS`
2. `RETRY`
3. `BACKTRACK`
4. `BLOCKED`

### B.2 阻断原因码建议

1. `permission_missing`
2. `dependency_unready`
3. `missing_required_input`
4. `policy_denied`
5. `goal_ambiguous`
6. `human_confirmation_required`
7. `resource_exhausted`

### B.3 阻断作用域建议

1. `affair`
2. `node`
3. `task`

这些枚举的意义在于：v3 不允许每个业务事务随意发明自己的控制协议。业务可以变化，但流程控制协议必须收敛。

## 附录 D. 四类核心数据库的最小职责

### D.1 taskdb

职责：保存任务对象、父子任务关系、当前状态、当前节点位置和恢复依据。

### D.2 logdb

职责：保存原始事件流，不负责裁决，只负责可回放。

### D.3 decisiondb

职责：保存为什么做出某个动作，不负责记录全部执行细节。

### D.4 graph_registry

职责：保存静态图版本、节点类型注册、事务类型注册与容器定义。

## 附录 E. v3 与后续版本的边界

v3 明确不做以下事情：

1. 不做真正并发调度。
2. 不做多级子图运行时。
3. 不做日志全量对内暴露。
4. 不做强化学习辅助裁决。
5. 不把业务数据库收编进 AOK 核心数据库。

这些边界的价值在于防止 v3 被未来愿景拖垮。一个版本若无法清楚说明“自己暂时不做什么”，就很难稳定说明“自己真正做什么”。

## 附录 F. 面向后续版本的理论扩展框架

后续版本若要扩展，可沿以下路径推进：

1. 从单级图推进到多级嵌套图运行时。
2. 从单 PA 强裁决推进到多控制面协同。
3. 从规则系统推进到统计学习和策略推荐。
4. 从只读日志分析推进到受控日志摘要内暴露。
5. 从轻量数据库推进到关系型数据库与查询引擎。

## 附录 G. 附录结论

主论著提供的是一套纯理论骨架，本附录提供的是把这套骨架压缩为 v3 最小实践框架的方式。两者共同说明：任务事务工作流系统的关键，不在于一开始做得多复杂，而在于是否先冻结最重要的协议、状态、裁决与留痕结构。
