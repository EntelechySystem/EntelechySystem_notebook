## 附录 A. 融合系统的最小模块图解说明

一个最小可行的融合系统至少包含以下模块：项目经理 Agent、调度 Skill、任务/事务数据库、文献数据库、知识数据库、检索 Workflow、知识管理 Workflow、分析 Workflow、审计模块和人工闸门接口。项目经理 Agent 读取任务图和研究阶段信息，请求调度 Skill 给出下一事务；调度 Skill 依据边权、阶段模式和审计约束返回可执行动作；执行面调用相应 Workflow；运行结果写回数据库与日志；必要时审计模块输出结果码并交由项目经理 Agent 决定是否继续、回退或阻断。这个最小模块图说明，融合系统不是靠单点智能完成，而是靠多层协同完成。

## 附录 B. 研究对象流转的完整链条

从对象视角看，一项研究至少经历以下几类对象流转：问题草案对象 -> 任务对象 -> 文献/数据检索请求对象 -> 原始材料对象 -> 规范化资产对象 -> 知识对象 -> 分析对象 -> 写作对象 -> 评审对象 -> 修订对象 -> 最终发布对象。每一次流转都意味着对象被重新解释和重新组织。若某一层流转不清晰，后续链条就会出现断裂。例如，没有把原始材料转化为知识对象，分析链就只能直接面对大体量原文；没有把分析对象转化为写作对象，结果就难以组织成论文结构。

## 附录 C. 项目经理 Agent 的决策模板

项目经理 Agent 在科研融合系统中可以围绕几个固定问题做决策：当前最重要的研究任务是什么？该任务当前受什么约束？在当前阶段有哪些候选事务？哪一个候选事务对目标推进收益最大且风险可接受？该事务需要调用哪个 Skill 和 Workflow？执行后若出现 `RETRY/BACKTRACK/BLOCKED`，下一步该如何组织？通过这样的模板，项目经理 Agent 的行为就不再神秘，而具有清晰的管理语义。

## 附录 D. 评审意见到任务拆解的映射模板

一条评审意见进入系统后，可按以下模板处理：

1. 提取意见文本。
2. 分类为文献类、数据类、方法类、结果类、表达类、伦理类或其他。
3. 判断影响层级：局部修改、子链重做、主链回退或问题重构。
4. 生成对应任务：如“补充文献争议条目”“重建变量口径说明”“增加稳健性检验包”“重写引言缺口段落”。
5. 给出优先级与预期完成标志。
6. 回写到任务系统并触发相关事务。

通过这一模板，评审意见才真正进入结构化科研工作流，而不是只存在于回复文档中。

## 附录 E. 审计结果到科研动作的映射模板

治理审计和复现审计的结果不应停留在“通过/不通过”层，而应被映射为具体科研动作。例如：来源授权不通过 -> 进入人工闸门或替代来源检索；元数据缺失 -> 回到规范化入库事务；变量口径冲突 -> 回到数据管理和知识对齐；分析不可复现 -> 回到分析 Workflow 和运行日志校验；论证不一致 -> 回到写作链与知识链。只有这种映射存在，审计才能真正改变路径，而不是事后批评。

## 附录 F. 团队协作下的融合收益

在团队研究中，融合框架的收益更加明显。首先，任务系统减少了“谁在做什么”的信息不透明。其次，数据库和日志减少了跨成员交接时的口头损耗。再次，知识管理减少了不同成员分别重复整理同一批材料的低效。最后，评审响应任务化使返修阶段的多人协作更容易被管理。团队级科研一旦缺少结构化工作流，很快就会陷入文件版本冲突和责任边界模糊；而融合框架恰恰在这些方面提供了明确支撑。

## 附录 G. 个人研究者的融合收益

对于个人研究者而言，融合框架同样意义重大。它可以显著降低长期项目中的认知负担，使研究者不再完全依赖记忆维持进度；它还能把个人形成的文献理解、变量经验和评审模式沉淀为稳定知识资产，避免每个新项目都从零开始。此外，个人研究者往往更容易在多项目并行时混淆上下文，任务系统与知识系统的结合能帮助其更清楚地区分不同项目的对象和阶段。

## 附录 H. 融合框架的保守使用原则

虽然融合框架潜力很大，但使用时仍应保持若干保守原则。第一，不要让自动化绕过合规和伦理边界。第二，不要为了“全部纳入系统”而在早期过度工程化。第三，不要把所有知识都当成稳定资产，应允许候选状态和冲突状态存在。第四，不要让 Agent 承担本应由数据库和 Workflow 稳定承接的动作。第五，不要忽视人工总结和系统复盘，因为那是系统长期演化的重要来源。

## 附录 I. 附录结论

本附录进一步展示，融合框架并不是抽象论证，而是可以被拆解为模块、对象、模板、映射和使用原则的一整套结构。正文负责论证“为什么要融合”，附录负责说明“融合后系统长什么样、如何工作、如何被安全使用”。两者结合，才能真正形成较完整的论著形态。
