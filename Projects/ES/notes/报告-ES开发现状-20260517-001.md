# ES 当前开发情况梳理报告

## 1. 报告目的

这份报告用于在长时间中断之后，快速恢复对 ES（EntelechySystem）项目当前状态的整体认知。重点不是回顾全部历史，而是回答四个问题：

- 这个项目现在到底是什么形态；
- 目前已经稳定存在的开发基线是什么；
- 你上次离开时实际开发停在了哪里；
- 如果现在重新接手，最短的恢复路径是什么。

## 2. 当前总体判断

截至 2026-05-17，ES 的当前状态可以概括为：

ES 已经具备一个可运行的最小 Python 实验框架，但整体仍处于“研究型工程 + 多方向探索并行推进”的阶段，还没有收敛成单一、稳定、统一的产品化架构。

项目中目前最明确、最稳定的主线，是“实验脚本 + 配置 + Python 模拟器”的运行链路；最明显但尚未收口的探索方向，是 Virtual2DMiniNursery 这类世界环境/AWS 方向，尤其是 js/ts 前端环境与 Python 主体之间的联通问题。

从仓库状态看，这个项目不是“完全停滞”，而是停在一个中间态：文档在 2026-02 做过一次系统补齐，本地工作区则保留着尚未提交的依赖整理和入口修正改动。

## 3. 当前已经成型的开发基线

### 3.1 项目定位

ES 被定义为一个面向通用人工智能探索的多子系统工程。根目录 README 将项目描述为同时覆盖宏观世界交互尺度、中观智能体认知尺度、微观运作机制尺度的系统，并给出四个子系统方向：

- 复杂智能体系统；
- 基本概念系统；
- 生命周期管理系统；
- 多智能体世界系统。

这说明 ES 目前不是一个单一任务程序，而是一个总项目容器，里面既有运行代码，也有理论设想、实验环境、系统库、工作区资产和笔记化延伸内容。

### 3.2 工程运行基线

当前真正可落地的工程主线，是 Python 侧的实验驱动模拟框架。

它的核心结构是：

- `EntelechySystem_python/Experiments/EXP_test_010.py` 作为示例实验入口；
- `EntelechySystem_python/simulator.py` 作为模拟器入口；
- `EntelechySystem_python/Libraries/ConfigsLibrary/config_test` 或 `workstage/config/` 作为配置来源；
- `EntelechySystem_python/Libraries/` 作为系统、模型、世界环境等组件库；
- 输出目录中保存日志和 `gb.pkl` 形式的全局配置快照。

从现有实现来看，这条主线已经不是概念层面的草图，而是一个明确可执行的结构：

1. 实验脚本构造 `config` 字典；
2. 模拟器决定是读取 `config.py` 还是 `config.pkl`；
3. 全局变量 `gb` 被填充；
4. 自动创建实验输出目录；
5. 导出一次运行的配置快照；
6. 根据配置开关决定是否继续进入实验组模拟程序。

这意味着，如果你现在要重新进入项目，最可信的切入点仍然不是某个概念文档，而是这条“实验入口到模拟器”的最小运行链路。

### 3.3 技术栈基线

当前 Python 运行侧的约束相对明确：

- Python 版本要求为 `>=3.12`；
- `pyproject.toml` 中已经声明了 `numpy`、`pandas`、`pygame`、`pettingzoo`、`gymnasium`、`torch` 等依赖；
- 当前本地未提交改动还额外加入了 `pandas-stubs`，说明你已经开始朝类型检查或编辑器补全质量提升的方向走。

需要注意的是，文档仍多次把 `requirements.txt` 作为主要安装入口，但当前工作区中该文件已处于删除状态，说明依赖管理正在从旧的 requirements 方式转向 `pyproject.toml` / `uv.lock`，但迁移还没有完全收口。

换句话说，你不是停在一个“已经完全稳定”的版本上，而是停在一个“正在把工程状态从历史堆叠推进到更规范结构”的中间态上。

## 5. 当前最重要的开发方向

### 5.1 已经明确的主线：Python 实验框架

这一条线已经具备最小闭环：

- 有实验入口；
- 有模拟器；
- 有配置体系；
- 有输出目录和配置快照；
- 有用户手册、开发者指南和需求文档。

这条线的价值是：它是目前最适合继续推进的“工程基座”。

### 5.2 仍在探索中的主线：Virtual2DMiniNursery / AWS 世界环境

ES_notebook 中的项目笔记显示，Virtual2DMiniNursery 的构想非常明确：

- 一个婴儿智能体；
- 一个教育者；
- 一个 2D 或 3D 场景；
- 简化视觉和听觉，用文本标签和文本消息代替复杂感知；
- 通过动作、观察和状态变化驱动环境交互。

对应到代码仓库，`EntelechySystem_python/Libraries/WorldLibrary/Virtual2DMiniNurseryEnv_js/` 已经不是空壳目录，而是存在：

- `package.json`；
- `pnpm-lock.yaml`；
- `p5`、`phaser`、`bitecs` 相关依赖；
- 多种前端环境实现文件；
- 若干静态资源。

这表明你的探索并不只是“想法”，而是已经进入了实际环境原型实现阶段。

但从文档与代码中的表述看，这条线目前仍缺一个真正收口的工程答案：

如何把 js/ts 侧世界环境与 Python 侧算法/模拟器稳定联通起来。

文档里已经明确提出了 WebSocket、HTTP、gRPC 等桥接思路，但还更像路线图而不是已经交付的成品能力。

### 5.3 结构性重构方向：ECS / Unit 节点统一

需求文档和开发者指南都写到了一个很重要的下一阶段任务：

把当前散落的 Unit 节点操作，统一替换为更清晰的 ECS 风格工具包接口。

这说明你当时已经意识到：

- 现有工程可以运行，但内部抽象并不统一；
- 节点/实体/状态相关操作可能散落在多个模块；
- 如果继续叠加功能而不先收敛接口，后面会越来越难维护。

因此，ECS 统一并不是附属优化，而是未来要不要继续扩大项目规模的结构性关口。

## 6. 当前暴露出的几个真实问题

### 6.1 文档与当前依赖状态不完全一致

开发者指南和用户手册仍在指导使用 `requirements.txt` 安装依赖，但本地工作区里该文件已删除。这意味着：

- 文档描述的是旧基线；
- 工作区正在向新依赖治理方式迁移；
- 迁移尚未在文档层完全同步完成。

如果你现在直接照文档执行，可能会遇到“文档写有这个文件，但现场已经没有”的认知断裂。

### 6.2 代码主线可运行，但存在历史演化痕迹

`simulator.py` 中保留了大量注释掉的逻辑和阶段性备注，例如：

- 配置程序预运行逻辑；
- 各类资源复制到输出目录的流程；
- 世界环境导入处有“这里一导入就会直接运行到卡死”的备注。

这说明当前代码不是“简洁的新架构”，而是“历史逻辑仍在、主链能跑、但内部尚未完全重整”的状态。

### 6.3 当前文档里混入了一部分未来规划

需求文档和开发者指南中除了描述现状，也混入了大量下一阶段建议，例如：

- ECS 接口统一；
- js/ts 与 Python 桥接；
- 容器化部署；
- gRPC 通道。

这些内容很有价值，但也会带来一个问题：

当你久未接触项目回来再看时，容易把“已经完成的现状”和“当时计划要做的下一步”混在一起。

因此，重新上手时必须有意识地区分：

- 哪些是已经存在的；
- 哪些只是写进文档的开发意图。

## 7. 你离开这个项目时，实际上停在什么位置

综合代码仓库、文档、项目笔记和本地未提交改动，可以比较准确地判断：

你离开这个项目时，并不是停在“从零开始搭框架”的阶段，而是停在下面这个位置：

一个最小可运行的 Python 实验主链已经搭起来了；文档也已经补齐到足以帮助重新上手；但更大的目标，比如世界环境联通、ECS 统一、前后端桥接、目录结构重建，还都处在“已经识别问题并启动探索，但还没有统一交付”的阶段。

如果换成更直白的话说：

你已经把 ES 从“纯构想项目”推进成了“能运行、能继续开发、但还没有架构收口的研究型工程”。

## 8. 现在重新接手的最短路径

如果你现在要恢复开发，不建议一开始就重新理解全部理论、全部子系统和全部历史笔记。最短路径应当是下面这个顺序。

### 8.1 先确认现场状态，而不是先读概念

第一步应该先确认当前工作区到底以什么为准：

- 本地未提交改动是否保留；
- 依赖安装方式是否已经转向 `uv`；
- `EXP_test_010.py` 入口是否以相对导入版本为准；
- `requirements.txt` 删除是否是你的最终决定。

如果这一步不先确认，后面无论读多少文档，都会停留在半旧半新的状态里。

### 8.2 再验证最小运行链路

优先只验证一件事：

`EXP_test_010.py` 是否还能在当前环境中跑通到生成输出目录和 `gb.pkl`。

只要这条链路能跑通，你就重新拿回了对项目的工程控制权。

### 8.3 然后在两条开发线里二选一

恢复之后不要同时抓所有方向，建议先选一条：

- 方向 A：收敛 Python 主链，清理依赖、配置、导入与文档一致性；
- 方向 B：继续推进 Virtual2DMiniNursery/AWS 环境，把前端环境与 Python 桥接做成真正可跑的 demo。

如果两条同时做，会再次回到“概念很多、落点分散”的状态。

## 9. 最终结论

ES 当前不是一个陌生到需要从零重建认知的项目，而是一个已经有明确基座、但主攻方向还没有最终收敛的研究型工程。

你现在最应该记住的不是所有宏大设想，而是以下四点：

1. ES 当前最稳的东西，是 Python 侧的实验脚本驱动模拟框架；
2. 你当时最有实际推进痕迹的功能方向，是 Virtual2DMiniNursery 这一类世界环境原型；
3. 你已经意识到项目的下一个结构性问题，是 ECS 统一和跨语言桥接；
4. 当前最大的阻碍不是“没有东西”，而是“现场状态、文档状态和未来规划混在一起，需要重新分层”。

因此，重新接手 ES 的正确方式，不是先大范围思考理论，而是先夺回对当前工程现场的判断权：先确认未提交改动，再验证最小运行链路，再决定下一阶段只推进哪一条主线。
