# ARK与AOK分层日志治理落地计划-计划-20260310-001

## 1. 任务背景与目标

基于 `think-ARK与AOK技术承接分层决策-20260310-001.md` 与本轮讨论结论，当前需要把 AOK 的技术分层进一步落地到日志治理与回放体系。

本计划按 AOK 工程直接执行口径编写，作为 AOK 日志治理开发基线。

本任务目标：

1. 明确日志治理分层边界（谁负责记录、谁负责管理、谁负责审计）。
2. 形成统一日志方案：`JSONL` 事件正文 + `CSV` 元数据索引。
3. 形成可执行的分阶段实施计划，覆盖设计、开发、验证、回滚。

## 2. 可行性分析

### 2.1 现状基础

当前仓库已具备可复用能力：

1. 事务执行层：`autodokit/affairs/`、`autodokit/flow_graph/`、`autodokit/scheduling/`。
2. 工具与任务数据库层：`autodokit/tools/`、`autodokit/taskdb/`。
3. 工作流与配置入口：`workflows/`、`config/`、`autodokit/main.py`、`autodokit/api.py`。
4. 文档体系与规范体系已成型，可直接承载日志 schema 与实施文档。

### 2.2 主要问题

1. 事件日志写入点分散，未形成统一写入接口。
2. `execution_runs.jsonl` 回放链路存在，但稳定落库链路尚未全覆盖。
3. 人工可读日志（Markdown）与结构化日志（JSONL）存在重复与漂移风险。
4. 缺少统一索引层，跨任务/事务检索效率不足。

### 2.3 结论

方案可行，且建议采用“双层日志架构”：

1. 事件事实源：`JSONL`（统一 schema，按事件追加）。
2. 检索索引层：`CSV`（只存元数据与定位信息，不存完整正文）。

不建议“一条日志一个 JSON 文件”，避免文件数量爆炸与回放性能下降。

## 3. 方案决策

### 3.1 分层责任

1. AOK（技术层）承接：日志基础设施（统一写入器、索引器、schema 校验、导出）。
2. 领域层（业务事务包）承接：语义事件定义（审计、事务状态、证据链字段）。
3. 编排层（命令/runner）承接：触发时机约束与每步留痕监督。

### 3.2 组件设计

新增两个核心能力：

1. `LogWriter`：统一写入 `JSONL`，负责 schema 校验、脱敏、UID 生成、原子追加。
2. `LogIndexer`：从 `JSONL` 提取元数据，追加写入 `CSV` 索引库。

建议目录：

1. `logs/run/events/YYYY-MM-DD.jsonl`（事实源）。
2. `database/logs/log_index.csv`（索引库）。
3. `database/logs/log_schema_version.json`（schema 版本与迁移信息）。

建议代码落点：

1. `autodokit/tools/logging/log_writer.py`
2. `autodokit/tools/logging/log_indexer.py`
3. `autodokit/tools/logging/schema.py`
4. `autodokit/tools/logging/__init__.py`

### 3.3 统一字段（首版）

事件正文字段（JSONL）建议最小集合：

1. `event_uid`
2. `run_uid`
3. `timestamp`
4. `phase`（`task|transaction`）
5. `state`（`start|end|fail|retry|backtrack|blocked|audit`）
6. `task_uid`
7. `transaction_uid`
8. `agent`
9. `skill`
10. `provider`
11. `model`
12. `status`
13. `artifacts`
14. `metadata`
15. `content`
16. `schema_version`

索引字段（CSV）建议集合：

1. `event_uid`
2. `timestamp`
3. `run_uid`
4. `task_uid`
5. `transaction_uid`
6. `agent`
7. `skill`
8. `phase`
9. `state`
10. `status`
11. `provider`
12. `model`
13. `severity`
14. `jsonl_file`
15. `line_no`

## 4. 分阶段实施计划

### P0 规范冻结（1-2 天）

1. 冻结 JSONL/CSV 字段与枚举字典。
2. 冻结日志路径规范与命名规范。
3. 冻结脱敏规则与禁写字段（如 API Key）。

验收：

1. 形成 `日志 schema v1` 文档。
2. 形成 `日志字段字典` 与 `状态枚举字典`。

### P1 基础能力落地（2-4 天）

1. 实现 `LogWriter`。
2. 实现 `LogIndexer`。
3. 增加统一调用入口（避免各事务直接写文件）。
4. 增加最小验证命令（用于快速验证写入与索引行为）。

验收：

1. 单元级写入验证通过。
2. 脱敏规则验证通过。

### P2 接入关键链路（3-5 天）

优先接入：

1. 调度与事务执行主链路（`autodokit/scheduling/*` + 事务 runner）。
2. 高频事务入口（`autodokit/affairs/` 中主链事务）。
3. 任务状态持久化链路（`autodokit/taskdb/*`）。
4. 工作流执行入口（`autodokit/main.py`、`autodokit/api.py`）。

验收：

1. 事务开始与结束均产生日志。
2. 关键失败/重试/阻断事件可追踪。

### P3 回放与一致性验证（2-3 天）

1. 让 taskdb 回放入口优先消费统一事件流或与之对齐。
2. 校验 `JSONL` 事实源与 `CSV` 索引一致性。
3. 校验运行日志与结构化日志关键字段一致性。

验收：

1. 回放结果一致率 >= 99%。
2. 关键字段缺失率 <= 1%。

### P4 灰度与回滚（持续）

1. 按事务白名单灰度接入。
2. 保留旧日志路径兼容读取能力与导入转换脚本。
3. 出现字段断裂或回放失败时按开关回滚。

验收：

1. 不影响现有 CLI 可用性。
2. 回滚耗时可控（目标 < 30 分钟）。

## 6. 风险与控制

主要风险：

1. 事件 schema 频繁变化导致下游回放脚本不稳定。
2. 业务代码绕开统一 logger 直接写日志，造成数据漂移。
3. 索引构建失败导致检索可用性下降。

控制措施：

1. 引入 `schema_version` 与迁移策略。
2. 代码评审中禁止直接写日志文件，统一走 `LogWriter`。
3. 索引构建失败不阻断主流程，但必须写审计告警。
