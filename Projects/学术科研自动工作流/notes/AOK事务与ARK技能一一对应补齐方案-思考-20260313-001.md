# AOK事务与ARK技能一一对应补齐方案-思考-20260313-001

## 1. 需求分析和目标分析

### 1.1 需求重述

本轮思考的目标不是直接补代码，而是先明确一套可执行的承接方案，使三层对象形成稳定的一一对应关系：

1. 上游能力目录以 `.opencode/skills/` 为准。
2. `academicresearch_kit/skills/` 中每一个 ARK 技能脚本，都只做一件事：直接调用 AOK 中唯一对应的一个事务。
3. `autodokit/affairs/` 中每一个被纳入 opencode 技能目录的事务，都有唯一对应的 ARK 技能脚本。

换言之，本次要建立的是“技能目录驱动”的双向约束，而不是继续允许 ARK 与 AOK 各自长出相近但不等价的实现。

### 1.2 当前现状

基于当前仓库清单，可以得到以下事实：

1. opencode 技能目录当前共有 43 个技能。
2. ARK 当前已有 27 个 Python 技能模块，但其中 `cnki_bridge.py` 聚合了承接多个 CNKI 技能，而不是一技能一脚本。
3. AOK 当前已经有一批中文事务目录，部分与 opencode 技能能直接对上，部分只是“近似能力”，还有一批完全缺失。
4. AOK 已经存在统一事务执行入口 `autodokit.run_affair(...)`，这意味着“ARK 只做薄桥接”在技术上是可行的。
5. ARK 当前只存在 `aok_runtime_proxy` 的工具代理，还没有“统一调用 AOK 事务”的专用桥接层，因此 ARK 技能尚未全面转成 AOK 事务前端。

### 1.3 现有差异类型

当前差异不是一种，而是至少有五种：

1. 已有 ARK 技能，也已有 AOK 近似事务，但两边尚未明确绑定为唯一配对。
2. ARK 有脚本，但 AOK 缺少对应事务。
3. AOK 有近似事务，但 ARK 缺少对应技能脚本。
4. 多个 opencode 技能被 ARK 或 AOK 聚合进一个总线模块，例如 CNKI 系列。
5. 某些能力在 AOK 中是“内部支撑事务”，不应该强制暴露为 ARK 技能。

### 1.4 可行性判断

该目标可行，而且适合分阶段推进，原因如下：

1. opencode 技能目录已经给出了上游能力边界，适合作为唯一盘点基准。
2. AOK 已经有事务注册、事务校验、事务执行入口，不需要从零新造运行时。
3. ARK 的技能层可以收缩为薄包装层，改造成本可控。
4. 多技能复用同一内部实现并不矛盾，只要外部契约保持“一技能一事务一入口”即可。

### 1.5 主要挑战

主要挑战有四个：

1. AOK 当前运行时 `affair_uid` 默认等于事务目录名，而现有目录名基本是中文，和 opencode 英文技能名不是同一套契约。
2. CNKI、审稿、写作三类能力存在“总线式聚合”，必须拆成外部一一对应、内部允许复用的结构。
3. 不是所有 AOK 事务都应进入 ARK 技能层，例如图节点、文档维护、任务文档归档等内部事务，不应被错误纳入“一一对应”。
4. 如果不建立自动校验，后续新增技能时很容易再次发生 ARK、AOK、opencode 三侧漂移。

### 1.6 范围边界

本方案只在“opencode 技能目录覆盖的能力”内建立一一对应，不做以下事情：

1. 不要求所有 AOK 图节点事务都暴露为 ARK 技能。
2. 不要求所有文档维护事务都进入 ARK 技能目录。
3. 不在本轮思考中扩展新的业务域，只处理现有 opencode 技能清单的补齐问题。

## 2. 决策和计划

### 2.1 总体决策

本轮建议采用以下四条核心决策：

1. 以 opencode 技能名作为上游能力清单的唯一基准。
2. ARK 技能脚本一律降级为“薄桥接层”，不再承载业务实现。
3. AOK 事务成为业务实现的唯一事实来源。
4. 对外必须做到“一技能一事务一桥接入口”，对内允许多个事务复用同一个共享 helper。

### 2.2 统一契约设计

建议建立统一的三层契约：

1. `skill_id`：使用 opencode 原始技能名，例如 `workspace-sanity-check`。
2. `ark_module`：使用 Python 文件名规范，例如 `workspace_sanity_check.py`。
3. `aok_affair_uid`：建议新增显式字段承接 `skill_id`，不要再依赖中文目录名隐式映射。

推荐规则如下：

1. AOK 事务的中文目录名保留为人工可读名称，但事务运行时应新增显式 `skill_id` 或等价字段作为外部契约。
2. ARK 统一通过一个共享桥接 helper 调用 `autodokit.run_affair(...)`。
3. ARK 技能脚本只负责三件事：输入预处理、调用 AOK 事务、输出结果规范化。
4. 所有路径字段继续遵循 AOK 现有规则，统一先在 tools 层转为绝对路径，再交给事务执行。
5. 对外公开配置仍以 `workspace_root` 为根，不重新引入新的工作区根契约。

### 2.3 建议的 ARK 技能脚本形态

每个 ARK 技能脚本应统一成如下职责：

1. 接收 Python 友好的函数参数。
2. 组装为 AOK `config` 字典。
3. 调用统一桥接函数，例如 `run_aok_affair_skill(skill_id=..., config=...)`。
4. 返回统一结构，例如：`status`、`mode`、`affair_uid`、`result`、`artifacts`。

不建议继续在各个 ARK skill 文件中保留独立 engine 逻辑，否则“一一对应”会退化成“名称对应，行为分叉”。

### 2.4 建议的 AOK 事务补齐原则

每个纳入映射的 AOK 事务应满足以下要求：

1. 一个事务目录只承接一个 opencode `skill_id`。
2. `affair.json` 中显式声明该技能对应关系。
3. `affair.py` 成为唯一业务执行实现。
4. `affair.md` 只描述该事务，不再混合多个技能。
5. 对外输出尽量稳定，方便 ARK 直接透传或轻度包装。

### 2.6 分批实施计划

建议按四批推进，并以小时为估算单位。

#### 第一批：建立桥接骨架与自动校验，预估 2 至 4 小时

目标：先把“以后不能再漂移”的基础设施立住。

1. 在 ARK 新增统一桥接 helper，例如 `run_aok_affair_skill(...)`。
2. 在 AOK 事务清单中新增显式的 `skill_id` 或等价字段。
3. 新增一致性校验脚本，自动比对三侧清单：`.opencode/skills`、`academicresearch_kit/skills`、`autodokit/affairs`。
4. 输出覆盖率报告：已映射、缺脚本、缺事务、聚合未拆分。

#### 第二批：把已可直接对应的能力改造成薄桥接，预估 4 至 6 小时

目标：优先清理最容易落地的一批能力。

推荐先处理：

1. `workspace-sanity-check`
2. `project-bootstrap`
3. `retrieval-governance`
4. `local-reference-ingestion`
5. `knowledge-prescreen`
6. `method-whitelist-selection`
7. `variable-operationalization`
8. `econometrics-runtime-setup`
9. `did-rdd-pipeline`
10. `empirical-four-pack`
11. `paper-draft`
12. `revision-response`
13. `integrity-check`
14. `rag-evidence-synthesis`

#### 第三批：拆分聚合能力，预估 6 至 10 小时

目标：把“一个总线承接多个技能”的问题拆开。

优先拆分：

1. CNKI 十项技能。
2. `review-response` 与 `revision-response`。
3. `paper-draft` 与 `ml-paper-writing`。
4. `literature-reading` 与 `single-paper-reading` 的边界。

这里的关键不是内部代码一定完全分开，而是外部必须一技能一入口一事务。

#### 第四批：补齐缺失能力，预估 8 至 12 小时

目标：把剩余未承接的技能补到闭环。

优先补齐：

1. `citation-verification`
2. `research-ideation`
3. `results-analysis`
4. `paper-self-review`
5. `aliyun-bailian-sdk-bootstrap`
6. `api-data-fetch`
7. `cn-local-library-manager`
8. `cn-subscribed-literature-access`
9. `cn-web-acquisition`

12. `taskdb-bootstrap`
13. `taskdb-validate`
14. `taskdb-replay`
15. `whitelist-governance-check`
16. `ark-workflow-executor`

### 2.7 验收标准

完成后应满足以下验收条件：

1. `.opencode/skills/` 中 43 个技能全部有唯一 ARK 技能入口。
2. 43 个技能全部有唯一 AOK 事务承接。
3. 每个 ARK 技能脚本都能通过统一 helper 调用 AOK 事务，而不是自带业务实现。
4. 一致性校验脚本输出零缺口、零重复映射、零聚合未拆分项。
5. 关键 smoke test 能验证 ARK 调用后确实落到 AOK 事务，而不是走 ARK 私有实现。

## 3. 任务分配

以下任务建议交给任务运作智能体实施。

### 3.1 任务包 A：建立桥接契约与校验器

交付目标：建立“三侧一致性”治理底座。

1. 在 ARK 新增统一 AOK 事务桥接 helper。
2. 在 AOK 事务元数据中加入 `skill_id` 对应信息。
3. 新增盘点脚本，自动生成映射报告。
4. 为该盘点脚本补最小测试。

预期结果：以后任何新增 skill 或 affair，只要不一致就能立即暴露。

### 3.2 任务包 B：改造现有可直连技能

交付目标：把现有已具备 AOK 事务基础的 ARK 技能改造成真正的薄桥接。

1. 批量改造 ARK 技能文件。
2. 删除或下沉这些技能中的重复业务逻辑。
3. 增加 smoke test，验证调用链确实落到 `autodokit.run_affair(...)`。

预期结果：第一批可直连技能全部改为 AOK 前端，而不是双实现。

### 3.3 任务包 C：拆分聚合能力

交付目标：解决 CNKI、审稿、写作这三组最容易漂移的聚合问题。

1. 为 CNKI 十项技能补独立 ARK 脚本与独立事务入口。
2. 拆分 `review-response` 与 `revision-response`。
3. 拆分 `paper-draft` 与 `ml-paper-writing`。
4. 明确 `literature-reading` 的主事务边界。

预期结果：聚合能力在外部全部恢复到一一对应。

### 3.4 任务包 D：补齐剩余缺失事务与技能脚本

交付目标：清零缺口。

1. 为缺失技能新增 ARK 脚本。
2. 为缺失技能新增 AOK 事务目录、`affair.json`、`affair.py`、`affair.md`。
3. 补全注册与测试。

预期结果：43 个 opencode 技能全部承接完成。

### 3.5 任务包 E：文档与回归

交付目标：把映射关系固化为可维护资产。

1. 更新 ARK 技能 README。
2. 更新 AOK 事务手册或开发者指南中的映射说明。
3. 输出最终映射表与回归结果。

预期结果：后续维护者可以按文档继续扩展，而不是重新猜映射关系。

## 4. 监控和调整

### 4.1 监控指标

建议在实施过程中持续跟踪以下指标：

1. `opencode_skill_count`：应固定为 43，作为基准分母。
2. `ark_bridge_coverage`：已有 ARK 薄桥接的技能数量。
3. `aok_affair_coverage`：已有唯一 AOK 事务承接的技能数量。
4. `ambiguous_mapping_count`：一技能多事务或一事务多技能的数量，应收敛为 0。
5. `private_logic_in_ark_count`：ARK 技能中仍保留业务实现的数量，应收敛为 0。

### 4.2 调整策略

实施过程中如果遇到以下情况，建议这样调整：

1. 如果某个中文事务很难直接映射到单一技能，不要先改 ARK，先拆 AOK 事务边界。
2. 如果某组技能高度同构，例如 CNKI 系列，可以内部共享 helper，但外部入口不能继续合并。
3. 如果某个 ARK skill 已经形成稳定调用面，但 AOK 暂时缺事务，可先补 AOK 事务，再把 ARK 改成直调，避免反向兼容层越积越多。
4. 如果发现某个 AOK 事务本质是内部支撑能力，不属于 opencode 技能目录，就把它明确标注为 internal，不纳入一一对应考核。

### 4.3 风险控制点

有三个风险点需要重点看住：

1. 不要把 “同名” 误当成 “同契约”，尤其是 `review-response`、`revision-response`、`ml-paper-writing` 这几类近义项。
2. 不要在 ARK 技能层继续增加业务逻辑，否则补齐完成后仍然会形成双实现。
3. 不要把 AOK 图节点事务和业务技能事务混在同一张映射表里，否则一一对应关系会被内部节点噪音污染。

### 4.4 最终建议

本轮最优实施顺序不是“先盲目补文件”，而是：

1. 先确定统一 `skill_id -> ARK 脚本 -> AOK 事务` 契约。
2. 再把已经能直接对上的能力全部改成薄桥接。
3. 然后拆 CNKI、审稿、写作三组聚合能力。
4. 最后补齐剩余缺失项并加自动校验。

这样做的好处是，补齐工作不会越补越乱，而是越补越收敛。
