# Zotero附件关系设计与ARK内容主库差异-分析-20260412-001

## 1. 问题背景

当前 A020 与 A040 已经进入同一条文献附件治理主链：离线导入、本地复制、在线下载、后续补件，最终都需要回到同一个 content.db。这个背景下，附件关系设计不能只从“参考文献管理软件如何组织单用户资料库”来判断，而要从“自动化工作流如何管理可追溯文献资产”来判断。

因此，Zotero 的附件模型可以作为重要参照，但不能直接照搬。

## 2. Zotero 为什么天然更偏 1:n

Zotero 的核心对象是 item，而不是 workflow 中的资产事实层。它的第一原则是让用户围绕一条题录记录编辑、浏览、同步和导出资料，所以附件通常作为某个父条目的子对象存在。这会自然导向偏 1:n 的关系表达。

Zotero 偏 1:n 的原因主要有 4 个：

1. 交互中心是单条题录。用户在界面里看到的是“一篇文献带若干附件”，而不是“一个附件可能被多篇文献共用”。
2. 同步与冲突处理要尽量简单。把附件视作父条目的附属对象，更容易做增删改、同步和版本冲突判断。
3. 导出语义更贴近书目管理。多数导出场景关心的是“这条文献带了哪些 PDF/网页快照/笔记”，而不是附件实体本身的复用网络。
4. 人工维护优先于自动治理。Zotero 默认假设用户会在图形界面里修条目、拖附件、手动去重，所以附件级实体规范化不是第一目标。

从产品立场看，这个设计没有问题。它服务的是“以单条文献为中心的个人资料管理”。

## 3. 为什么 ARK 内容主库更适合 n:n

ARK 的 content.db 不是个人参考文献软件的对象树，而是事务工作流的事实层。它需要同时承载离线导入、在线补检、补件、去重、解析、阅读状态推进和审计回溯。这个目标决定了附件不能只作为某一条文献的子挂件。

ARK 采用 n:n 更合理，至少有 6 个原因：

1. 同一个二进制文件可能被多个文献对象引用。最常见场景是重复题录、占位条目与正式条目合并前后的共用附件。
2. 同一篇文献可能有多个附件。除了 PDF/CAJ 正文，还可能有补充材料、网页存档、翻译稿、结构化副产物、封面页等。
3. 附件需要独立去重。工作流关心的是“这份文件是否已经存在、是否已经下载、是否已经解析”，这天然是附件实体问题，不只是文献子字段问题。
4. 来源审计需要落在附件级。A020 的离线复制、A040 的在线下载、后续人工补件，本质上是不同来源事件，应该能在附件级被区分。
5. 物理命名必须稳定。若磁盘文件名依赖 cite_key 或 first_author，一旦元数据被修复，文件路径就会抖动；改用稳定附件 UID 派生基名，才能把磁盘稳定锚点和题录元数据解耦。
6. 自动化事务需要可回放。任务系统要回答“这个附件何时入库、由哪个事务写入、当前挂在哪些文献上”，这要求附件是可独立审计的实体。

因此，ARK 更适合把附件拆成两层：

1. attachments：附件实体事实。
2. literature_attachment_links：文献与附件的关系边。

## 4. 这不是简单的“Zotero 错、ARK 对”

两者针对的问题域不同。

Zotero 优化的是：

1. 个人资料整理。
2. 图形界面可操作性。
3. 书目管理软件的同步与导出稳定性。

ARK 优化的是：

1. 自动化工作流中的资产治理。
2. 附件去重、补件、复用与来源审计。
3. 多事务连续运行时的可追溯性。

如果把 Zotero 的 item-child 附件树强行塞进 ARK，短期会看起来更直观，但长期会带来 4 类问题：

1. 同一附件被多文献复用时难以表达真实关系。
2. 在线下载和离线导入容易形成两套附件口径。
3. 文件物理路径会被题录元数据牵着走，导致反复重命名。
4. 审计时只能回答“某文献下面挂了什么”，难以回答“某附件作为资产经历了什么”。

## 5. 本次 A020 与 A040 改造体现出的设计结论

这轮改造实际上把上述理论选择落到了可运行规则上：

1. A020 与 A040 共用同一套附件事实层，不再各写各的附件治理逻辑。
2. 主附件物理命名切到稳定 uid_attachment，不再用 cite_key 当文件名。
3. 未命中的孤儿附件隔离到 unmatched_attachments，而不是继续混入正式附件目录。
4. 在线下载文件必须正式登记到 attachments 和 literature_attachment_links，而不是只把 PDF 放进文件夹。
5. authors 实体侧新增 `标准作者名`、`作者类型`、`作者质量标记`，说明题录治理也在向“实体事实层 + 关系层 + 质量层”演进，而不是只保留一个扁平作者字符串。

这里最关键的设计取向是：

附件文件本身应该围绕稳定实体治理；cite_key 只负责学术引用和知识回链，不负责磁盘真相。

## 6. 对内容管理理论部分的启发

如果把 ARK 的内容主库理解为一个学术工作流型 CMS，那么这次差异说明了一个重要原则：

当系统目标从“人工资料管理”转向“自动化资产治理”时，数据建模重心会从对象树转向事实层与关系层分离。

这意味着文献管理系统至少应分 3 层理解：

1. 文献事实层：文献对象、作者实体、标签实体、附件实体。
2. 关系层：文献-作者、文献-标签、文献-附件、知识-文献等边。
3. 审计与状态层：来源事务、质量标记、阅读阶段、解析状态、人工复核状态。

Zotero 更强在第一层的“对象组织”和用户交互；ARK 更强在第二层、第三层的自动化推进与审计收口。

如果以后要把两类系统协同，而不是互相替代，更合理的思路应该是：

1. 把 Zotero 当成人工协作与题录维护前端。
2. 把 ARK content.db 当成自动化事务运行时的事实主库。
3. 同步时以稳定 UID、来源字段和关系边为中心，而不是以磁盘文件名为中心。

## 7. 当前结论

当前项目不应改成 Zotero 式的单纯 1:n 附件子对象模型。

更合理的结论是：

1. 参考 Zotero 的交互经验，但不照搬其底层关系假设。
2. 保持 ARK 的 `attachments + literature_attachment_links` 作为附件真相源。
3. 继续把 `literature_attachments` 仅当作迁移期兼容投影，而不是重新扶正为主契约。
4. 以后若要接 Zotero，同步层应做关系映射，不应反向削弱 ARK 的附件实体治理能力。
