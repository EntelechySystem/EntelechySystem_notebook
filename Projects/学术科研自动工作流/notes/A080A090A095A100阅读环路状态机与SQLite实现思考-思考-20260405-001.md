# A080A090A095A100阅读环路状态机与SQLite实现思考-思考-20260405-001

## 一、问题定义

当前要讨论的是一个带环路的普通文献阅读主链：A080、A090、A095、A100。

从人的理解方式看，这条链天然适合被理解为“若干清单之间的状态转移”：

1. 待预处理清单
2. 已预处理清单
3. 待泛读清单
4. 正泛读清单
5. 已泛读清单
6. 待研读清单
7. 正研读清单
8. 已研读清单

这个理解方式本身是对的，因为它最接近科研工作流的人类心智模型。

真正要讨论的，不是“清单式状态机是否合理”，而是“在 SQLite 里要不要把这些清单直接实现成很多个 0/1 字段”。

## 二、结论先行

按当前开发阶段的目标，我的结论调整为：

1. 清单式状态机非常合适，应该保留为上位概念模型。
2. 当前阶段可以先用 `content.db` 中一张新的单表来承载状态机当前态。
3. 这张新表以 `uid_literature` 为唯一主键，每一个清单对应一个 0/1 列，另加一个 `研读次数` 计数列。
4. 文档层优先使用中文清单名和中文字段名进行表达，同时附一份中英对照表，供 SQLite 与 AOK 工具实现时使用。
5. 后续如果状态复杂度明显升高，再从“单表 0/1 当前态”升级到“当前态表 + 事件表 + 来源边表”。

换句话说，当前阶段的取舍是：

1. 先用单表实现，降低理解和开发门槛。
2. 先把主流程跑通，再在后续版本补充更细粒度的事件审计结构。

## 三、为什么清单式状态机是合适的

### 3.1 它符合科研真实行为

文献阅读不是单次直线流程，而是带回流的循环系统：

1. 先从综述或本地检索拿到候选。
2. 先做预处理，确保有可读资产。
3. 再做泛读筛选。
4. 其中一部分升级为研读。
5. 研读时又会发现新的候选文献。
6. 新候选再次进入预处理和泛读。

这本质上就是一个有限状态机，只不过节点名称是“清单”，而不是传统软件工程里的 `state_a -> state_b`。

### 3.2 它适合人工审计和 Git 提交节奏

你要求每跑完一个事务节点就可以 Git commit 一次，并记日志库。这种要求天然偏好“节点边界清晰、输入输出明确”的状态机设计。

如果没有清单化状态边界，就会出现以下问题：

1. 同一轮运行里混进预处理、泛读、深读多种改动。
2. 一次 commit 难以解释到底完成了哪一类动作。
3. gate 审计难以判断哪个阶段失败。
4. 回滚时无法只回滚某一个状态转移批次。

## 四、单表 0/1 方案的适用边界与风险

当前阶段改用“单表 + 0/1 清单列”是可以接受的，但必须明确它只是极简当前态方案。

### 4.1 为什么当前阶段它是合适的

1. 对人类阅读最直观，一眼就能知道某篇文献在哪个清单里。
2. 对事务开发最直接，A080、A090、A095、A100 只需要围绕同一张表改列值。
3. 对调试最方便，直接查询一行即可看到当前状态全貌。
4. 对当前“泛读只读一次、研读暂不自动重复进入”的约束足够用。

### 4.2 它的主要风险

1. 互斥清单可能被错误同时置为 1。
2. 来源关系不容易表达完整。
3. 历史状态变化无法只靠这张表完整回放。
4. 后续如果支持重复泛读、重复研读、在线检索回流，单表会逐渐变重。

### 4.3 当前阶段的控制原则

为了让单表方案尽量稳，必须遵守以下原则：

1. 每次状态转移都要先清旧清单，再置新清单，避免同层互斥清单同时为 1。
2. `已泛读清单` 一旦为 1，当前阶段默认不再回到 `待泛读清单`。
3. `研读次数` 单独维护，不用 0/1 代替。
4. 来源关系、推荐原因和审计信息先写入日志或导出文件，不强行塞进所有清单列。

## 五、推荐的数据建模思路

### 5.1 当前阶段的极简实现：单表当前态

建议在 `content.db` 中新增一张状态表，作为 A080、A090、A095、A100 四节点共用的当前态表。

推荐逻辑表名：文献阅读状态表

推荐物理表名：`literature_reading_state`

主键规则：

1. `uid_literature` 作为唯一主键。

这个设计表示：

1. 一篇文献在当前主链中只有一条当前状态记录。
2. 这条记录上直接挂载所有清单 0/1 列。
3. `研读次数` 用整数列记录。

### 5.2 当前阶段建议保留的清单列

推荐按当前清单模型直接落列。

逻辑清单名：

1. 待预处理清单
2. 已预处理清单
3. 待泛读清单
4. 正泛读清单
5. 已泛读清单
6. 待研读清单
7. 正研读清单
8. 已研读清单

此外增加一个计数列：

1. 研读次数

### 5.3 中文逻辑名与物理字段名对照建议

文档和人工讨论层，统一使用中文清单名。

SQLite 与 AOK 工具实现层，建议保留下列物理字段名：

1. `uid_literature`：文献 uid
2. `pending_preprocess`：待预处理清单
3. `preprocessed`：已预处理清单
4. `pending_rough_read`：待泛读清单
5. `in_rough_read`：正泛读清单
6. `rough_read_done`：已泛读清单
7. `pending_deep_read`：待研读清单
8. `in_deep_read`：正研读清单
9. `deep_read_done`：已研读清单
10. `deep_read_count`：研读次数
11. `source_stage`：来源阶段
12. `source_uid_literature`：来源文献 uid
13. `recommended_reason`：推荐原因
14. `analysis_light_synced`：轻量分析已同步
15. `analysis_formal_synced`：正式分析已同步
16. `innovation_synced`：创新点已同步
17. `updated_at`：更新时间

### 5.4 为什么仍然保留中英对照

原因不是要否定中文，而是为了兼容：

1. Python 代码中的 SQL 拼接和数据类字段。
2. 后续 AOK tools 的函数参数命名。
3. 将来如果要导出 JSON、CSV 或接入别的模块。

因此，本设计采用：

1. 逻辑层用中文。
2. 物理实现层保留英文别名对照。

## 六、当前阶段的推荐实现口径

当前阶段直接采用：

1. 新增单表 `literature_reading_state`
2. `uid_literature` 唯一主键
3. 清单用 0/1 列表示
4. `研读次数` 用整数列表示

不建议当前阶段做的内容：

1. 不急着引入多张事件表。
2. 不急着引入来源边表。
3. 不急着把所有状态抽象成多阶段队列机。

当前阶段先保证：

1. 清单状态一目了然。
2. 四个事务能稳定衔接成环。
3. Git commit 和审计文件可以对应每一轮动作。

## 七、适合当前阶段的极简实现

考虑到现在要快速推进，我建议把极简实现进一步收敛为“单表 + 中文清单 + 少量辅助列”。

### 7.1 极简真相源

只保留一张当前态表：`literature_reading_state`。

这一张表直接表达：

1. 这篇文献是否在待预处理清单。
2. 这篇文献是否已预处理。
3. 这篇文献是否在待泛读清单。
4. 这篇文献是否正在泛读。
5. 这篇文献是否已泛读。
6. 这篇文献是否在待研读清单。
7. 这篇文献是否正在研读。
8. 这篇文献是否已研读。
9. 这篇文献被研读了几次。

### 7.2 极简辅助字段

除了清单列与 `研读次数`，当前阶段仅建议增加：

1. `来源阶段`
2. `来源文献 uid`
3. `推荐原因`
4. `轻量分析已同步`
5. `正式分析已同步`
6. `创新点已同步`
7. `更新时间`

### 7.3 极简历史留痕

当前阶段不强制新建独立事件表。

状态变化历史先通过以下方式保留：

1. A080、A090、A095、A100 的审计文件
2. 日志数据库中的运行事实
3. Git commit 与任务绑定关系

## 八、对环路主链的建议结论

推荐保留如下主链：

1. A070 产出普通文献候选，写入 A080。
2. A080 做候选规整与预处理，输出到 A090。
3. A090 做逐篇泛读，输出到 A095 和 A100，同时把新发现候选回流到 A080。
4. A095 做批量分析笔记汇总，不直接承担主要队列转移，但为 A100 提供更稳定的主题判断背景。
5. A100 做深读、正式分析笔记修订和创新点笔记更新，同时把新发现候选回流到 A080。

因此，这四个节点形成的不是简单直线，而是：

`A070 -> A080 -> A090 -> A095 -> A100 -> A080`

其中：

1. A095 是分析收束节点，不是主要候选分发节点。
2. 真正闭环的是 A090 和 A100 对 A080 的回流。

## 九、最终建议

最终建议可以压缩为四句话：

1. 清单式状态机是对的，应保留。
2. 当前阶段先用 `content.db` 新增单表实现最清晰、最省力。
3. 这张表以 `uid_literature` 为唯一主键，清单列用 0/1，另加 `研读次数`。
4. 文档层统一用中文清单名和中文字段概念，代码实现层补一份中英对照即可。
