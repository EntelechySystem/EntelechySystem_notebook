# contentdb关系事实表与派生视图分层重构理论设计-设计-20260527-001

## 1. 问题定义

当前 content.db 已经形成以下混合状态：

1. 一部分对象是稳定事实表，例如文献主表、附件表、知识笔记。
2. 一部分对象是应用层根据别的字段重建出来的关系或实体，例如作者表、文献作者关联、知识文献关联、知识证据关联的部分更新路径。
3. 一部分对象是正式运行时读模型视图，例如文献流程状态、文献预处理、事务关联总视图、文献主附件视图。

该混合状态的问题不在于“用了 SQLite 还是没用 SQLite”，而在于对象职责没有完全收口，导致：

1. 关系真相源不唯一。
2. 某些同步路径采用整表删除再重写，容易覆盖人工修订与局部治理结果。
3. 事务程序、智能体、技能、文档对同一对象的认知口径存在轻微漂移。
4. 使用者容易把视图当成可回写对象，或者把派生缓存误认为事实对象。

因此，需要建立一套统一的理论分层，使 content.db 的每一类对象都具有唯一职责。

## 2. 术语说明

本文中的“事实表”“派生表”“读模型”属于数据建模术语，不是 SQLite 原生术语。

SQLite 原生对象主要包括：

1. 表。
2. 视图。
3. 索引。
4. 触发器。

本文使用以下工作术语：

1. 事实实体表：保存长期业务对象本身。
2. 事实关系表：保存对象之间需要被维护、审计、允许人工修订的关系事实。
3. 派生读模型：为查询、汇总、展示、流程调度而从事实对象投影出来的只读结果，优先使用视图实现。
4. 修复工具：当历史库或脏数据存在时，用于一次性回填或修复事实对象的程序，不作为常态主写入路径。

## 3. 单一主源原则

content.db 的重构必须遵守以下单一主源原则：

1. 任一业务事实只能有一个正式可写主源。
2. 视图只承担读职责，不承担事实回写职责。
3. 关系对象只要带有业务属性、人工裁定、审计字段或排序字段，就必须作为事实关系表存在。
4. 任一回填程序只能作为修复工具，不得默认承担主运行路径。

## 4. 分层设计

### 4.1 事实实体表

以下对象定义为事实实体表：

1. 文献主表。
2. 附件表。
3. 作者表。
4. 标签表。
5. 知识笔记。
6. 知识索引。
7. 文献分块集。
8. 文献分块。
9. 工作区节点状态。

这些表的职责是保存对象本身，而不是保存对象之间的关系。

### 4.2 事实关系表

以下对象定义为事实关系表：

1. 文献附件关联。
2. 文献作者关联。
3. 文献标签关联。
4. 知识文献关联。
5. 知识证据关联。

它们之所以必须保留为真实表，而不是只做视图，是因为这些对象带有下列业务属性中的至少一种：

1. 关系角色，例如主附件、补充附件、主关联、辅关联。
2. 关系排序，例如作者顺序。
3. 业务判断，例如是否第一作者、是否通讯作者、是否主项。
4. 关系来源，例如来源类型、来源字段。
5. 审计时间，例如创建时间、更新时间。

上述字段不是单边实体字段，不能安全并入文献主表、作者表、附件表或知识笔记表。

### 4.3 派生读模型

以下对象定义为派生读模型，原则上使用视图维护：

1. 文献附件总视图。
2. 文献主附件视图。
3. 文献作者关联总视图。
4. 文献标签关联总视图。
5. 作者总表。
6. 标签总表。
7. 文献流程状态及其总视图。
8. 文献预处理及其阶段筛选视图。
9. 事务关联总视图及 A060-A160 事务过滤视图。
10. 工作流总览视图。

这些对象的共同特征是：

1. 可由事实实体表与事实关系表计算得出。
2. 主要面向调度、审计、查询与展示。
3. 不应被事务程序直接写入。

## 5. 当前摘要列的定位

文献主表中的以下一对一摘要字段仍然保留，但其职责必须重新定义为“当前指针”而不是“实体替身”：

1. PDF 路径。
2. 主附件名称。
3. 结构化状态。
4. 结构化正文路径。
5. uid_标准笔记。
6. flow 当前态摘要列。
7. queue 当前态摘要列。

这些字段可以保留在文献主表，因为它们表达的是：

1. 当前主附件是谁。
2. 当前有效解析资产在哪里。
3. 当前有效标准笔记是谁。
4. 当前流程状态是什么。

但它们不能替代：

1. 附件实体。
2. 知识笔记实体。
3. 关系事实。

## 6. 写入原则

### 6.1 主写入路径

常态主写入路径必须改为：

1. 文献导入事务直接写 文献主表、附件表、文献附件关联、作者表、文献作者关联、标签表、文献标签关联。
2. 预处理、泛读、精读事务直接写 文献主表摘要列、附件表摘要列、文献解析资产、知识笔记、知识文献关联、知识证据关联。
3. AOE 只消费视图，不负责额外修复关系表。

### 6.2 修复路径

修复路径保留，但降级为工具路径：

1. 作者回填工具用于历史库修复，不作为 init_content_db 默认破坏性步骤。
2. 知识关系回填工具用于历史标准笔记修复，不作为每次保存后的默认整表刷新步骤。
3. 标签实体补齐可保留为非破坏式补齐工具，但不再整表删除重建。

## 7. 关于“视图先关联，再生成同名表”的理论判断

该方案不作为正式推荐方案，理由如下：

1. SQLite 同一 schema 下不能同时存在同名表与同名视图。
2. 从视图再生成表，本质上仍然是派生缓存，并没有消除同步问题。
3. 关系属性如果需要审计、人工修订和稳定主键，就应直接落在关系事实表，而不是从视图二次物化。

若未来确有需要，可采用“基础关系视图 + 关系属性表 + 最终组合视图”的高级方案，但这不是当前主收口方向。

## 8. 正式推荐方案

当前正式推荐方案为：

1. 关系事实进表。
2. 展示与调度投影视图化。
3. 修复工具与主写入路径分离。
4. 事务程序直接维护事实关系，不再依赖 init_content_db 或 save_tables 之后的整表关系回填。

## 9. 对 AOE / AOK / PA 的影响

### 9.1 对 AOK 事务的影响

1. 所有写 content.db 的事务程序必须明确自己写哪些事实实体表、哪些事实关系表、哪些摘要列。
2. 不再允许“先写文献主表，再指望 init_content_db 帮我把作者关系和知识关系推出来”的隐式路径。

### 9.2 对 AOE 的影响

1. AOE 继续只消费正式视图与摘要列。
2. AOE 不直接理解回填工具内部细节。
3. AOE 的调度判断以视图为准，不回退依赖旧队列表或中间快照。

### 9.3 对 PA 的影响

1. PA 解释 content.db 时，需要把 文献作者关联、文献附件关联、文献标签关联、知识文献关联、知识证据关联 明确视为事实关系表。
2. PA 需要把 文献作者关联总视图、文献标签关联总视图 等视为读模型，而不是原始关系真相源。

## 10. 验收准则

完成重构后，应满足以下准则：

1. init_content_db 不再默认破坏性重建作者关系、知识关系、标签实体。
2. 任意新导入文献在主写入路径中即可形成完整关系表，不需要额外整库回填。
3. 手工修订关系表后，重复初始化 content.db 不会覆盖该修订。
4. AOE 运行与 PA 判读仍只依赖正式视图，无需改回旧队列。
5. docs、技能、智能体对事实表/关系表/视图的口径一致。

## 11. 理论摘要

本次理论设计的核心不是“让 SQLite 替代应用层做全部关系维护”，而是：

1. 用 SQLite 的表保存事实。
2. 用 SQLite 的视图暴露读模型。
3. 用应用层事务程序维护事实写入。
4. 用修复工具处理历史异常，而不是让修复工具替代主运行路径。

简化表达为一句话：

关系事实进表，展示投影进视图，修复逻辑降级为工具，主事务直接维护单一真相源。
