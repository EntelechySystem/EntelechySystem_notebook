# ARK技能AOK事务化-copy-分析-20260318-001

**总原则**
AOK 现有 affair 的粒度，明显更偏“单一稳定职责”，而不是“一个 skill 对应一个大杂烩事务”。从 autodo-kit/autodokit/affairs/检索治理/affair.json、autodo-kit/autodokit/affairs/方法白名单选择/affair.json、autodo-kit/autodokit/affairs/本地文献导入/affair.json 看，默认模式是“一件事一个 affair”。  
例外是 autodo-kit/autodokit/affairs/CNKI桥接/affair.json，它之所以能一对多，是因为多个 mode 共用同一个 CNKI planner 域模型，输入输出和产物形态也基本同构。

所以判断规则可以直接定成这三条：

1. 单一职责、单一状态、单一主产物，优先一对一。
2. 一个 skill 里如果串了多个可独立复用、可独立失败、可独立审计的步骤，就拆成一对多。
3. 多个 skill 如果只是同一引擎的不同默认参数或不同 mode，就合并成多对一。

3. model_routing_dispatch
建议：当前阶段一对一，新建一个“模型路由调度” affair。

原因：
- 当前 skill 虽然内部有决策、调用、产物写入、trace 四段逻辑，但它们共同服务于一个稳定事务目标：给定任务约束，产出路由决策，并在需要时完成一次模型调用。入口在 AcademicResearch-auto-workflow/academicresearch_kit/skills/model_routing_dispatch.py。

- 如果现在就拆成“模型路由决策”和“模型调用执行”两个 affair，会把目前这个 skill 的简单接口拆碎，反而增加编排成本。

我建议的做法：
- 新建一个 affair：模型路由调度
- 保留两个 mode：
  - decision-only
  - live-call

什么时候再拆？
- 当后面不止百炼一个 provider

- 那时再拆成：
  - 模型路由决策
  - 模型调用执行

当前不建议先拆。

**多对一该怎么用**
你前面问的“几个 skill 合并一个事务，多对一”是有明确适用场景的，不是少见例外。

已经成立的例子：
- retrieval_governance 和 api_data_fetch
这两个 skill 本质上都只是检索治理引擎的不同默认参数，应该共同桥接到 autodo-kit/autodokit/affairs/检索治理/affair.py。
- 多个 CNKI skill
如果只是 cnki-search、cnki-advanced-search、cnki-download 这种 mode 差异，它们就适合继续合并到 autodo-kit/autodokit/affairs/CNKI桥接/affair.json 这种“同域多 mode affair”。

判断标准很简单：
- 是否共用同一 engine 或 planner
- 是否只是 mode 不同
- 是否共享同构输入输出
满足这三条，就适合多对一。

**不建议事务化的是谁，为什么**
不建议事务化的主要是 ark_workflow_executor。

对应文件是 AcademicResearch-auto-workflow/academicresearch_kit/skills/ark_workflow_executor.py。

不建议的原因：
- 它不是叶子业务事务，而是 workflow 运行入口。
- AOK 自己已经把“事务调用入口”和“工作流运行入口”分开了：
  - 直接事务调用在 autodo-kit/autodokit/api.py
  - 顶层 workflow 调度在 autodo-kit/autodokit/main.py
- 如果把 workflow executor 再包成一个 affair，就会出现“affair 里再跑 workflow，workflow 再调 affair”的递归语义。
- 这会让调度边界、审计边界、失败重试边界都变混乱。它更像 runtime service，而不是 business affair。

如果不事务化，该怎么处理：
- 保留它是一个 skill facade，没有问题。
- 如果你希望它更偏 AOK，可以把它改成：
  - 对单事务场景，调用 autodo-kit/autodokit/api.py 的直接事务运行接口
  - 对整条 workflow 场景，继续走 autodo-kit/autodokit/main.py
- 也就是说，它应该是“调度入口适配层”，不是“业务事务”。

  - 工作区自检
  - 模型路由调度
  - 百炼SDK接入检查
  - 中文本地资源管理
  - 中文网页采集规划
  - 白名单治理检查

  - retrieval_governance + api_data_fetch -> 检索治理
  - 同域 CNKI mode skill -> CNKI桥接
- 不建议事务化：
  - ark_workflow_executor

3. 最后补 中文本地资源管理、中文网页采集规划、白名单治理检查。
