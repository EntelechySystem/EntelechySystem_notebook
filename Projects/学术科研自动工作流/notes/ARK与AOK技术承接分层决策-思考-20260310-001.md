# ARK与AOK技术承接分层决策-思考-20260310-001

## 1. 需求分析与目标分析

### 1.1 当前需求

明确 AOK（autodo-kit）作为统一工作流技术底座时，如何承接日志治理、执行编排与回放能力，并形成可持续演进的工程分层。

### 1.2 目标拆解

- 目标 A：明确 AOK 的技术层边界（编排、日志、索引、回放、校验）。
- 目标 B：明确领域层边界（学术语义、审计口径、证据链规则）与技术层解耦方式。
- 目标 C：形成 AOK 可直接执行的分阶段方案，避免历史实现耦合导致后续维护分裂。

### 1.3 现状证据（基于仓库实况）

- AOK 当前已具备通用工作流核心：`affairs/`、`flow_graph/`、`scheduling/`、`taskdb/`、`tools/`。
- AOK 已采用统一契约方向：`workspace_root + run + skip`。
- AOK 已具备可扩展事务体系（`autodokit/affairs/*/`）与配置入口（`config/`、`workflows/`）。
- 当前缺口主要在日志治理统一化：事件事实源、索引层、回放对齐与跨任务检索仍需标准化。

### 1.4 可行性评估

可行，且建议采用“技术底座先行、领域语义后挂”的演进路径。

原因：

- AOK 自身已覆盖大部分通用执行能力，适合作为日志治理与编排统一入口。
- 领域语义能力不应下沉到通用内核，避免内核被业务规则污染。
- 先建设 AOK 原生日志治理体系，再通过适配层接入不同业务域，风险最低。

潜在挑战：

- 日志字段若不先冻结，会导致索引与回放脚本频繁破坏性变更。
- 事务实现若绕开统一日志接口，会造成日志漂移与可追溯性断裂。
- CLI、文档、示例 workflow 需要同步升级，避免“代码已变、文档滞后”。

## 2. 决策与计划

### 2.1 决策结论

采用“AOK 原生双层架构”推进：

- AOK 技术层统一承接：日志写入、日志索引、调度事件、回放入口。
- 业务领域层按插件/事务包方式挂载，不反向侵入技术层。
- 所有日志相关能力走统一接口，禁止业务代码直接写散落文件。

### 2.2 异同点与适用性列表

| 维度 | 领域层（业务） | AOK 技术层 | 结论与适用性 |
| --- | --- | --- | --- |
| 产品定位 | 面向具体业务场景 | 通用任务/事务工作流底座 | 领域变化快，底座应保持稳定 |
| 核心对象 | 业务事务语义与产物 | affair 执行、调度、日志、索引、回放 | 领域层定义语义，技术层保障一致性 |
| 执行模型 | 可有场景差异 | AOF/节点运行时/调度统一 | 执行机制统一有利于质量治理 |
| 配置契约 | 业务字段扩展 | `workspace_root + run + skip` 主契约 | 主契约统一，业务字段外挂 |
| 扩展方式 | 新增业务事务包 | 新增通用工具与运行时能力 | 双层独立演进，互不阻塞 |
| 日志与审计 | 定义审计语义与规则 | 负责事件落盘、索引、回放、校验 | 审计口径在领域层，日志基础设施在技术层 |
| CLI 生态 | 可按业务保留子入口 | `aok` 统一主入口 | 主入口统一，子入口可适配 |
| 维护成本 | 受业务复杂度影响 | 受技术债影响 | 通过分层可把技术债集中治理 |
| 适合承担内容 | 策略、门禁、证据规则 | 编排、日志、索引、回放、验证 | 边界清晰后可持续迭代 |

### 2.3 分阶段计划

#### 阶段 P0：边界冻结（1 周）

- 冻结“技术层 vs 领域层”责任矩阵。
- 定义统一日志 schema v1（JSONL 正文 + CSV 索引）。
- 定义统一调用协议（输入、输出、错误码、日志字段、脱敏规则）。

预期结果：迁移范围明确，避免盲目重构。

#### 阶段 P1：适配层落地（1-2 周）

- 在 AOK 内实现统一日志组件：`LogWriter`、`LogIndexer`。
- 接入 AOK 调度与事务执行主链路，确保开始/结束/失败/重试事件完整落盘。
- 保持现有事务输入输出契约不变，仅替换日志写入路径与接口。

预期结果：实现“统一日志底座无感接入”。

#### 阶段 P2：双轨验证（1 周）

- 对比旧日志方式与新日志方式的字段完整率与一致性。
- 校验 JSONL 与 CSV 索引可互相定位。
- 校验回放结果、任务状态、事务状态一致性。

预期结果：得到可量化迁移结论。

#### 阶段 P3：扩面迁移（按事务批次）

- 逐批接入全部核心事务与关键命令。
- 清理分散日志写入点，统一由日志组件托管。
- 同步更新 API 手册、开发者指南与示例 workflow。

预期结果：日志治理统一、检索回放统一、维护成本下降。

## 3. 任务分配（交付给任务运作智能体）

### 任务包 T1：差异基线与映射清单

- 任务内容：产出 AOK 技术层能力清单（日志、调度、回放）与领域层挂载点清单。
- 预期结果：责任矩阵 + 字段矩阵 + 调用矩阵。

### 任务包 T2：日志组件原型

- 任务内容：实现 `LogWriter` + `LogIndexer` 最小版本，覆盖开始/结束事件写入。
- 预期结果：在不改业务事务语义的前提下完成统一日志接入。

### 任务包 T3：一致性验证与回滚机制

- 任务内容：构建双轨回归脚本，校验 JSONL/CSV/回放一致性与回滚可行性。
- 预期结果：形成上线门槛与回滚开关。

### 任务包 T4：文档与契约同步

- 任务内容：同步更新开发者指南、API 手册、workflow 示例。
- 预期结果：文档与代码一致，降低误用风险。

## 4. 监控与调整

### 4.1 监控指标

- 执行成功率：接入前后同任务成功率差值。
- 日志一致性：JSONL 与 CSV 索引定位一致率。
- 回放一致性：taskdb/执行回放结果一致率。
- 故障可恢复性：异常时回滚到旧日志路径的耗时与成功率。

### 4.2 调整触发条件

- 若任一核心链路一致率 < 99%，暂停扩面迁移，仅修复适配层。
- 若审计链路出现字段缺失或状态机断裂，立即回滚到旧执行路径。
- 若迁移后维护成本不降反升，收缩接入范围并优先稳定日志基础设施。

### 4.3 风险最小化与回滚建议

- 全程保留旧日志路径读取兼容，不做一次性切换。
- 采用“功能开关 + 事务白名单”逐步放量。
- 每批迁移都保留可比对的执行日志与产物快照，支持按批次回退。

## 建议结论（供决策）

建议按“AOK 技术层先行统一日志治理，领域层后挂接入”的路径推进。该方案可以先解决当前日志分散、回放断裂、跨任务检索困难的问题，再逐步扩展到全链路事务，风险可控且收益明确。
