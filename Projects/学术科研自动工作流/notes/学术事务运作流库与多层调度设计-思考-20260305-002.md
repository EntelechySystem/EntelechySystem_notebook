# 学术事务运作流库与多层调度设计-思考-20260305-002

## 1. 需求分析和目标分析

### 1.1 需求分析
在确认“任务层 + 事务层 + 执行层”多层结构后，需要把学术事务运作流从“细粒度堆叠”调整为“主干精简 + 细节按需展开”。当前核心需求：

1. 建立一级事务主路网，降低事务节点全集的复杂度。
2. 允许一级事务按场景细化二级事务，但避免全部提前固化。
3. 用 AOK 承载事务、流程图、表格管理与执行留痕。
4. 用 CC 项目管理 agent 负责调度、任务状态机控制和跨流程协同。
5. 统一任务表、事务表、关系表与日志表，形成“可运行的数据面”。

### 1.2 目标分析
形成“主路网化 + 动态重规划 + 表驱动 + 双引擎协同”的落地蓝图：

1. 输出简化可控的一级事务主路网及默认连接关系。
2. 定义二级事务展开规则、准入门槛和升级机制。
3. 定义由 AOK 管理的核心表模型。
4. 定义由 CC 管理的动态调度职责和日志治理机制。

### 1.3 可行性与挑战
可行性：高。

1. AOK 已具备节点事务化编排能力。
2. ARW 已具备 CC 代理协同与审计体系。

挑战：

1. 事务节点全集若过细，事务运作流会出现排列组合爆炸。
2. 若未做版本治理，事务流容易发生“静默漂移”。
3. 若调度规则不统一，任务图和事务图可能冲突。
4. 研究过程天然非线性，若强行预设固定全路径会降低适应性。

## 2. 决策和计划

### 2.1 多层架构定版

1. 任务层（CC 主控）：任务生成、挂起、激活、注销、父子任务编排、前后任务编排。
2. 事务层（AOK 主执行）：一级事务主路网 + 二级事务按需展开。
3. 执行层（CC+AOK 协同）：agent/skill 调用 AOK workflow 执行具体动作，按步重规划下一跳。
4. 审计层（CC 双审计）：`whitelist-auditor` + `reproducibility-auditor` 输出结果码驱动回退。

### 2.2 一级事务主路网（精简版）

以下 15 个一级事务作为主节点：

1. 提出研究问题。
2. 确定研究目标。
3. 确定研究方法/数据。
4. 文献检索。
5. 数据检索。
6. 文献管理。
7. 文献阅读。
8. 数据管理。
9. 实证。
10. 实验。
11. 写作与修订。
12. 评审。
13. 事务管理。
14. 任务管理。
15. 总管理调度。

> 原则：一级事务只保留主干语义，不直接承载大量细节分支。

### 2.3 二级事务展开规则（按需细化）

一级事务可按场景细化为二级事务，但二级事务不应全部提前固化为独立流程图。

示例：

1. `文献检索` 可细化：国内开源、国内闭源、国外开源、国外闭源、本地检索。
2. `数据检索` 可细化：国内开源、国内闭源、国外开源、国外闭源、本地检索。
3. `文献管理` 可细化：去重、引用键对齐、证据分级、冲突对账。
4. `数据管理` 可细化：口径比对、谱系记录、变量字典、可识别性预检查。
5. `评审` 可细化：内部评审、外部意见拆解、修订后复审。

细化触发条件：

1. 当前一级事务执行失败，需要定位具体瓶颈。
2. 当前任务类型对某一子环节有高风险约束（如闭源授权）。
3. 审计要求新增证据链条，一级粒度不足以留痕。

### 2.4 一级事务关系图（非 DAG，可回环）

主路网是可回环的，不要求一次性线性跑通。常见事务运作流包括但不限于：

1. `提出研究问题 -> 文献检索 -> 文献管理`。
2. `文献管理 -> 文献阅读`。
3. `文献阅读 -> 思考 -> 确定研究目标`。
4. `文献阅读 -> 思考 -> 数据检索 -> 实证`。
5. `文献检索 -> 文献管理`。
6. `数据检索 -> 数据管理`。

说明：

1. 事务运作流可以是线性片段，也可以是子流程图。
2. 某些运作流可跨阶段贯穿全局（如事务管理、任务管理、总管理调度）。
3. 回环是常态，不是异常。

### 2.4.1 基本流向倾向分值（Base Transition Tendency）

为避免穷举固定事务运作流，建议在一级事务关系图上为每条边定义“基本倾向分值”。

定义：

1. 记一级事务节点为 `Ti`，候选下一事务为 `Tj`。
2. 记边 `Ti -> Tj` 的基本倾向分值为 `b(i,j)`，取值范围建议 `0-100`。
3. `b(i,j)` 越大，表示在一般场景下从 `Ti` 流向 `Tj` 的先验倾向越强。

参考边示例（可在后续校准）：

1. `提出研究问题 -> 文献检索`：`b=90`。
2. `文献检索 -> 文献管理`：`b=92`。
3. `文献管理 -> 文献阅读`：`b=88`。
4. `文献阅读 -> 确定研究目标`：`b=80`。
5. `文献阅读 -> 数据检索`：`b=72`。
6. `数据检索 -> 数据管理`：`b=90`。
7. `数据管理 -> 实证`：`b=85`。
8. `实证 -> 写作与修订`：`b=78`。
9. `评审 -> 写作与修订`（回环）：`b=89`。

### 2.5 执行策略：动态重规划而非预设全路径

具体执行一个任务时，事务运作流通常不是事先完全确定的，而是逐步演化的。

建议采用“逐步决策”机制：

1. 每执行完一个事务，基于最新状态重算下一事务候选集。
2. 候选集按“基本倾向分值 + 实时状态增量”计算综合分值。
3. 选择当前最优下一跳，不承诺远期固定路径。
4. 若结果码为 `RETRY/BACKTRACK/BLOCKED`，触发局部回退或切换分支。

建议评分形式：

1. 综合分值：`score(i,j)=w_b*b(i,j)+w_g*goal_gain+w_r*risk_penalty+w_c*cost_penalty+w_t*time_penalty+w_a*audit_bonus`。
2. 路由概率：`P(i,j)=softmax(score(i,j))`，按概率或按最大值选择下一跳。
3. 当审计硬约束触发时，直接将不合规边的 `P(i,j)` 置零。

说明：

1. `b(i,j)` 是先验，运行时特征是后验修正。
2. 这与神经网络“连接权重影响激活路径”的类比是成立的，但这里的权重可解释、可审计、可人工干预。

该机制可类比下棋：每走一步都要根据盘面变化更新后续路径。

### 2.6 AOK 入库策略：不是每个细化事务都要写成独立流

为避免流库膨胀，建议分层入库：

1. 一级事务：默认全部入库，作为稳定主路网。
2. 二级事务：仅将高复用、高风险、高审计价值子事务写入 AOK。
3. 临时性子事务：先以内联步骤运行，不立即沉淀为标准流。
4. 连续多次复用后，再升级为正式二级事务模板。

推荐准入门槛（满足其三即可）：

1. 最近 N 次任务中复用次数达到阈值。
2. 涉及授权、合规、复现等高风险环节。
3. 输入输出契约稳定，能标准化。
4. 失败代价高，值得独立监控与回放。
5. 审计要求强，需要独立日志链。

### 2.7 表驱动管理（由 AOK 事务实现）

建议以 AOK 事务维护以下表：

1. `tasks`（任务属性表）
- `uid, name, status, parent_uid, priority, hypothesis, owner_agent, created_at, updated_at`

2. `transactions`（事务属性表）
- `uid, name, level, input_schema, output_schema, audit_policy, retry_policy, version`

3. `task_transaction_map`（任务-事务关系表）
- `task_uid, flow_uid, step_order, transaction_uid, step_status, last_result_code`

4. `task_edges`（任务有向关系表）
- `from_task_uid, to_task_uid, edge_type, condition, active, base_tendency_score, dynamic_delta, transition_prob`

5. `flows`（事务运作流表）
- `flow_uid, flow_name, node_list, branch_rules, rollback_rules, version`

6. `flow_templates`（主路网模板表）
- `template_uid, template_name, level1_node_set, default_edges, policy, version`

7. `next_step_policy`（下一跳策略表）
- `policy_uid, candidate_rules, scoring_rules, risk_rules, audit_gate_rules, probability_rules, version`

8. `execution_runs`（执行日志表）
- `run_uid, task_uid, flow_uid, transaction_uid, agent_uid, skill_uid, aok_workflow_uid, result_code, audit_result, selected_edge, edge_score, edge_prob, started_at, ended_at`

### 2.8 CC 项目管理 agent 的调度职责

建议由 CC 的项目管理 agent（总经理/总设计）实现以下动作：

1. 任务图调度：创建、挂起、激活、恢复、完成、注销。
2. 事务流选择：根据任务属性与阶段状态选取一级事务与二级事务。
3. Agent 交接：按事务路段选择执行 agent，并记录交接日志。
4. 动态重规划：每步执行后重算下一跳，不固定全路径。
5. 审计裁决：读取审计结果码 `PASS/RETRY/BACKTRACK/BLOCKED` 后路由。
6. 日志治理：统一把任务事件写入 `logs/run/`，审计事件写入 `logs/audit/`。

### 2.9 启动前与接管后两种实施模式

启动前（预建模式）：
1. 优先固化 15 个一级事务与最小默认边集。
2. 只预建高复用二级事务，避免过早细化。
3. 完成 dry-run 以验证输入输出契约。

接管后（动态模式）：
1. 运行时发现缺口再新增二级事务。
2. 新事务通过准入门槛后注册进 flow 库。
3. 由 CC 调度将新事务接入当前任务图。

### 2.10 准入门槛（新增事务/流程图）

1. 必须声明 input/output schema。
2. 必须声明结果码与回退策略。
3. 必须声明日志字段与落盘路径。
4. 必须声明版本、兼容范围与回滚方案。

## 3. 任务分配

### 3.1 分配给任务运作智能体

任务 A：建立“一级事务主路网”
1. 内容：登记 15 个一级事务及其默认可回环边。
2. 产物：主路网索引文档与主路网版本清单。

任务 B：建立“二级事务白名单机制”
1. 内容：定义二级事务准入、升级、下线规则。
2. 产物：二级事务治理规范与样例。

任务 C：建立“动态重规划调度协议”
1. 内容：定义每步执行后的候选生成、评分、下一跳选择与回退机制。
2. 产物：调度接口说明与错误处理手册。

任务 D：建立“表驱动事务与日志模板”
1. 内容：实现 tasks/transactions/map/edges/flows/templates/policies/execution_runs 的增删改查事务。
2. 产物：AOK 事务定义、`logs/run/` 与 `logs/audit/` 模板。

任务 E：建立“三类 agents 分工模型”
1. 内容：明确总体管理类、事务类、任务类 agent 的职责边界与交接协议。
2. 产物：agent 职责矩阵与交接日志规范。

### 3.2 agents 三大类分工

1. 总体管理类。
- 角色：项目经理、项目设计师。
- 职责：目标拆解、路由策略、优先级、冲突裁决、审计裁决。

2. 事务类。
- 角色：负责各事务执行的专业 agent。
- 职责：在指定一级/二级事务内完成检索、管理、分析、写作动作并返回结构化结果码。

3. 任务类。
- 角色：负责具体任务包落地的执行 agent。
- 职责：把多个事务结果组装为任务交付物，维护任务上下文与依赖关系。

## 4. 监控和调整

### 4.1 监控指标

1. 主路网稳定度：一级事务节点与默认边的变更频次。
2. 二级事务复用率：已入库二级事务被重复调用比例。
3. 动态重规划命中率：每步重规划后一次选中有效下一跳的比例。
4. 调度稳定性：任务图与事务图冲突次数。
5. 回退有效性：`RETRY/BACKTRACK/BLOCKED` 后成功收敛比例。
6. 审计闭环率：每轮任务是否具备治理+复现双审计结论。
7. 日志完整率：任务、事务、审计日志是否全量留痕。
8. 倾向分值校准误差：`base_tendency_score` 与真实转移频率偏差。
9. 概率路由有效性：高 `edge_prob` 边的实际成功率。

### 4.2 调整机制

1. 若主路网频繁改动：冻结一级事务范围，只在二级层调整。
2. 若二级事务膨胀：提高入库阈值，优先以内联步骤运行。
3. 若图冲突高：统一任务图优先于事务图，补充冲突裁决规则。
4. 若回退过多：前移验证事务，减少下游返工。
5. 若日志缺失：禁止进入下一节点，先补齐留痕。

### 4.3 本轮结论

“一级事务主路网 + 二级事务按需展开 + 每步动态重规划 + 表驱动治理 + CC 调度 + AOK 执行 + 双审计裁决”是更可控的主路径。它能够在不牺牲探索性的前提下，显著抑制事务流数量爆炸，适合 ARW 的长期演进。
