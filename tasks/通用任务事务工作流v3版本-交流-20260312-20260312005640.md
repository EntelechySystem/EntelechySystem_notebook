## me-1

一个任务可以分为两个维度：
- 工作流项目（简称工作流，或者流Workflow）
- 事务（使用情景）

工作流项目对应于一次完整或者半完整的自动运作流程。每个工作流项目可以有不同的任务，这些任务串起来顺序运行。任务根据不同的使用情景（事务）分为不同类型的任务。这些任务有不同的类型。

举一个例子。工作流项目1是一个流程。每一个流程包括多个任务串行组成。这些任务类型不同，对应的事务不同（使用情景）。这些任务分别是：
1. 自动化导入知网研学的文献到专题；
2. 手动提取专题的文献原文PDF文件和导出题录元数据；
3. 将导出的题录元数据和文献原文导入和预处理以生成文献元数据；
4. 根据关键词筛选查阅相关的文献元数据获取相关文献的信息； 
诸如此类的各种事务。这些类型的事务对应的任务串起来运行形成了一次学术流程。工作流项目1对应的这一次学术运作流程。






### AI Agent 工作流运作全过程



AI Agent 流程图运作过程中，有哪些需要管理的内容？业务逻辑是，项目经理 agent（PA）使用各种 skills 宏观管理整个流程图的运作。包括生成 task，分配 task agent（TA）调用相应的 skill 在流程图的某个子流程上面运行。

任务管理是：TA 驱动一个任务（ task ）在流程图节点沿着事务流运行。如果遇到分岔路，那么需要判断 task 要不要分出子 task 。task 要不要先挂起，然后然前向 task 先运行。这些都涉及到 task 管理。task 管理系统负责存储所有当前运行的、挂起的、已经注销的 task 之属性及其 task 与 task 之间的图连接关系。以便于 TA 或者 PA 管理。 TA 和 task 是一对一关系，就像一位司机只能驾驶一辆车。PA 和 TA 是一对多关系。整个项目只有一个 PA ，他负责运筹调度各 TA 。
TA 的任务从一个节点流向下一个节点的时候。需要决策。决策依据是：
- 事务执行结果；

决策内容是：
- 该任务是否继续？
- 如果不继续，则反馈给 PA 当前任务执行情况，让 PA 根据整体情况裁决。
- 如果继续，则也要反馈 PA 当前任务执行情况，让 PA 根据整体情况裁决。

节点管理是：每当一个任务运行到一个节点的时候，流程图自带的节点管理器（node manager，简称 NM）就要进行节点运作：
 1. 根据节点属性判断是否有开启了节点司（node agent，简称 NA）；
 2. 将任务派发给节点对应的事务，让 AA 进行管理。
 3. 根据以下几种方法来决策：
	 1. 根据节点流程图的基本流向倾向分值（流程图节点之间的边权重，如果节点之间没有连边，则权重不存在，可以视作值为0）来决策该节点对应的下一个节点是什么？特别对于有环路的情况或者有分支的情况
	 2. 如果有 NA，则由 NA 辅助判断节点流向的下一个节点。


事务管理是：在流程图的每一个节点上都有一个事务（affair），节点之间代表事务的流向。每一个事务有相关的事务 agent （AA）管理。AA 调用相应的 skill 来执行事务。执行结果返回给 TA 。


信息管理是：各个 agent 之间各种传递的信息，需要用信息管理系统来管理。注意，这里说的信息管理系统不是广义的信息管理系统。


日志管理是，对于 PA、TA、NA、AA 的每一个操作，都要写一个对应的日志。日志全部汇总到一个日志文件（json 文件）、一个日志索引数据库（csv 文件）

**用算法形式重写一遍**

下面我给你一版 v3 可直接落地的最小算法。

第一阶段：事务执行

输入：
当前任务 task
当前节点 node
当前事务 affair
当前上下文 context

输出：
事务回执 receipt

事务回执最小结构：

- result_code
- block_reason_code
- block_scope
- retryable
- requires_human
- evidence
- message

事务执行算法：

1. AM 执行当前事务。
2. 如果事务完成且输出满足契约，返回 PASS。
3. 如果事务失败，但问题可在当前点修复，返回 RETRY。
4. 如果事务失败，且说明当前路径选错了，返回 BACKTRACK。
5. 如果事务失败，且自动流程在当前治理边界内不能继续，返回 BLOCKED。

第二阶段：节点归一化

输入：
事务回执 receipt
节点配置 node_policy
任务上下文 task_context

输出：
节点控制结果 node_outcome

节点归一化算法：

1. 读取事务回执。
2. 如果 result_code 不是 BLOCKED，则直接透传。
3. 如果 result_code 是 BLOCKED：
   4. 判断阻断只影响事务本身，还是影响整个节点。
   5. 必要时把 block_scope 提升为 node。
   6. 补充节点证据与节点策略说明。
7. 形成节点控制结果。

第三阶段：TM 生成候选动作包

输入：
node_outcome
task_state
retry_count
history_summary

输出：
candidate_actions

候选动作只保留这 6 个：

1. continue
2. retry
3. backtrack
4. suspend
5. split
6. human_gate

生成规则：

1. 如果 result_code = PASS
候选动作 = continue

2. 如果 result_code = RETRY 且 retryable = true 且 retry_count 未超限
候选动作 = retry

3. 如果 result_code = BACKTRACK
候选动作 = backtrack

4. 如果 result_code = BLOCKED 且 requires_human = true
候选动作 = human_gate

5. 如果 result_code = BLOCKED 且 retryable = false 且存在多个可替代子目标
候选动作 = split 或 suspend

6. 如果 result_code = BLOCKED 且既不能 retry 也不能 split
候选动作 = suspend 或 human_gate

第四阶段：PA 裁决

输入：
candidate_actions
task_summary
node_summary
evidence

输出：
final_decision

PA 裁决算法：

1. 读取候选动作包。
2. 检查当前任务目标是否仍成立。
3. 检查是否需要分裂子任务。
4. 检查是否需要人工外部确认。
5. 在 candidate_actions 中选一个最终动作。
6. 回写 task 状态与运行轨迹。
7. 写 decisiondb 和 logdb。

第五阶段：任务状态回写

我建议 v3 保留最简状态：

1. ready
2. running
3. suspended
4. blocked
5. completed
6. failed
7. cancelled

回写规则：

1. continue -> running
2. retry -> running
3. backtrack -> running
4. split -> 父任务 suspended，新子任务 ready
5. human_gate -> blocked
6. 无合法后续且目标不可达 -> failed
7. 达成目标 -> completed

- evidence = 缺少构建文件路径

含义：
不是权限问题，也不是永久失败，而是依赖没齐。

PA 常见裁决：
suspend 或回到上游任务补产物

3. 办公流程缺少公文编号

事务回执：

- result_code = BLOCKED
- block_reason_code = missing_required_input
- block_scope = node
- retryable = false
- requires_human = true
- evidence = 表单校验失败记录

含义：
当前节点没有足够信息，不能继续自动流转。

PA 常见裁决：
human_gate

**你说像马尔可夫决策或强化学习，这个判断对不对**

对，抽象上很像。

你现在这套系统确实可以表达成：

当前状态
到
观察
到
决策
到
行动
到
新状态

所以从理论上，它可以被建模为 MDP，甚至以后可以引入强化学习或策略学习。

但我明确建议：
v3 不要上强化学习。

原因不是它不高级，而是它会把你当前最缺的东西掩盖掉。你现在最缺的是：

1. 状态定义
2. 结果码协议
3. 决策记录
4. 任务状态机
5. 人工闸门边界

这些都还没冻结。如果现在上 RL，最后只会得到一个“会选动作的黑箱”，但你连它在什么状态下做了什么都未必解释得清楚。

所以我建议路线是：

1. v3
纯规则 + PA 裁决 + 完整决策记录

2. v4 或以后
在 decisiondb 和 logdb 积累足够数据后，再做统计学习、策略推荐、甚至 RL 辅助 PA

也就是说，先把规则系统跑通，把日志和决策记录沉淀好，后面学习系统才有数据基础。

**那规则决策到底怎么写，才不模糊**

我建议你把 v3 的规则系统压缩成一张小表，不要写成很长的自然语言规范。

最小规则表如下：

1. 如果 result_code = PASS
则推荐 continue

2. 如果 result_code = RETRY 且 retryable = true 且 retry_count < max_retry
则推荐 retry

3. 如果 result_code = BACKTRACK
则推荐 backtrack

4. 如果 result_code = BLOCKED 且 requires_human = true
则推荐 human_gate

5. 如果 result_code = BLOCKED 且 block_reason_code = dependency_unready
则推荐 suspend

6. 如果 result_code = BLOCKED 且 block_reason_code = permission_missing
则推荐 human_gate

7. 如果 result_code = BLOCKED 且 block_reason_code = goal_ambiguous 且存在多个子目标候选
则推荐 split

8. 如果 result_code = BLOCKED 且无合法恢复路径
则推荐 failed 或 cancelled

这就是 v3 的规则决策核心。非常简单，但已经能跑。
