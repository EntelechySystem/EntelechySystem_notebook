# think-ES微观思维运作系统初步设计-20260324-002

## 1. 需求分析和目标分析

### 1.1 微观系统要解决什么问题

ES 的微观思维运作系统，不应直接等价为传统意义上的神经网络实现，也不应直接等价为旧版 ES 中以数组堆叠为主的模型实现。它要解决的核心问题是：

1. 如何以 Unit 作为基础构件，统一表示认知系统中的各类细粒度功能件。
2. 如何让这些 Unit 在连接、激活、抑制、传递、调制、组合、装配的过程中形成更复杂的局部功能结构。
3. 如何让微观运行结果向上支撑宏观任务、问题、状态与决策，而不是与宏观层完全断裂。

### 1.2 为什么不能直接沿用旧实现

现有 ES 旧实现已经揭示了一些正确方向，例如：

1. 用统一数据结构表示不同类型的运作单元。
2. 给单元分配 gid、uid、type、input、output、connection、content、notes 等字段。
3. 把 neuron、goal、task、state、question、conception 等对象放在同一类型学下观察。

但旧实现同时暴露了明显局限：

1. 结构层偏静态数组与矩阵，缺少明确的单元协议层。
2. 连接表达偏“存储连接关系”，而非“执行连接关系”。
3. 缺少事件驱动、局部传播、状态更新与调制规则的清晰抽象。
4. 缺少面向组合结构的层次化装配机制。
5. 多个实现版本并存于 Numpy、PyTorch、JAX，但没有收敛到统一架构。

### 1.3 微观系统的目标

微观系统第一阶段的目标应当是“定义微观协议”，而不是马上追求仿脑规模。

具体目标为：

1. 定义什么是 Unit。
2. 定义 Unit 可以有哪些类型。
3. 定义 Unit 之间如何连接、触发、传播、调制与组合。
4. 定义微观局部结构如何被装配成更高阶功能组件。
5. 定义微观系统如何向宏观系统暴露可调用结果。

### 1.4 可行性与挑战

可行性来源于两方面：

1. ES_notebook 的 CIS 理论与开发笔记已经提供了大量关于机、件、器、门、功能、层次、装配的思考。
2. ES 旧代码已经沉淀了一批 Unit 级原型结构，可作为反例与迁移参考。

主要挑战则包括：

1. 旧代码方向多、版本多，容易陷入历史实现包袱。
2. 如果 Unit 类型定义不够清晰，系统会重新退化成混乱的数据容器。
3. 如果没有传播与调制协议，微观系统只能停留在静态存储结构。
4. 如果没有组合规则，微观系统无法从单元走向功能件与局部模块。

## 2. 决策和计划

### 2.1 核心决策

本轮微观系统建议先做以下决策：

1. 以 Unit 而不是 neuron 作为基础抽象名词。
2. neuron 只是某一类 Unit，而不是所有微观结构的默认原型。
3. 微观系统先定义协议，再定义实现后端。
4. Numpy、PyTorch、JAX 等仅是执行后端选择，不是架构本体。
5. 微观系统最终应能装配出局部功能模块，并向宏观系统暴露接口。

### 2.2 建议的微观对象结构

第一版建议至少定义以下微观对象：

1. UnitSpec
   - 描述单元类型、输入口、输出口、内部状态槽、可接受信号类型、调制接口。
2. UnitState
   - 描述单元当前激活值、阈值、耗散状态、冷却状态、缓存、局部记忆等。
3. UnitPort
   - 描述单元的输入输出端口与可连接协议。
4. LinkSpec
   - 描述连接方向、连接强度、连接类型、传播延迟、条件触发规则。
5. SignalPacket
   - 描述微观传播中的最小信号包。
6. ModulationRule
   - 描述抑制、增强、门控、偏置、累积、衰减等调制规则。
7. UnitAssembly
   - 描述多个 Unit 组成的局部装配模块。
8. MicroExecutionStep
   - 描述一次微观传播或更新步的输入、计算、输出和状态变化。

### 2.3 建议的 Unit 类型族

参考现有手稿与旧代码，第一版不宜只保留 neuron。建议把 Unit 类型分成若干族：

1. 感知类 Unit
   - 接收外部或内部观测信号。
2. 表征类 Unit
   - 承载概念、标签、特征、状态模式。
3. 逻辑类 Unit
   - 实现条件判别、匹配、组合、门控。
4. 传输类 Unit
   - 负责信号转发、汇聚、扩散、选择。
5. 调制类 Unit
   - 实现增强、抑制、偏置、优先级调整。
6. 容器类 Unit
   - 承载局部集合、缓存、中间态。
7. 控制类 Unit
   - 承担局部调度、局部同步、局部节拍控制。
8. 执行映射类 Unit
   - 把微观结果映射到宏观事件、状态或动作线索。

### 2.4 建议的运行机制

微观系统应采用离散执行步或事件驱动执行步，而不是仅仅存储静态数组。

建议每个微观步包含：

1. 收集输入信号。
2. 做局部匹配与门控。
3. 更新单元内部状态。
4. 执行调制规则。
5. 生成输出信号。
6. 写入连接传播队列或下一步缓存。
7. 必要时写入局部可观测摘要，供宏观层使用。

### 2.5 建议的组合层级

微观系统不应停在单个 Unit。建议定义以下组合层级：

1. Unit
2. MicroCircuit
3. FunctionalAssembly
4. LocalMachine
5. MacroInterface

含义如下：

1. Unit 是最小构件。
2. MicroCircuit 是若干 Unit 与 Link 形成的局部传播网络。
3. FunctionalAssembly 是围绕某一功能形成的装配结构。
4. LocalMachine 是可复用的局部机器件。
5. MacroInterface 是面向宏观任务系统输出的接口层。

## 3. 任务分配

### 3.1 交给任务运作智能体的实施任务

建议按以下顺序推进：

1. 先写一版微观协议草案。
   - 预期结果：明确 UnitSpec、LinkSpec、SignalPacket、UnitAssembly 等字段。
2. 再做一版最小运行原型。
   - 预期结果：实现一个极小的事件传播或离散步传播引擎。
3. 再构建 2 到 3 个典型局部模块样例。
   - 预期结果：例如匹配模块、门控模块、局部缓存模块。
4. 最后再设计微观到宏观的接口。
   - 预期结果：让微观系统可以向宏观层输出状态摘要、触发信号、概念激活或约束变化。

### 3.2 不建议当前立即做的事

1. 不建议直接恢复旧版所有模型分支并继续维护 Numpy、PyTorch、JAX 三套实现。
2. 不建议一开始就追求大规模并行性能优化。
3. 不建议一开始就把所有旧版 Unit 类型硬兼容进新协议。

## 4. 监控和调整

### 4.1 监控重点

微观系统后续实施时，建议重点监控：

1. Unit 协议是否足够清晰，能否承载不同类型单元。
2. Link 与 Signal 的定义是否足以描述传播与调制。
3. 局部装配是否能稳定复用，而非每次手写特例。
4. 微观输出是否能稳定映射到宏观状态或任务线索。
5. 执行步模型是否足够简单可验证。

### 4.2 调整策略

如果推进过程中发现问题，建议这样调整：

1. 若 Unit 过于抽象不可实现，则先收缩到 3 到 5 种最基本类型。
2. 若传播规则过于复杂，则先收缩为离散步更新模型。
3. 若组合机制混乱，则先从固定模板式装配开始。
4. 若宏微接口不清，则先输出有限的状态摘要和事件触发信号，不直接暴露全部内部细节。

## 5. 本轮 think 的结论

本轮关于 ES 微观思维运作系统的结论是：

1. 微观系统的正确起点是 Unit 协议，而不是继续扩写旧数组模型。
2. neuron 应是某类 Unit，而不是唯一原型。
3. 微观系统的关键不只是存储结构，而是连接、传播、调制、组合与局部装配规则。
4. 微观系统应当逐步装配出局部功能件，再向宏观任务中心系统暴露接口。
5. ES 旧代码适合作为历史原型与迁移线索，但框架和思路都需要重新设计改造。
