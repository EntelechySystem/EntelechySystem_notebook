# ES宏观思维运作系统初步设计-思考-20260324-001

## 1. 需求分析和目标分析

### 1.1 需求是什么

当前需要为 ES 设计一套宏观思维运作系统。这里的“宏观”不是指更抽象的空谈层，而是指高于 Unit 级别、直接围绕任务推进、问题生成、决策循环、计划调整、回溯恢复与人机协作的运行系统。

结合现有材料，需求可以拆成以下几项：

1. 要把 ES_notebook 中长期积累的任务驱动思维理论转译成可实现的系统对象与运行闭环。
2. 要避免把 ES 宏观系统做成单纯知识检索器，或做成只有节点执行的普通流程图系统。
3. 要能复用 autodo-engine 已经成熟的任务步闭环、状态机、候选动作、决策记录与审计框架。
4. 要能复用 autodo-kit 已经成熟的任务、知识、文档、Obsidian、工具桥接能力。
5. 要给未来的 ES 微观 Unit 系统预留接口，但不让宏观系统被微观细节牵制。

### 1.2 目标是什么

宏观思维运作系统的目标不是“尽可能模拟人脑全部细节”，而是先构造一套可运行、可回放、可治理、可与知识和工具环境协同的任务中心思维系统。

其阶段性目标应为：

1. 把任务定义成运行态核心对象。
2. 把问题定义成任务推进中的一级驱动对象。
3. 把状态、需求、证据、约束、候选动作、决策记录组织成稳定的数据结构。
4. 把任务步闭环定义成最小推进单位。
5. 把过程痕迹沉淀为决策记录、任务文档、知识条目与经验条目。

### 1.3 可行性分析

本方向可行，原因如下：

1. ES 代码中已存在 goal、task、state、question、conception 等类型学基础。
2. ES_notebook 中已有较成熟的任务、问题、需求、状态、分析、嵌套、回溯、判断点相关理论。
3. autodo-engine 已经提供运行控制面，不需要从零重写任务步引擎。
4. autodo-kit 已经提供外部记忆与工具环境，不需要从零重写知识/文档/Obsidian 桥接。

### 1.4 潜在挑战

主要挑战有四个：

1. ES 旧代码与手稿之间存在时间跨度大、表达口径不完全一致的问题。
2. ES 现有代码在宏观层还缺少真正的调度与推理实现，不能直接继承为现成内核。
3. 如果不严格界定宏观对象，很容易让系统退化成“节点执行系统”或者“知识问答系统”。
4. 如果不定义好元思考外化机制，系统将缺少可积累、可审计、可复盘的思维痕迹。

## 2. 决策和计划

### 2.1 核心决策

本轮思考建议确定以下核心决策：

1. ES 宏观思维运作系统以任务树为运行态中心。
2. 知识网络作为资源池与长期记忆，而不是运行时主递归结构。
3. 任务步而不是节点执行，作为最小推进单位。
4. 决策痕迹、任务文档、知识沉淀共同构成元思考外化层。
5. ES 负责认知语义层，autodo-engine 负责控制面，autodo-kit 负责外部记忆与工具面。

### 2.2 宏观系统分层

建议把宏观系统拆成五层：

1. 任务语义层
   - 定义 Goal、Task、Question、State、Plan、Constraint、Evidence 等对象。
2. 运行控制层
   - 采用任务步闭环，承接状态机、候选动作、回执协议、决策路由。
3. 认知资源层
   - 组织知识条目、案例、规则、经验、文献、概念等长期记忆资源。
4. 外部记忆层
   - 负责任务文档、决策记录、过程记录、知识条目、附件与引用。
5. 治理审计层
   - 负责决策可回放性、人工闸门、阻塞治理、风险控制与复盘。

### 2.3 核心对象建议

宏观系统第一版建议显式定义以下对象：

1. MacroTask
   - 宏观任务对象，承载任务标题、目标、当前状态、当前节点、约束、优先级等。
2. GoalObject
   - 目标对象，定义结果导向与完成条件。
3. QuestionObject
   - 问题对象，定义认知缺口、问题来源、问题状态、关联任务。
4. StateSnapshot
   - 状态快照对象，定义当前观察、资源、阻塞、上下文摘要。
5. DecisionTrace
   - 决策痕迹对象，记录候选动作、选择原因、参与成员、证据与覆盖解释。
6. ResumePoint
   - 中断恢复点对象，记录中断原因、恢复条件、恢复入口。
7. CompletionJudge
   - 完成判别器，负责判断某问题或任务是否可以进入下一阶段。
8. KnowledgeBinding
   - 知识绑定对象，负责任务与知识、文档、附件、案例之间的引用关系。

### 2.4 主循环建议

建议宏观主循环采用以下闭环：

1. 装载当前任务上下文。
2. 装载当前任务节点或局部阶段上下文。
3. 收集观测与状态变化。
4. 规范化执行回执与观测结果。
5. 生成候选动作与问题清单。
6. 调用决策部门给出当前步决策。
7. 执行动作、生成子任务、回溯或挂起。
8. 写入状态迁移、决策痕迹、文档更新与知识沉淀。
9. 判断是否终止、等待、阻塞、恢复或继续下一步。

### 2.5 与现有仓库的接口计划

建议采用“少改 ES、多复用现成控制面”的策略：

1. ES
   - 新增宏观对象模型与任务中心语义适配层。
2. autodo-engine
   - 直接复用任务步主循环、状态机、候选动作、决策结果和审计能力。
3. autodo-kit
   - 直接复用任务文档、知识索引、Obsidian 依赖解析、工具与 LLM 路由能力。

## 3. 任务分配

### 3.1 交给任务运作智能体的任务

建议后续由任务运作智能体按以下顺序实施：

1. 先整理一份 ES 宏观对象结构草案。
   - 预期结果：形成 Python 数据类或协议层草案，不急于接入旧代码。
2. 再整理宏观主循环状态图。
   - 预期结果：把 continue、retry、split、backtrack、suspend、complete、fail、cancel 等动作映射到 ES 宏观对象层。
3. 再设计 ES 到 autodo-engine 的适配边界。
   - 预期结果：明确哪些字段由 ES 提供，哪些字段由 autodo-engine 管理。
4. 再接入 autodo-kit 的文档与知识层。
   - 预期结果：能为每个任务步沉淀文档痕迹与知识引用痕迹。

### 3.2 暂不建议立即实施的任务

1. 不建议现在直接重写 ES 全部旧模型实现。
2. 不建议现在直接把微观 Unit 系统一并实现。
3. 不建议现在就做全仓库兼容性修补。

## 4. 监控和调整

### 4.1 监控指标

后续在宏观系统落地时，建议重点监控以下指标：

1. 一个任务是否能形成完整的任务步闭环。
2. 决策记录是否足够解释为什么做出该动作。
3. 子任务拆分、回溯、中断恢复是否有明确痕迹。
4. 任务与知识、文档、附件之间是否能形成稳定引用。
5. 人工闸门是否只在真正高风险或高不确定性场景触发。

### 4.2 调整策略

如果实施过程中出现偏差，建议这样调整：

1. 若系统退化为简单流程图执行器，则补强问题对象、状态对象和完成判别器。
2. 若系统退化为知识检索器，则强化任务树与任务步闭环的中心地位。
3. 若系统难以复盘，则补强决策痕迹结构与文档沉淀流程。
4. 若 ES 与 autodo-engine 耦合过深，则回退到更薄的适配层设计。

## 5. 本轮 think 的结论

本轮关于 ES 宏观思维运作系统的结论是：

1. 宏观系统应该被定义为任务中心认知系统。
2. 它的运行态应是任务树与问题树，而不是知识图本身。
3. 它的最小推进单元应是任务步闭环，而不是节点执行。
4. 它应通过决策记录、任务文档与知识沉淀实现元思考外化。
5. 它最合理的工程路线是：ES 定义语义层，autodo-engine 提供控制面，autodo-kit 提供外部记忆与工具环境。
